## 原始修复设计边界

1. **独立差额责任**：按过账批次记录方向、对方、币种、初始金额、已处理额/待处理额、责任人、凭证关联和状态。不得把多收货值伪装成销售现金回款，或通过修改订单 paidAmount 来平掉应付差额。
2. **原子、唯一、可回读**：责任记录与货抵过账同一事务；同批次只能生成一笔原始责任，重放不可重复。金额来自被冻结的估值，而非前端任意覆盖。
3. **允许不同处置方案**：退款、结转可用余额或经审批的调整须有明确业务凭证；登记责任不等于实际付款。未经授权不自动向外支付资金。
4. **拆开完成状态**：抵扣数量/金额完成与差额处置完成分别呈现。不能仅因 remainingOffsetAmount=0 就向使用者暗示全部财务义务已结清。
5. **反冲与并发**：未处置的责任可随原批次原子撤销；已退款/已使用余额的批次须阻止直接反冲，或走完整补偿凭证链，不能删除历史。测试双财务同时处置、重复请求、处置与反冲竞争。
6. **验收**：覆盖负 50 的生成/处理/回读、重复处理不增加金额、不同币种不混算、反冲恢复、财务与销售权限边界、浏览器实际操作、双实例 API 和数据库对账；迁移同时覆盖 SQLite 与 PostgreSQL。

以上为设计边界，不等于全部方案已实现；实际完成范围如下。不改动原验收目录，不以文案调整替代财务模型修复。

## 已实现的首个处置路径（2026-09-27）

- 新过账负差额在同一事务内产生唯一 `BarterCashObligation`，冻结金额、原币种、对方与责任人。没有伪造销售现金回款；退款登记不更改销售已收、实物库存或库存成本。
- 财务用原币全额、实际日期、外部付款凭证、核对说明登记**已经在外部完成的退款**。本入口不实际打款，不支持部分退款、结转余额、跨币种换算或任意抹账。负差额过账与关联订单币种不一致时拒绝，事务无副作用。
- 销售角色不能登记；后端沿用 `barter.post` 和记录数据范围校验。请求键与付款凭证具有唯一约束；相同人、相同键、相同凭证重放返回原结果，不重复审计。相同凭证不能处理第二笔责任。
- 退款和反冲先锁同一批次，再处理责任。开放责任可随货物反冲原子转为 `void`；已登记退款或历史待核对责任禁止直接反冲，不删除凭证。
- 协议列表独立提示“抵扣完成 · 差额待处理”；台账原币金额不受全局显示汇率转换影响。浏览器首次提交后冻结键与凭证，服务端成功而客户端丢包时仍按原键重试。
- SQLite / PostgreSQL 新增表与索引。既有已过账负差额仅回填 `review`，因为不能断言历史上未在外部退款；不捏造付款信息、不开放再次支付。历史核对处置工作台尚未实现。
