# 发货创建请求 v1：边界与兼容

## 单一业务写入边界

`shipment-submission.service.ts` 负责现有发货创建事务：订单数量声明、物料/批次校验、发货单、创建审计、原始回执一起提交或回滚。不建立新工作流、库存表或通用幂等平台。

现有 `shipments` 只追加三个可空字段：`submission_key`（唯一）、`submission_fingerprint`、`submission_json`。旧单保留 NULL；SQLite 升级和 PostgreSQL 迁移均为追加，不改旧凭证。

## API

- `POST /api/shipping` 接受稳定的 `Idempotency-Key`，或兼容的 `idempotencyKey` 请求字段；两者同时提供必须相同。
- 第一次创建返回 201；原操作人、同键、同原始内容重放返回 200 和**原创建回执**。不同内容或不同操作人不能取得该单。
- `GET /api/shipping/submissions/:key` 仅供原操作人确认原请求，仍要求 `shipping.write` 和原有仓库数据职责。其他人或不存在的键返回 404。
- 创建回执冻结 `pending` 创建事实，不代替当前物流状态。出库后重放不能再次扣库存、记成本或把状态改回 `pending`；当前状态从现有台账读取。
- 回执与原始审计及关键发货字段不一致时拒绝确认，不静默当作“未创建”。普通物流列表不公开私有请求身份与回执。

## 两个原生入口

订单行发货和 OCR 建单共用 `shipmentSubmissionIntent.ts`：按操作人及入口保存原内容，存储写入并回读成功后才 POST；网络中断后只恢复原键、原内容。订单最后余量全部分配后仍保留恢复入口。OCR 仍须人工选择已发布物料，且同步挡住重复点击。

清理浏览器原请求前校验键、操作人、事实、SHA-256 指纹、发货身份及原始回执；损坏存储/回执不能自动生成新键。

首次 POST 收到确定的业务回滚（例如批号不存在），仅在服务器拒绝回执的原键、操作人、内容指纹全部吻合时解锁更正。断网、超时、500、冲突或回执不一致均不解锁。已经进入结果未知恢复流程的请求也不能靠随后一次负响应清除。

## 明确未改变的部分

- 旧的**无键集成调用**保持兼容，但不获得跨重试防重保证；不能为旧调用补造可证明的请求身份。外部集成应主动迁移到稳定键。
- v1 只确认实际保存的创建字段。旧入口忽略的备注、温控等额外字段，在带键创建时拒绝，不返回假保存回执。
- 创建回执本身不实现实物预留，也不将草稿当出库；后续的实物预留与资料后补遵循 [跨国发货边界](shipment-late-information-v1.md)，不重写 v1 回执。
- 不据此提升原 37 项验收计数：原销售预留链、20 人跨角色链及真实数据库重启恢复仍须各自完成。

## 可执行证据

- 后端服务与 SQLite 迁移测试覆盖同键重放、异人/改内容、损坏证据、旧单 NULL 兼容及审计失败。
- 前端单元测试覆盖存储可靠性、操作人/入口隔离、回执变异及清理边界，已接入原前端测试命令。
- 隔离原生诊断（PowerShell）：`$env:ROUND2_BROWSER='true'; $env:ROUND2_SHIPMENT_SUBMISSION='true'; node scripts/enterprise-round2-local-v1.cjs --sales-partial`。覆盖丢 ACK 后刷新、最后余量恢复、OCR 恢复、双实例同键并发、提交前失败重试，以及出库后重放原回执；只写新建的 `output/round2/` 沙箱。
- 每包仍重放前序累积链条，不以新增诊断代替原验收。
