## 真实业务与故障步骤

1. 通过既有 API 创建 1,000 元销售订单和 300 元待核销回款，不通过数据库写入/修复业务事实。
2. 两个独立财务账号、两个实际应用实例打开回款中心；第一个账号真实点击核销，另一个账号从订单入口重放。
3. 已签名 HTTP 接收器首次返回 503（零入账），第二次 fsync 持久保存相同事件 ID 的一笔效果，但扣住 HTTP 确认。
4. 确认 outbox 正在 sending 且持有未到期租约，实际 SIGKILL 两个测试应用；在它们死亡期间读库确认未写成功回执且租约未变，再重启。
5. 不改数据库时钟/租约，等待原始 30 秒租约自然到期；原 UUID、原 payload 重发并得到 202。接收器去重账本仍只有一笔 300 元效果。
6. 双实例、两入口再重放 8 次；付款、订单金额/状态、历史审计和事件 payload 与崩溃前完全一致。两实例 API 均读回已收 300 / 部分回款 / 一笔回款。
7. 两个财务浏览器刷新、普通点击订单详情；真实可见的 300.00 和“已核销”必须通过可见性与遮挡检查。加载层消失、中文栅格字体有效、零 pageerror，并人工查看截图。
8. PostgreSQL 共享实时总线要求两个独立财务会话各收到一次同 UUID；SQLite 的内存总线只断言对应单实例会话，不借此声称分布式通知通过。

这是**应用进程崩溃**与租约恢复，`databaseRestarted=false`。数据库服务器重启/未知提交结果、回款登记持久请求键、冲销浏览器和全 20 岗位权限仍是独立未完成义务。HTTP 至少一次投递不是网络 exactly-once；下游必须按事件 ID 去重。

- 专项：`node scripts/enterprise-round2-local-v1.cjs --payment-event`。保持 37 项报告；其余 36 项明确 not_run，不冒充累计通过。
- 最终本地：`npm run audit:enterprise:cumulative:local`，强制执行本包与全部前序包，专项筛选不进入累计路径。
