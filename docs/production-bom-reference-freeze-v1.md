# BOM 工单引用冻结 v1

## 真实缺陷与修复边界

在隔离库使用正式 API 复现：创建未绑定原料 ID 的旧 BOM → 物料治理回填 → 建工单并进入生产 → 回滚治理运行。原接口返回 200，清空旧 BOM 明细的 materialId，正在生产的同一工单由“需求 10、缺料 0、可领 10”变成“需求 10、缺料 10、无可领批次”。这是后端引用对象被改写，不是前端缓存。

原始失败保存在 `output/round2/1790497993763-5d199a2b/enterprise-round2-v1.json`；修复后的同路径专项在 `output/round2/1790498321069-16e30026/enterprise-round2-v1.json` 返回 409，工单预览及关联未变。两次均只操作当次新建的隔离数据。

当前普通 BOM API 仅查询与新建，新版是新 BOM ID；工单保留原 bomId。漏洞来自治理回填/回滚可以改写旧版物料身份。本次锁住这两条现有写入口，不扩展成新版配方审批产品。

## 事务规则

1. 创建工单、回填、回滚必须在同一个事务内先锁定相同的 BOM 父记录。
2. 多个父 ID 去重并按升序取锁；使用参数化原值更新获取数据库写锁，不修改版本、配方、时间戳。
3. 治理持锁后检查全部工单引用，不能只检查在制工单。已完成、已取消工单同样保护历史关联；冲突返回 409，并回滚整个混合批次，不产生成功治理运行或成功审计。
4. 未引用 BOM 仍允许回填和回滚。原有幂等读回不写业务数据；真正的瞬时数据库冲突按既有有限次数重试，业务冻结冲突不重试。
5. BOM 耗用量验证拒绝仍保留结构化 issues，但应是 409 而不是 500。第二轮新增真实测试发现了这个错误分类，未把断言放宽为接受 500。

这是**基于不可改写引用的版本绑定**，没有新增工单 JSON 快照，没有给历史工单伪造快照，也不是数据库管理员级的防篡改机制。未来增加任何 BOM 更新入口，必须复用该锁及引用检查，或另行设计不可变版本机制；启动修复/直接 SQL 的完整边界仍需独立审核。

## 固定目录中的新增检查

- `bom-revision-freeze`：v1 需求 10 kg，创建 v2 后新工单需求 20 kg，旧工单仍 10 kg；同一个测量值在 v1 合格、v2 不合格，独立复核放行 v1；以新版 20 kg 完结旧工单返回 409，按旧版 10 kg 完结成功。数据库核对产成品 10 kg、原料余 90 kg、唯一追溯边耗用 10 kg、成本凭证 -100/+100、旧质检限值与旧版定义未变，两个实例回读各自版本。
- 同一 API 检查中还覆盖：在制工单阻止治理回滚、已取消工单历史保护、受保护/未引用混合回填原子拒绝、未引用正向对照，以及首次建工单与回填/回滚共四次同步竞争。谁先取得锁决定合法串行顺序，引用完成后再次改写必须失败。
- `bom-history-browser`：已有仓库角色在真实生产工作台筛选旧/新工单、打开详情、回读绑定 BOM 号和版本，检查可见性、遮挡、中文字体像素、浏览器错误并保存截图。不是浏览器编制配方，也不等于完整 20 岗位权限矩阵。

首次完整探针 `1790525475008-7ccca2d0` 保留 500 分类失败。随后 `1790525610425-21e9a075` API 通过，但浏览器字体辅助函数收到 Locator 而不是 selector，脚本失败；已纠正参数，不算成产品已通过或跳过该检查。

## 累计验收与非目标

新通过 ID 只有在实际证据复核后才追加到累计基线。每包在最终源码上重放前序全部关键用例，再推送同一版本进行 PostgreSQL 企业云复测。不能用新的通过数量抵消旧用例失败，也不能用 SQLite 结果代替云端锁竞争证据。

企业云 PR 路径过滤同步覆盖本次写入口、冻结服务、浏览器详情和探针；增加源码契约防止未来只修改这些文件时漏触发累计回归。首次累计 `output/round2/1790526132248-158e5f7c/cumulative-regression.json` 为 20/20 通过，但补齐这些 CI 触发路径后仍须重跑最终源码。

本包不改配方审批/生效期规则、不开放角色权限、不做历史工单修复，不把草稿引用解释为已审批；没有完成双工单同批次领料、原料 QC 隔离、密度/包装单位换算、损耗返工或数据库重启不确定提交。完整第二轮仍按原 20 岗位 / 12 链 / 37 ID 判定。下一工作包顺序仍是双工单同批次领料，再是 QC 隔离。
