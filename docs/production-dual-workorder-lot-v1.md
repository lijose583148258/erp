# 同批次双工单完工耗料与直接追溯 v1

## 范围与已确认问题

使用独立测试库、两个应用实例和两个不同仓库账号，从正式 API 新建物料、库存、BOM、工单、检验和独立放行，随后同步发起两个完工请求。此系统当前在完工时确认耗料；本包不是独立的生产前领料单、预占或 WIP 记账模块，也不是完整 20 岗位验收。

`output/round2/1790557258820-cf0d24ee/enterprise-round2-v1.json` 保留修复前失败：

- 原料 100 kg，两单各用 60 kg，只有一张完工、原料余 40 kg，数量保护成立，但另一请求及随后重试误返回 **500** 而非业务冲突。
- 对已完工工单再次提交没有重复扣料，却每次追加一笔“状态变更成功”审计。两个工单完结后的状态审计由 4 条变 6 条，违背真实状态变更与审计一致。
- 同一批次分布两个库位时，原料批次扣减前的读数可能先于另一事务；库存余额与最终成本总和正确，也不能保证每行 quantityBefore/After 连续。旧边界被确定性的服务单测与台账反例覆盖；本地 SQLite 不替代 PostgreSQL 并发验证。

更早 `1790557200296-34524c26` 的失败只是新测试夹具漏填 sampleNo，未进入业务竞争，不作为产品缺陷证据。

## 修复

1. 库存冲突使用类型化异常，控制器按类型返回 409，不依赖中英错误文字匹配；未知失败仍 500。
2. 状态变更成功审计移入同一数据库事务，只有成功的状态条件更新者写入。已完成回读与竞争中落败的同状态回读不新增成功事件；审计失败不再吞掉，事务失败。保留旧审计，不清洗或删除历史重复记录。
3. 库存凭证、成本及状态审计记录当前操作者，不再把工单创建者当成实际完工操作者。权限矩阵不变。
4. 原料 ProductBatch 条件扣减后持锁回读，反推真实数量边界，并校验成本台账累计数量吻合；不同库位共享批次时不能用过期读数写成本凭证。瞬时数据库冲突有限重试，业务冲突不重试。历史数量/成本有差异时拒绝继续，不自动改账。
5. 批次详情新增只读“物料批次关联”，读取已有 `/production/batches/:id/trace`：直接上游原料、下游产出、工单和实际耗用数量/单位。请求取消、批次身份校验、加载/失败/空关联状态明确；失败不展示旧关联。没有把直接关联冒充完整多级召回。
6. 没有关联工单的原料批次日期不再被页面推断成“生产完成”，显示“批次日期（非工单完工凭证）”。沿用原有组件样式，不重设计整页；既有窄列竖排问题不计为已修复。

## 固定检查目录

- `dual-workorder-same-lot`：100 kg 两单各 60 kg 时恰一成一冲突；拒绝后的工单、库存、成本和追溯无副作用；20 kg 带来源凭证补入后另一工单完成，最终原料 0、产出 120 kg、原料成本转产出 1200。另测同库位两单各 40 kg 均成功，以及同批次两个库位各 50 kg 同时耗尽。重复完工保持全状态/凭证/审计不变。
- 对三种场景逐行检查库存凭证与成本凭证连续性、无负数、原料批次/库位/成本余额一致、每个成功工单恰一进一出和一条追溯边；未完成工单不能残留产成品、凭证或谱系。两实例都回读。
- `genealogy-readback`：3 种场景、每种原料加两张产出批次、两个实例，共 18 次 API 回读，对照数据库关联 ID、物料、数量、单位、工单；真实仓库浏览器查看短缺补料场景的三张批次。故障注入一次追溯 GET 503，必须显示错误、清除旧关联，手动刷新恢复。
- 本包补入库存使用隔离夹具的带来源入库凭证，**不是预售补单责任人/交期/采购生产计划闭环**。未验证的新模块不能借这个补料步骤算通过。
