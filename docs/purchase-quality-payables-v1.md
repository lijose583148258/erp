# 采购、来料检验与供应商应付 v1

## 范围与业务口径

实收即登记应付；QA 独立放行前冻结付款，不抹除债务。采购员确认并冻结供应商报价和检验标准，独立审批后才允许实收。每张实收凭证形成独立内部批次，同一供应商批号不得合并检验状态。

- QC 记录实际测量、仪器和样品；服务端依冻结标准判定，QA 不得审核自己的检验。
- 重检立即重新隔离；旧 QA 或旧付款的幂等回执可以读取，但不能解除新的隔离。
- 外部付款登记只是待核实提案，不能显示为已付；独立财务核实后，按累计已付分摊原币与人民币分值。
- 相同提交身份只能产生一次效果；同一银行外部流水不得重复核销。未知回执须先查询原提交，不得换键重记。
- 未核实提案可由原登记人取消并留痕；已核实历史不可删除。供应商退款、余额结转和真实银行执行不在本包范围。

## 兼容与耦合边界

仅新增 `IncomingQualityCheck` 和 `SupplierPayment` 两个必要业务实体，无新增依赖、通用工作流或并行总账。复用收货、库存、成本和审计事务。旧 V1 收货回执保持可重放；历史缺失的应付依据按未知处理，不按零处理、不补造检验记录。

QC 页面没有采购价格或财务请求；应付查询同时要求财务和采购数据域。登记与核实权限分开，不为修复页面报错扩大角色权限。

## 验收与有限收口

原始 37 项中的 `purchase-partial-receipt-qc-payables` 执行真实双节点 API、原始数据库核对，以及 QC、QA、付款登记、付款核实四个独立最小权限浏览器。检验失败/复检、付款冻结、原币/本币尾差、重复与丢失回执、取消留痕、审计故障回滚均须有原始证据；契约测试的合成数据不算业务通过。

基线只能追加本项，保留全部前序义务。累计裁决必须重新核验 API 和浏览器原始事实，不相信 `passed` 或 `requirements: true`。**每完成一个新包，重放前序所有包的关键用例，确认无回归。**

交付顺序：廉价静态/单元门禁 → 最终源码冻结 → 完整本地累计回归 → 提交同源源码 → 已授权仓库推送 → PostgreSQL 企业云累计回归 → 下载原始产物并复核。任一步失败保留原证据，不改时间戳或把未发布临时报告改成通过。

当前登记是候选，不代表云端由 31/37 晋升为 32/37。所有正式数字以同一提交的云端原始证据为准；完整 20 人及数据库重启等剩余义务不被本包替代。

## 测试调度修复

整轮顺序执行增长后不再受旧 420 秒总截断：保持原有单项期限（最长已有 240 秒），外部监护只认可真实用例进展，停滞和总时长仍有上限。Windows 通过 IPC 观察进度，避免监护读取报告时争用原子替换；落盘只做有限重试，不重试业务操作。外层终止复用已拥有 PID 的进程树清理，不影响其它运行。
