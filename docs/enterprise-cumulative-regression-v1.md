## 目的与裁决边界

每个新工作包必须在最终源码上重放此前所有已完成包的关键用例。不比较总通过数，而是逐 ID 验证；新通过项不能抵消旧失败，也不能通过删项、跳过或复用旧报告得到绿色。

- **累计回归 passed**：证明已登记关键用例在本次环境没有退化。
- **第二轮完整验收 passed**：仍须固定 20 岗位、12 条业务链、37 项检查全部满足。累计绿色不能取代它。
- 初始本地 18 个门禁断言与云端 40 个断言不是 18/40 条新业务链；其中包含证据完整性检查。BOM 引用冻结包追加 2 个 ID 后为本地 20 / 云端 42 个断言。未完成的 QC、预售计划等不能算进已通过基线。

自动旧库夹具是完整当前表结构去除新现金责任空表后重建的**上一版边界样例**，不是来自真实客户的历史库。它不替代任意更早版本/真实历史数据的迁移演练。脚本仍支持传入已有旧库路径，源库只读、仅副本执行升级。数据库重启、生产并发等未完成用例保持未执行。

## 执行

从仓库根目录运行：

```sh
npm run test:contract:enterprise-round2
npm run audit:enterprise:cumulative:local
```

本地入口创建唯一隔离目录，重新构建后端和真实前端，启动两个服务，共用本次测试库；依次重放第二轮、销售续发、完整旧库升级。某个探针失败不截断其余独立探针，最终统一判定。报告位于 `output/round2/<run>/cumulative-regression.json`，原始报告、截图和日志同目录保留。

原生脚本退出码：1 为回归失败；2 为累计回归通过但第二轮不完整；0 才是完整通过。某些 npm/PowerShell 启动层会归一化非零退出码，应读原始报告，不将“命令结束”理解为成功。

云工作流不再用 `round2=false` 跳过已完成的第二轮检查。该输入仅决定是否要求 37 项全部通过：累计回归始终执行。基线模式汇总 23 项审计；启用完整第二轮模式汇总 24 项，缺失项仍使最终完整门禁失败。

## 防止旧证据和缩减基线

- 每次运行在构建前登记随机运行键、Git SHA、源码内容指纹、时间窗、数据库环境和云 run/attempt。各探针复制该标识，最终重新核对源码指纹。
- 不覆盖已存在的运行上下文；失败报告保留，不重贴新时间戳将旧证据冒充新执行。
- 重新计算 37 项结果，拒绝缺失/重复/未知 ID、伪造汇总、空证据、缺失时间戳、错误数据库、超时残留报告、旧通过项跳过以及源码中途变更。
- 初始基线有固定指纹。后续修改只能**追加**修订，新修订必须包含前序全部义务；实现了新检查但没有登记为后续必跑项，同样拒绝验收。
- 这些检查防止意外假绿，不构成对恶意修改整套测试代码的密码学证明。代码评审与原始业务断言仍必要。

## 新工作包验收步骤

1. 新增/修复业务断言，先跑针对性用例定位问题，不降低前序断言。
2. 审查新增通过项的 API、数据库、浏览器、角色证据；在基线中追加修订，不能改写初始修订。
3. 在合并后的最终源码上跑累计本地回归；任何源码修改使旧指纹失效，需要重跑。
4. 推送同一版本后跑企业云，下载原始报告核对 SHA、步骤 outcome、原始业务结果与截图。
5. 分别记录新增结果、前序重放、退化、未执行项。未验证完不能宣称本包交付，更不能称系统完美通过。

本包只增加验收自动化，不修改 BOM、库存、财务生产业务逻辑，也不增加部分退款、余额结转或历史核对界面。下一包按 BOM 冻结、同批次双工单、QC 隔离顺序推进，并按上述规则追加基线。
