# 后端功能成熟度与可发布细节审计

日期：2026-06-16

## 1. 本轮结论

本轮纠偏的核心结论是：不能再简单说“审批、通知、风控、批次、货物兑换、BI 都没有完成”。

当前后端已经存在大量生产级能力，尤其是：

- 商业平台工作流：定义、实例、任务、动作、通知已具备 API 闭环。
- 商业平台通知与预警：通知列表、已读、预警运行、BI summary、readiness 已具备 API。
- 客户授信与发货拦截：`CreditEngine` 已接入销售下单和发货状态变更。
- 回款与催收：逾期同步、承诺付款、争议、客户冻结、发货冻结已具备独立模块。
- 批次与库存追溯：采购入库、生产完工、仓储调拨、发货扣库、库存流水已有多条审计链路。
- 货物兑换：协议、结算、审批、过账、反冲、库存联动已有后端闭环。
- 可观测性：`/health`、`/metrics` 和基础请求指标已存在。

真正的差距不是“有没有代码”，而是“是否所有核心业务单据都统一接入这些能力，并达到可发布冻结标准”。

## 5. 后续按“可发布细节治理”的顺序

### P0：冻结前必须先治理

1. 继续收敛工作树，把本轮治理改动分组确认，避免 80+ 项混在一起。
2. 修复仍在报告或脚本中出现的真实 mojibake；只修文件真实内容，不修 PowerShell 显示层。
3. 重新打包，确保 `SOURCE_MANIFEST.json` 的 `sourceDirtyCount` 为 0。
4. 再跑 `audit:release:freeze`，目标是只在真正可冻结时变成 `frozen`。

### P1：能力闭环治理

1. 不重写现有审批引擎，只做接入策略表：哪些单据必须走通用工作流，哪些保留模块内状态机。
2. 为授信超限、额度调整、价格低毛利、库存异常补“进入审批/预警”的桥接点。
3. 建立统一附件关联规则，先不做复杂文件中心。

### P2：可用性细节治理

1. 继续补销售订单、CRM、仓储、发货、回款等高频输入的长度限制和溢出显示。
2. 对触屏场景强制显示表格操作按钮，避免 hover 依赖。
3. 增加紧凑模式下的表格密度回归审计。

### P3：发布级稳定性

1. 执行 release core。
2. 执行 Phase 3 package audit。
3. 执行浏览器核心路径。
4. 只有包、运行时、源码 manifest、核心审计全部对齐时，才允许标记为可发布冻结。

## 6. 反幻觉判定

- 不能用“代码里有表/字段”证明功能完成。
- 不能用“API 200”证明业务闭环完成。
- 不能用“构建通过”证明可以发布。
- 本轮商业平台能力已经通过后端链路审计，不能再误判为“没有”。
- 当前发布冻结仍被有效阻断，不能宣称最终可发布。

## 7. 联网反幻觉复核

本轮复核了成熟发布管理与 artifact 管理资料，结论与当前治理方向一致：

- 发布管理应覆盖计划、构建、测试、部署与发布后监控，不只是打出一个 zip。
- artifact 管理强调二进制、配置和构建产物必须可追溯、可复现，并作为单一可信来源治理。
- 发布 checklist 的核心是降低停机和回滚风险，因此冻结闸门必须保留“源码状态、构建来源、运行时 manifest、包指纹”的一致性检查。

参考方向：

- JFrog Artifact Management：artifact 需要可追溯、可验证、可复现。
- JFrog Release Management：发布管理是规划、协调、监督部署的结构化过程。
- LaunchDarkly Release Management Checklist：发布清单应服务于降低发布中断风险。

对应到本系统：`audit:release:freeze` 当前继续阻断脏工作树和脏包来源是正确的；本轮只修正“选错旧 zip”的假阻断，不降低冻结门槛。
