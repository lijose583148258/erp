# 全局分模块打磨方案
**保持整体联动一致性 · 2026-06-11**

> 本方案的核心原则：**任何模块的修改不能破坏跨模块数据流**。  
> 系统共享的"通用层"（产品主数据、货币格式、状态枚举、组件库、i18n）必须**先行统一**，  
> 否则各模块各自打磨会产生新的不一致。

---

## 0. 通用层（所有模块共享，优先级最高）

这一层不属于任何单一模块，但**所有模块都依赖它**。如果通用层不先统一，后续每个模块打磨都是在加深裂痕。

### 0.1 产品主数据（Product Master）— 影响 7 个模块

```
影响范围：销售订单、采购、仓库、生产、物流、RMA、调整中心
```

当前 `productName` 自由文本散布在 7 张表，统一为 `Product` 表后，所有模块的产品选择器组件统一为同一个 `<ProductPicker>`：

```typescript
// 所有模块共用同一个组件
<ProductPicker 
  value={item.productId} 
  onChange={(product) => updateItem({ 
    productId: product.id, 
    productName: product.nameZh,  // 快照，用于历史显示
    unit: product.unit,
    casNo: product.casNo 
  })}
/>
```

**联动效果**：销售订单选择"乳化剂A级"后，生产模块的 BOM 用料、仓库的库存查询、采购的补货建议都引用同一个 `productId`，不再有拼写不一致问题。

---

### 0.2 货币格式化统一 — 影响 SalesOrders、Procurement、Contracts、BarterWorkspace、FinanceAnalytics

当前 `formatPrice(amount)` 在不同模块调用方式不一致（合同模块已正确传 `currency` 参数，销售订单"净额"列未传）。

**统一签名**：
```typescript
formatPrice(amount: number, currency: 'CNY' | 'VND' | 'USD'): string
// CNY → ¥12,800.00
// VND → ₫45.000.000  (vi-VN，无小数)
// USD → $1,280.00
```

**强制规则**：任何展示金额的地方，`currency` 参数必须来自该记录自身的 `order.currency` / `contract.currency`，禁止省略走默认值。建立 ESLint 自定义规则检测 `formatPrice(` 调用是否传了第二个参数。

---

### 0.3 状态枚举统一 — 影响所有带 status 字段的模块

当前各模块各自维护状态字符串（如 RMA 的 `x.PENDING` 在 `types-Cf11yT98.js` 中定义，调整中心的 `pending/posted/reversed/rejected` 在 `AdjustmentCenterView` 内联定义）。

**统一到一个共享枚举文件** `shared/enums.ts`：
```typescript
export const OrderStatus = {
  PENDING: 'pending', CONFIRMED: 'confirmed', PROCESSING: 'processing',
  SHIPPED: 'shipped', COMPLETED: 'completed', CANCELLED: 'cancelled',
} as const;

export const AdjustmentStatus = {
  PENDING: 'pending', POSTED: 'posted', REVERSED: 'reversed', REJECTED: 'rejected',
} as const;

export const RmaStatus = {
  PENDING: 'pending', IN_REVIEW: 'in_review', 
  RESOLVED: 'resolved', REJECTED: 'rejected',
} as const;
// ... 其余模块同理
```

**联动效果**：`<StatusBadge>` 组件（目前已被 7+ 模块共用）根据枚举值自动选择颜色和文案，新增状态值时只需改一处。

---

### 0.4 分页组件统一 — 影响 RMA、Contracts、AuditLogs 等硬编码 pageSize=100 的模块

当前 RMA 调用 `/rma?pageSize=100`，固定写死。统一为共享 Hook：

```typescript
// shared/hooks/usePaginatedList.ts
function usePaginatedList<T>(fetcher, options = { pageSize: 50 }) {
  // 统一分页状态管理、loading、error、刷新逻辑
  return { data, meta, page, setPage, refresh, loading };
}
```

所有列表模块改用该 Hook 后，分页 UI（页码、每页数量选择器）可以做成共享组件 `<PaginationBar>`，一次实现全局生效。

### 0.5 表单脏检查全覆盖 — 影响 10 个未接入 useUnsavedForm 的模块

已确认接入：SalesOrders、Procurement、WarehouseWorkspace（部分）。

**未接入清单**（按优先级排序）：
1. ProductionWorkspace（BOM 编辑器、工单创建）— 表单最长，丢失代价最大
2. CollectionActionModal — 催收记录填写中途关闭
3. BarterWorkspaceView — 协议/结算表单
4. Contracts — 合同新建/OCR识别后的编辑
5. Assets — 批次新建/调整
6. RMA — 退货申请表单
7. Samples — 样品记录
8. TeamManagement — 用户/角色编辑
9. AdjustmentCenterView — 调整记录（已部分使用 useUnsavedForm，需确认覆盖率）
10. ReceiptDiscrepancyWorkbench — 差异处理表单

**统一接入模式**（每个模块只需 3 行）：
```typescript
const { dirty, requestClose } = useUnsavedForm({

// 关闭按钮: onClick={() => requestClose(() => setIsOpen(false))}
// Escape键: 在根容器加 onKeyDown 检测
```

## 1. 销售订单模块（SalesOrders）— 102KB，系统核心枢纽

### 定位
所有下游模块（物流、RMA、催收、财务分析）的数据起点。打磨优先级最高，但**改动必须保证向下游输出的数据结构不变**（`orderId`、`status`、`currency` 等字段名和取值范围不能动，否则物流/催收模块联动失效）。

### 1.1 布局重构（核心问题，影响联动）

当前编辑器 `max-w-[96vw]` + 左侧固定 360px + 表格 `min-w-[1080px]`，必然横向滚动。

**重构方案**：改为「订单头 + 订单行」两段式布局，编辑器改为 `100vw` 全屏：

```
┌──────────────────────────────────────────────────────────────────┐
│  新建销售订单                                          [×]         │
├──────────────────────────────────────────────────────────────────┤
│  Step 1: 订单信息                          Step 2: 订单明细 (●)    │
├──────────────────────────────────────────────────────────────────┤
│  客户: [Combobox搜索▾]   日期: [今天]   货币: [CNY▾]               │
│  付款条款: [现款][30][60][90][自定义]    佣金: [3%____]            │
├──────────────────────────────────────────────────────────────────┤
│  [+ 添加产品]                                    共 8 行  [粘贴Excel]│
│  ┌──────────────────────────────────────────────────────────┐    │
│  │ 产品(ProductPicker) │ 规格 │ 数量 │ 单位 │ 单价 │ 小计 │ 操作│    │
│  └──────────────────────────────────────────────────────────┘    │
│                          合计: ¥xxx  折扣: [▾] 最终: ¥xxx          │
├──────────────────────────────────────────────────────────────────┤
│                                            [取消]  [上一步]  [创建] │
└──────────────────────────────────────────────────────────────────┘
```

**联动验证点**：创建成功后跳转到订单详情页时，传给路由的 `orderId` 格式不变（仍是数字），物流模块的"快速发货"按钮读取的 `order.status` 字段值仍是统一枚举中的值，不受布局重构影响。

### 1.2 客户选择器 → Combobox（联动到 CRM）

替换原生 `<select>` 为可搜索 Combobox，数据源直接复用 0.1 节统一后的 `customer.service`，搜索逻辑与 CRM 模块的全局搜索共用同一套（同时匹配主名称、别名表、编码）。

**联动效果**：在 CRM 客户详情页点击"新建订单"时，自动带入 `customerId`，Combobox 直接显示已选中状态，不需要用户重新搜索。

### 1.3 其余细节修复

- 去除结案按钮 `animate-pulse`，改为 `hover:ring-2`
- 付款方式 value 改枚举码（`bank_transfer`），**联动**：催收模块的回款记录展示需要同步更新映射表
- `paymentTermsDays` 加 `max={365}`
- 空状态英文文案改 i18n（"No payments recorded." → `t.noPayments`）
- `handleQuickShip` 改用 `useNavigate`，**联动**：跳转参数 `orderId` 传递方式不变，物流模块入口逻辑无需改动
- 订单行超过 50 行分页展示

## 2. 物流发货模块（Shipping）— 62KB

### 定位
消费销售订单数据，同时为资产容器（冷链批次）提供来源数据。

### 2.1 当前已发现的良好设计（保留）

代码中 `searchText` 函数已经正确聚合了多语言客户名称（`customerNameZh/En/Vi`）和产品 CAS 号，搜索体验本身设计是对的——**这部分不要动**，但要把这个搜索模式作为标准，推广到 RMA、采购等模块（目前 RMA 的搜索字段较少）。

### 2.2 MSDS（安全数据表）状态展示打磨

当前 `valid/expired/missing` 三态用小圆点+文字展示，问题是**没有点击行为**——MSDS 缺失或过期时，用户除了看到红点不知道下一步该做什么。

**打磨方案**：
```
MSDS状态: 🔴 已过期        ← 点击展开
  ┌─────────────────────────────────┐
  │ 该产品MSDS已于2026-03-15过期      │
  │ [上传新版MSDS]  [标记为豁免]      │
  └─────────────────────────────────┘
```

**联动**：上传后的 MSDS URL 写入 `Product.msdsUrl`（0.1节统一的产品主数据表），所有模块（采购、生产、物流）共享同一份 MSDS 状态，不需要每个模块各自维护。

### 2.3 B2B 标识可视化增强

代码中 `s.id.includes("B2B")` 已经有背靠背订单标识，但只是一个小图标+文字。

**打磨方案**：B2B 订单行增加可展开的关联链：
```
#SHP-2026-0418  [⇄ B2B]
  └─ 来源采购单 #PO-2026-0203（点击跳转）
  └─ 对应销售单 #ORD-2026-0501（点击跳转）
```

**联动**：跳转到采购/销售模块时使用 `useNavigate` 并传递 `highlightId` 参数，目标模块打开后自动定位高亮该记录。这要求采购模块和销售订单模块都支持 `?highlight=PO-2026-0203` 这样的 URL 参数高亮定位——这是一个**需要统一实现的跨模块特性**。

## 3. 客户关系管理（CRM）— 90KB

已在前一份方案中详细设计（工作台、详情页360视图、联系人重构、风险状态条等）。这里补充**与其他模块的联动点**：

### 3.1 与销售订单的联动

客户详情页右侧"账务快照"中的"本年度成交"、"未收款合计"，数据来源是 SalesOrders 模块的订单表。**联动要求**：CRM 不应该自己重新计算这些汇总，应该调用销售订单模块暴露的统一聚合接口 `GET /orders/customer-summary/:customerId`，确保两个模块看到的数字永远一致（避免出现"CRM显示未收款8万，订单列表汇总显示7.8万"的不一致）。

### 3.2 与催收模块的联动

CRM 详情页顶部的风险状态条数据（逾期金额、催收级别）应直接读取 `Customer` 表上的 `overdueAmount`、`dunningLevel` 字段——这两个字段由催收模块在后台批量任务中更新。**联动要求**：催收模块更新这两个字段后，需要触发一个轻量事件（WebSocket 或简单的 polling），CRM 页面如果正打开着同一客户详情，能在几秒内看到状态条颜色变化，而不需要手动刷新。

### 3.3 与AI助手的联动

AI助手如果要回答"这个客户最近怎么样"，需要能访问 CRM 的客户时间线数据。**联动要求**：把 0.1-0.4 节统一后的数据结构作为 AI 助手的"系统上下文"传入，AI 回答时引用的客户名称、订单号、金额格式与系统其他地方完全一致（参见第10节AI助手专项）。

## 4. 催收中心（CollectionCenterView）— 62KB

### 4.1 信息架构重组（已在第一轮方案提出，这里给出与其他模块的联动细节）

催收中心拆分为「工作台」「逾期台账」「承诺管理」「争议管理」四个子视图后，**联动关键点**：

**工作台的"今日待跟进"数据**直接来自 CRM 模块统一的 `CollectionFollowUp` 表，催收中心和 CRM 工作台（2节）显示的是**同一份数据的不同视图**——催收中心按"我的待办"聚合，CRM工作台按"客户视角"聚合，但底层查询的是同一张表，避免两处数据来源不一致导致数字不一样。

### 4.2 止货操作的跨模块联动（关键）

止货操作（`creditHold`/`shipmentHold`）会立即影响：
- **销售订单模块**：被止货客户的"创建订单"按钮变为禁用，鼠标悬浮显示"该客户已被止货，需先解除止货"
- **物流模块**：被止货客户已存在的待发货订单，发货按钮变灰，显示"⛔ 客户止货中，需经财务审批后发货"
- **CRM详情页**：风险状态条立即变为深红色"⛔ 止货中"

**实现要求**：止货状态作为 `Customer.creditHold` / `Customer.shipmentHold` 字段，是单一数据源。任何模块判断"是否可以创建订单/发货"时，都从这两个字段读取，不允许任何模块维护自己的"客户黑名单"副本。

### 4.3 催收动作 Modal 拆分

把 CollectionActionModal（10.7KB）的四种动作（记录催收/设承诺/标争议/发提醒）拆分为行内快捷按钮 + 独立的"记录催收详情" Modal。**联动**：发提醒动作触发后，在 CRM 客户详情时间线中插入一条系统事件"已发送催收提醒（短信/邮件）"——这要求 0.4 节统一的时间线事件类型增加 `reminder_sent` 类型。

## 5. 生产工作区（ProductionWorkspace）— 93KB，第二大模块

### 5.1 BOM 与产品主数据联动（最关键）

当前 `ProductionBom` 的物料明细各自填写 `productName` 文本。统一到 0.1 节产品主数据后：

```
BOM编辑器
┌────────────────────────────────────────────────┐
│ 产品: 乳化剂A级 (EMU-A-01)  版本: v2  状态: 生效  │
├────────────────────────────────────────────────┤
│ 物料清单：                                       │
│  [ProductPicker] 苯乙烯单体    | 35%  | kg      │
│  [ProductPicker] 丙烯酸丁酯    | 28%  | kg      │
│  [ProductPicker] 乳化剂助剂A   | 12%  | kg      │
└────────────────────────────────────────────────┘
```

**联动效果**：当采购模块的某个原料产品改名或停用时（在产品主数据表中标记 `isActive=false`），所有引用该产品的 BOM 自动显示警告标记"该原料已停用，请更换替代品"。

### 5.2 BOM 库存可行性检查（联动仓库模块）

创建工单前，调用仓库模块暴露的接口检查每种原料当前库存：

```
创建工单 #WO-2026-0142
┌────────────────────────────────────────────────┐
│ 库存检查结果：                                   │
│  ✅ 苯乙烯单体     需要350kg  现有520kg          │
│  ⚠️ 丙烯酸丁酯     需要280kg  现有210kg  缺70kg  │
│  ✅ 乳化剂助剂A    需要120kg  现有380kg          │
│                                                  │
│  [一键生成采购建议]  → 联动采购模块创建采购草稿  │
└────────────────────────────────────────────────┘
```

**联动实现**：点击"一键生成采购建议"后，调用采购模块的 `POST /procurement/draft-from-shortage` 接口，传入缺口数据，采购模块创建一条 `status='draft'` 的采购单草稿，用户在采购模块里看到这条草稿并补充供应商信息后提交。

### 5.3 生产损耗与库存调整联动

工单完成时记录 `lossQuantity`，**联动要求**：这个损耗数值不应该让生产模块自己直接改库存数字，而应该调用 0.4 节统一的调整中心接口，创建一条 `domain='production', reasonCategory='production_loss'` 的调整记录（代码中调整中心已经预设了这个类型，但生产模块当前可能是直接写库存）。这样所有的库存变动都经过调整中心统一审计，财务模块可以追溯每一笔损耗的来源。

### 5.4 配方模式动态表单

`formulationMode`（按重量/体积/百分比）切换时，物料明细的列标题和单位应该动态变化：

| formulationMode | 列1标题 | 列1单位 | 总和校验 |
|-----------------|--------|--------|---------|
| weight | 用量 | kg | 无强制 |
| percentage | 占比 | % | 必须=100% |
| volume | 用量 | L | 无强制 |

切换模式时弹出确认："切换配方模式将清空已填写的用量数据，是否继续？"（这本身也是 useUnsavedForm 的应用场景）。

## 6. 采购模块（Procurement）— 55KB

### 6.1 供应商信息展示打磨

代码中供应商列已经正确聚合了 `nameZh/nameEn/nameVi/nameAliases`，联系人和地址也有结构化展示——**这部分设计是对标 0.1/0.2 节统一标准的范例**，建议把这套展示模式抽取为共享组件 `<EntityNameDisplay>`，CRM 的客户名称展示、生产模块的供应商展示都复用这一组件，保证多语言名称的展示风格全系统一致。

### 6.2 采购单与生产/库存的双向追溯（联动核心）

当前 `ProductBatch` 没有字段链接回 `PurchaseOrderReceipt`。补充字段后：

```
采购单 #PO-2026-0203 详情
┌────────────────────────────────────────────────┐
│ 状态: 已收货                                     │
│ 收货记录: 2026-06-08  生成批次 #BATCH-20260608-A │
│           （点击跳转仓库模块查看该批次）          │
│                                                  │
│ 该批次后续流向：                                 │
│  → 生产工单 #WO-2026-0142（消耗180kg）           │
│  → 当前库存余量: 30kg                            │
└────────────────────────────────────────────────┘
```

**联动实现**：这要求 5.3 节的"原料消耗"在 `ProductionBomItem` 执行记录中写入 `sourceBatchId`，采购模块查询时通过 `批次 → 消耗记录` 反向 join 即可展示完整链路。这是三个模块（采购、仓库、生产）共享同一个批次概念的体现。

### 6.3 B2B 背靠背订单标识统一

采购模块的 `isB2B` 标识和销售订单模块对应的标识、物流模块（2.3节）的标识，使用同一套视觉规范（同色徽章+图标），并且三处都支持点击跳转到关联订单——这是 2.3 节提到的"跨模块高亮跳转"特性在采购模块的应用。

## 7. 仓库工作区（WarehouseWorkspace）— 61KB

### 7.1 仓库→库位创建弹窗已接入 useUnsavedForm（良好范例）

代码显示 `createWarehouse` 和 `createLocation` 两个弹窗都已经用了 `useUnsavedForm`——这是目前覆盖率最好的模块之一，**应作为其他模块接入该 Hook 时的参考实现**。

### 7.2 库存余额视图与产品主数据联动

库存余额（`StockBalance`）当前按 `productName` 文本分组，统一到 `productId` 后：

```
库存总览
┌────────────────────────────────────────────────┐
```

## 8. 调整中心（AdjustmentCenterView）— 30KB

### 8.1 当前设计已经是"枢纽"角色（良好基础）

代码显示调整中心已经预设了三种 `domain`（finance/production/inventory）和对应的快捷模板（`ge` 数组），状态机（pending/posted/reversed/rejected）也已经用共享的 `StatusBadge` 组件。这个模块的架构设计本身是对的，**问题是入口分散**——目前各模块的损耗/盘点/收款更正可能各自有入口，没有统一引导到这里。

### 8.2 各模块"创建调整"入口统一

```
生产模块工单完成页：[记录损耗] → 跳转到调整中心，预填 domain=production

催收模块回款页：    [收款更正] → 跳转到调整中心，预填 domain=finance
```

**联动实现**：调整中心暴露一个"快速创建"路由 `/adjustments/new?domain=production&targetType=productBatch&targetId=123`，各模块的"记录XX"按钮直接跳转到这个带参数的 URL，调整中心打开时自动应用 `ge` 数组中对应的模板（代码中已有 `patch` 字段定义默认值）。

### 8.3 审批流挂接点（为后端审批流功能预留前端入口）

调整记录的 `status` 从 `pending` 变为 `posted` 应该需要审批（金额超过阈值时）。当前前端可能是直接切换状态，打磨方案：

```
调整记录详情

│ #ADJ-2026-0089  生产损耗  -50kg  ¥-2,400         │
│ 状态: 待审批  (金额超过¥1,000，需主管审批)        │
│                                                  │
│ [申请审批]  → 通知主管角色用户                   │
└────────────────────────────────────────────────┘
```

这是为后端"审批流引擎"（在之前的痛点分析中提到）预留的前端挂接点，即使后端审批逻辑尚未实现，前端先把"待审批"状态和按钮做出来，后端实现后无需改前端。

## 10. AI助手（AIAssistant）— 16.5KB

### 10.1 系统上下文注入（核心联动）

AI助手要能回答"客户XX最近怎么样"，需要访问 0.1-0.4 节统一后的数据结构。**实现方案**：

```typescript
// AI助手调用前，注入精简的系统上下文
const systemContext = {
  customer: await CRM.getCustomerSummary(customerId), // 0.1节统一的聚合接口
```

AI 回答中引用的金额格式必须经过 0.2 节的 `formatPrice`，状态文案必须经过 0.3 节的枚举映射——确保 AI 说"该客户当前逾期 ₫45,000,000，催收等级L2"而不是用训练数据里的格式说"overdue $45000, level 2"。

### 10.2 能力边界卡片（第一轮方案已提出，这里补充联动）

AI助手入口的能力卡片中的示例问题应该是**真实可执行**的——"查询客户XX的未收款记录"点击后应该直接触发 CRM 模块的查询并把结果作为对话的一部分展示，而不是纯文本提示用户自己去问。这要求 AI助手和 CRM、订单、催收模块之间有标准化的"工具调用"接口（类似 function calling），这是后续迭代的方向。

## 15. 联动一致性验收清单

每完成一个模块的打磨，用以下清单验证不破坏整体联动：

- [ ] 该模块所有产品引用是否走 `productId`（0.1节）
- [ ] 该模块所有金额展示是否传 `currency` 给 `formatPrice`（0.2节）
- [ ] 该模块所有状态值是否使用共享枚举（0.3节）
- [ ] 该模块所有列表是否使用 `usePaginatedList`（0.4节）
- [ ] 该模块所有弹窗/表单是否接入 `useUnsavedForm`（0.5节）
- [ ] 该模块向其他模块暴露的字段名/取值范围是否保持不变
- [ ] 该模块消费其他模块数据时是否调用统一聚合接口而非自行计算
- [ ] 跳转到该模块的 URL 参数筛选是否生效（9.2节规范）

---

*本方案以"通用层先行"为核心原则，确保各模块独立打磨的同时，整个系统的数据一致性和导航联动不被破坏。*
