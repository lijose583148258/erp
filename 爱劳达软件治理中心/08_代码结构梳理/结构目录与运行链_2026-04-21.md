## 1. 当前阶段结论

当前系统已经从“能启动的 ERP+CRM 半成品”进入“阶段 3：本地稳定两个月 + 后续服务器可迁移”的收口阶段。

不能再用“编译通过”代表完成。当前验收必须同时看：

1. 后端链路是否能真实写入、读取、回滚或对账。
2. 前端页面是否能真实点击、输入、刷新回读。
3. 数据库是否没有 schema 漂移、字段缺失和静默丢失。
4. 乱码是否按“三步法”先翻译、再判断、再修复。
5. 运行是否遵守 5 分钟上限，超过必须判定卡住而不是继续等。

## 2. 根目录分层

当前根目录不是单一源码目录，而是混合了源码、运行产物、治理资料和历史包。后续维护必须按层识别，避免把历史文件当当前入口。

| 层级 | 目录/文件 | 用途 | 当前处理原则 |
| --- | --- | --- | --- |
| 前端源码 | `app/`, `components/`, `pages/`, `services/`, `utils/`, `translations/`, `types.ts`, `constants.ts` | 当前 Vite/React 前端源码 | 只改当前有效源码；旧备份不参与编译 |
| 后端源码 | `backend/src/`, `backend/prisma/`, `backend/package.json` | Express + Prisma + SQLite 后端 | 控制器继续瘦身，事务服务继续下沉 |
| 构建产物 | `dist/`, `backend/dist/` | 构建输出 | 可重新生成，不作为源码事实 |
| 运行数据 | `D:\AilaoDaRuntime\stable.db`, `uploads/`, `logs/`, `output/` | 本地运行、上传、验收报告 | 不删除；测试报告需要标明时间和入口 |
| 治理资料 | `爱劳达软件治理中心/` | 架构、任务、审计、验收记录 | 当前推进依据；需要持续更新 |
| 历史归档 | `历史归档/`, `文档归档/`, `AilaoDa_Stable_Package*` | 历史版本和包 | 不参与当前运行；仅用于比对和恢复 |
| 自动化脚本 | `scripts/`, `backend/scripts/` | 审计、修复、验收、打包 | 旧脚本必须标记或隔离，避免误判 |

## 3. 当前运行链

### 3.1 前端链路

```text
浏览器 http://127.0.0.1:5001/
  -> backend/dist/server.js 静态托管 dist/
  -> dist/index.html
  -> Vite bundle
  -> app/App.tsx
  -> Layout / 路由 / 页面模块
  -> services/api.ts
  -> /api/*
```

前端当前风险不是“打不开页面”单点，而是：

1. 历史入口和旧脚本仍可能误把 `3000`、`5173` 或旧页面当验收对象，必须继续以 `http://127.0.0.1:5001/` 为稳定验收入口。
2. 生产、采购、仓储、CRM hook 已完成首轮大文件拆分，前端架构已从“单页堆叠”回到“页面壳 + 业务区块 + 配置/基础组件”的方向。
3. 样式已经开始进入 token/组件治理，但还没有全量迁移完成；剩余风险主要在审计脚本、语言包和 schema 治理。

### 3.2 后端链路

```text
backend/src/server.ts
  -> Express app
  -> routes/*
  -> controllers/*
  -> services/*
  -> Prisma Client
  -> SQLite stable.db
```

后端当前风险：

1. 大控制器还没有全部拆完。
2. `runtime-schema-repair.ts` 仍然偏大，但已开始拆分职责：schema 修复只负责表、字段、索引；数据清污进入 `runtime-data-repair.ts`。
3. 订单、回款、发货、仓储、生产、货抵等模块已经有闭环，但还需要继续做并发、撤销、部分履约、差异对账。

### 3.3 启动修复链分层

```text
scripts/start-stable-v2.ps1
  -> backend/dist/database/manage-db.cli.js repair
  -> repairRuntimeSchema()
     -> 只处理表、字段、索引、schema 级幂等补齐
     -> runtime-schema-repair-utils.ts 提供建表/加字段/建索引/白名单列检查
     -> runtime-schema-core-repair.ts 处理订单/客户/回款/供应商/物流/采购订单基础扩容字段
     -> runtime-schema-stock-repair.ts 处理 warehouses / locations / stock_* 三表
     -> runtime-schema-auth-repair.ts 处理 auth_roles / auth_permissions / auth_role_permissions
     -> runtime-schema-barter-repair.ts 处理 barter_* 货抵支付/换货贸易 schema
     -> runtime-schema-production-repair.ts 处理 production_bom* / inventory_cost_ledgers schema
     -> runtime-schema-receipt-repair.ts 处理 purchase_receipts / shipment_receipts / receipt_discrepancy_* / receipt_tolerance_rules schema 与默认规则 seed
  -> repairRuntimeData()
     -> 只处理白名单数据修复、默认仓库/库位、历史坏名清污
  -> backend/dist/server.js
```

当前规则：

1. `runtime-schema-repair.ts` 只做 schema repair 调度，不再新增具体表结构和业务数据清污逻辑。
2. `runtime-schema-repair-utils.ts` 承接通用 schema helper，不写业务表顺序。
3. `runtime-schema-core-repair.ts` 承接订单/客户/回款/供应商/物流/采购订单基础字段扩容，不写业务闭环。
4. `runtime-schema-stock-repair.ts` 承接仓储/库存 schema，不写库存业务扣减逻辑。
5. `runtime-schema-auth-repair.ts` 承接角色/权限表结构，不写权限定义 seed 和动态授权业务规则。
6. `runtime-schema-barter-repair.ts` 承接货抵支付/换货贸易表结构，不写货值抵扣、审批、过账业务规则。
7. `runtime-schema-production-repair.ts` 承接化工 BOM 扩容和成本台账表结构，不写工单完工、库存扣减、成本核算业务规则。
8. `runtime-schema-receipt-repair.ts` 承接收货/签收/差异/容差规则表结构和默认规则 seed，不写采购入库、发货签收、差异处理业务闭环。
9. `runtime-data-repair.ts` 承接已确认、可白名单化的数据修复。
10. 新增数据清污必须写明坏值、正确值、目标表字段，并通过乱码三步法确认层级。
11. 运行时修复链每次改动后必须执行 `npm run start:stable` 和 `scripts/check-runtime.ps1`。

## 8. 后续推进原则

1. 先补小闭环，再连大闭环。
2. 先拆最影响维护的大文件，再做漂亮重构。
3. 先证明真实读写，再宣布功能完成。
4. 先把入口、端口、数据库固定，再做浏览器人工点测。
5. 所有超过 5 分钟的命令必须停止等待并判定卡住。
6. 乱码必须三步法，不能直接重写文件。
7. 旧接口不能接就断开并标记，不让它继续干扰当前版本。
