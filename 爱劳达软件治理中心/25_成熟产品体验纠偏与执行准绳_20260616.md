# 成熟产品体验纠偏与执行准绳

日期：2026-06-16

## 1. 本轮纠偏结论

上一轮围绕登录、员工账号、角色授权做 P0 收口是必要的，但不能把它误当成“成熟产品体验”的全部。

结合以下文件重新判断：

- `爱老大全局分模块打磨方案.md`
- `CRM极致细节规范_像素级.md`
- `CRM极致细节规范_第三篇.md`
- `CRM极致细节规范_第五篇.md`
- `CRM极致细节规范_第六篇.md`
- `爱劳达V2精准审计报告.md`

成熟产品体验的主线应从“账号能登录、权限能保存”纠偏为：

1. 高频业务能少滚动、少误填、少等待。
2. 每个关键操作有清楚的前置条件、风险提示、保存反馈和审计证据。
3. CRM、销售订单、催收、发货、库存、财务看到的是同一份客户、订单、状态、金额数据。
4. 账号角色权限服务于业务闭环，而不是独立变成一个复杂权限工程。

## 2. 不能继续跑偏的地方

### 2.1 不把权限系统过早重构成大工程

可以继续做：

- 登录页区分正式员工账号与演示默认账号。
- 员工账号创建后的交付提示。
- 角色授权页的权限摘要、高风险权限提示、授权确认单。
- 角色权限变更审计。

暂不做：

- 多角色模型。
- 多组织授权。
- 字段级权限引擎。
- 子管理员授权范围。

原因：这些是 P2/P3 架构升级，不应在发布冻结前强塞进当前模型。

### 2.2 不用“视觉精致”替代高频效率

规范文件反复指向同一个问题：B 端业务系统最重要的是密度、清晰、稳定、可追溯。

后续 UI 调整必须优先满足：

- 表格行高、列宽、截断、提示稳定。
- 输入框四态清晰：默认、聚焦、错误、禁用。
- 超长内容有截断与完整查看路径。
- 触屏设备不依赖 hover 才显示关键操作。
- 页面顶部固定区不能挤压业务表格高度。

### 2.3 不把单模块修漂亮后破坏跨模块字段

全局方案明确要求：订单、客户、催收、物流、财务之间的字段名和状态枚举不能随意变。

后续任何模块重构必须先确认：

- `customerId`
- `orderId`
- `status`
- `currency`
- `shipmentHold`
- `creditHold`
- 金额格式化入口

是否仍被下游模块按同一口径读取。

## 3. 重新排序后的执行优先级

### P0：发布可信与不可错用

1. 继续保留默认演示账号不能直接进入业务区。
2. 继续保留员工首次登录强制改密。
3. 继续保留权限保存前复核与审计差异。
4. 发布验证必须走受治理入口，不把任意预览端口当成正式通过。
5. 继续使用乱码三步法，只修真实文件层乱码，不修终端显示层。

### P1：高频业务体验

1. 销售订单：客户选择器改为可搜索 Combobox，先不动下游字段。
2. 销售订单：订单头与订单行分区，避免 1440px 以下长期横向滚动。
3. CRM：客户列表、客户详情、跟进记录优先落地像素级规范中的行高、输入四态、字符计数、风险条。
4. 催收中心：止货、承诺、争议动作必须回写 CRM 客户时间线或风险状态。
5. 采购、仓储、发货：长字段、批次号、备注、凭证说明继续补长度限制和溢出查看。

### P2：跨模块一致性

1. 客户汇总指标由统一聚合接口提供，避免 CRM 和订单各算各的。
2. 止货状态以 `Customer.creditHold` / `Customer.shipmentHold` 为单一数据源。
3. 产品主数据、客户名称、供应商名称展示组件逐步统一。
4. 权限矩阵作为团队权限页的只读/半编辑视图补齐，不替代当前角色保存链路。

### P3：架构升级

1. 多角色。
2. 多组织。
3. 字段级权限。
4. 审批流与通用工作流的模块接入策略。
5. BI 宽表或读模型。

## 4. 本轮已做的小纠偏

本轮只做低风险产品体验修正，不做底层重构：

- 登录页增加正式员工账号与默认演示账号说明。
- 员工账号创建成功后增加交付提示，提醒通过安全渠道交付初始密码，并要求员工首次改密。
- 角色授权页增加权限摘要、数据范围摘要、高风险权限标识。
- 角色保存复核改为更接近“授权确认单”的语义。

这些改动符合成熟 ERP 的账号治理方向，但仍属于 P1 体验增强，不代表权限架构已经达到金蝶级完整模型。

## 5. 反幻觉验证记录

### 本地验证

- `npx tsc --noEmit --pretty false`：通过。
- `npm run build`：通过，生成前端入口 `index-D4DMUSUE.js`。
- `npm run audit:team:account-lifecycle`：通过，稳定运行时账号生命周期链路未被破坏。
- `npm run audit:permissions:system-ui`：通过，稳定运行时角色授权链路未被破坏。
- `npm run check:runtime`：通过，当前稳定运行时仍是旧前端入口 `index-QGkEKY_L.js`。

### 重要边界

本轮新构建在 `http://127.0.0.1:4173/` 预览时可以看到登录页新增文案，但登录请求被后端 CORS 拦截。

结论：

- `4173` 只能作为静态新构建视觉预览。
- 不能把 `4173` 的业务登录失败当成功能坏。
- 也不能把 `5001` 旧稳定包的浏览器审计当成本轮新 UI 已经发布。
- 后续进入打包前，必须把新 dist 部署进受治理运行时，再跑浏览器审计。

## 6. 外部对标纠偏

联网复核后，本轮采用以下判断：

- 成熟 SaaS/ERP 的权限体验应基于岗位角色、最小权限、审计日志和清晰授权确认。
- OWASP 将访问控制失败列为高风险，不能为了体验放松授权边界。
- NIST 身份指南强调认证与凭据生命周期治理，初始密码交付与首次改密必须清晰。
- 金蝶公开文档中，角色是权限载体，并提供权限查询、业务对象授权、授权范围等能力；这些应作为 P2/P3 目标，不应在 P1 强行照搬。

## 7. 下一步执行准绳

从下一节点开始，优先治理顺序调整为：

1. 先修 CRM / 销售订单这类最高频业务页面。
2. 再补团队权限的权限矩阵只读视图。
3. 同步做发布冻结闸门，不降低冻结标准。
4. 每做完一个节点，必须记录：改了什么、没改什么、验证了什么、哪些只是预览未发布。
