# 当前偏航点与收口建议

## 一、结论先行

当前系统没有“跑出 ERP”，但确实出现了一个明显的偏航点：

- 原方案的主线是 `数据库升级 -> 回款闭环 -> 生产管理 -> 财务报表 -> 部署优化`
- 当前实现把一部分精力前移到了 `调账中心`、`治理文档`、`结构整理` 和 `mock 支撑`

这不是方向错误，更像是**为了先跑通可用性而提前做了治理层收口**。问题在于：

- 如果继续扩大这条支线，它会挤占原本最该先补的数据库和生产主链路
- 如果不明确边界，后续会把“支撑模块”误当成“主业务完成”

## 二、当前偏航点

### 1. 先做了治理层，而不是先收底座

已经投入较多的是：

- 调账中心
- 文档治理中心
- 代码结构梳理
- 部署与运行说明

这些都对，但它们属于**体系治理和运维收口**，不是 V1.0 的第一优先级。

### 2. 调账中心被做成了跨域统一入口

调账中心已经覆盖：

- 财务补录
- 生产损耗
- 库存盘差

这样做的好处是统一留痕，但风险是：

- 语义会被压平
- 未来字段容易越长越多
- 财务、生产、库存的审批规则可能被混成一套

### 3. 开发环境里 mock 支撑先补齐了

这是为了保证本地能演示和迭代，但它也会带来一个错觉：

- 页面能跑，不代表主线已经完成
- mock 能响应，不代表真实业务闭环已经完成

## 三、收口建议

### 1. 把调账中心收回成支撑模块

调账中心继续保留，但只做三件事：

- 财务纠偏
- 生产损耗留痕
- 库存盘点修正

不要继续把它扩成新的核心业务域。

### 2. 把数据库升级重新拉回第一优先级

只要数据库还停在 SQLite，系统就仍然处在过渡期。

数据库升级的意义不是“换一个引擎”，而是：

- 让单机和线上部署统一
- 让并发和备份恢复更稳
- 让后续财务、生产、报表都站在同一底座上

### 3. 把生产链路提回主线

当前最欠缺的不是更多支撑页，而是：

- BOM
- 工单
- 工序
- 质检
- 库存联动

这些才是工厂型 ERP 的业务骨架。

### 4. 把财务报表放到生产之后收口

财务报表不是独立起步项，它需要：

- 回款数据
- 调账数据
- 生产成本数据
- 库存与损耗数据

没有这些，报表只能是静态统计，不能形成真正的管理闭环。

## 四、收口判定

当前可接受的定义是：

- **主线未跑偏**
- **执行顺序有轻微偏航**
- **需要马上收回到数据库和生产主链路**

换句话说：

**调账中心可以留，但不能抢主线。**
