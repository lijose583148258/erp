# 54_P3 运行时健康检查重试与顺序审计治理

日期：2026-06-19

## 本次目标

补齐企业版封装后的启动与健康检查证据，避免把验证脚本的瞬时误判当成产品故障，也避免多个审计同时抢占 5001 运行源。

## 诊断结论

并行运行 `desktop-shell`、`clean-runtime`、`package-e` 会互相切换运行源：

- `desktop-shell` 会验证 F 盘稳定包。
- `clean-runtime` 和 `package-e` 会验证 E 盘干净运行包。
- 并行执行时，5001 的 active origin 可能被切换，导致健康检查短暂失败。

另一个问题是 `check-runtime.ps1` 对第一个 `/health` 请求没有重试。报告中曾出现 `/health` 瞬时连接失败，但首页和所有静态资产均为 200，属于启动/切换窗口内的误判。

## 调整内容

- `check-runtime.ps1` 增加 `Invoke-WebRequestWithRetry`。
- 普通 URL 检查默认最多 3 次，每次间隔 500ms。
- 首页资产发现也使用同一重试逻辑。

## 验证结果

按顺序执行后通过：

- `npm run deploy:clean-runtime`
- `npm run audit:clean-runtime`
- `npm run audit:phase3:package-e`

`package-e` 结果：12/12 通过。

## 后续注意

发布侧审计不要并行跑会启动或切换运行源的任务。尤其是桌面壳、干净运行包、package-e，应按顺序执行，避免相互污染 active origin。
