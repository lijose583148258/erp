# CRM角色权限与客户池流转方案（当前版）

## 一句话结论

这个系统里的 CRM 不应该只分“公海 / 私海”，而应该按 **业务线（内销 / 分销） + 客户池（公海 / 内部池 / 私海） + 角色（销售 / 经理 / 管理员）** 三层一起管。

这样才符合当前代码里已经出现的 `direct / channel / mixed` 业务分段，也能兼容现有的 `salespersonId` 私海归属逻辑。

## 1. 角色权限层

### 管理员 `admin`

- 看全局
- 配置业务线、客户池、分配规则、回收规则
- 手动分配 / 回收 / 转派
- 看全部审计

### 经理 `manager`

经理建议再细分为：

- `manager_direct`：管内销线
- `manager_channel`：管分销线

权限建议：

- 看自己业务线的公海、内部池、私海
- 分配客户
- 回收客户
- 看团队负载、领取记录、超时客户
- 查看本业务线全部审计

### 销售 `sales`

- 只能看自己私海
- 可以看自己业务线的公海 / 内部池
- 可以领取允许领取的客户
- 不可以回收别人名下客户
- 不可以跨业务线领取

### 财务 `finance`

- 只读客户信用、回款、逾期、风控状态
- 不参与客户归属变更

### 仓库 `warehouse`

- 只读与发货、签收、客户收货相关的数据
- 不参与客户归属变更

## 2. 客户池层

建议把客户池分成三层，而不是只做两层：

### A. 公海

- 未明确归属的共享池
- 可以被领取
- 由经理或系统规则分配到内部池

### B. 内部池

这里建议把“内部池”理解成 **团队池 / 业务线池**，它比公海更近一步，但还没进入某个销售个人的私海。

它的作用是：

- 作为分配缓冲区
- 作为经理可控的待派发池
- 作为需要再筛选、再确认、再派发的客户池

### C. 私海

- 已明确归属到某个销售或某个 owner team 的客户
- 日常跟进责任落到个人
- 经理可以看，但不能绕过审计直接改历史

## 3. 推荐流转规则

### 3.1 公海 -> 内部池

适用场景：

- 新客户导入
- 经理筛选后进入团队待分配
- 公海客户按规则转入业务线池

执行人：

- `admin`
- `manager`

结果：

- 记录 `assignedAt`
- 记录 `assignedBy`
- 记录 `assignedReason`
- 客户池类型从 `public` 变为 `team` 或 `internal`

### 3.2 内部池 -> 私海

适用场景：

- 按负载、区域、行业、客户等级分派给销售
- 销售领取后确认接单
- 经理定向派发

执行人：

- `admin`
- `manager`
- 允许的 `sales` 领取动作

结果：

- 记录 `claimedAt`
- 记录 `claimedBy`
- 记录最终负责销售
- 客户池类型从 `internal` 变为 `private`

### 3.3 私海 -> 内部池

适用场景：

- 销售离职、转岗
- 长期无有效跟进
- 经理回收
- 系统 SLA 超时自动回收

执行人：

- `admin`
- `manager`

结果：

- 记录 `reclaimedAt`
- 记录 `reclaimedBy`
- 记录 `reclaimReason`
- 归属从个人改回团队池

### 3.4 私海 -> 公海

建议不要让销售直接随意放回公海。  
更稳的做法是：

- 销售只能发起“回收申请”或“放回申请”
- 经理或管理员审批后才真正回到公海

适用场景：

- 客户质量不符合要求
- 线索错误
- 无效客户
- 需要重新进入共享池

## 4. 业务线怎么切

### 内销线 `direct`

- 客户池：内销公海 / 内销内部池 / 内销私海
- 经理：`manager_direct`
- 销售：内销销售

### 分销线 `channel`

- 客户池：分销公海 / 分销内部池 / 分销私海
- 经理：`manager_channel`
- 销售：渠道销售 / 经销维护

### 总部视角 `mixed`

- admin / 部分 manager 看全局
- 主要用于策略、审计、财务、回收控制

## 5. 角色权限与动作矩阵

| 动作 | 销售 | 经理 | 管理员 |
| --- | --- | --- | --- |
| 看公海 | 允许本业务线 | 允许本业务线 | 允许全部 |
| 看内部池 | 允许本业务线部分范围 | 允许全部本业务线 | 允许全部 |
| 看私海 | 仅自己 | 团队范围 | 全局 |
| 领取公海 | 允许受控领取 | 允许 | 允许 |
| 公海转内部池 | 不允许 | 允许 | 允许 |
| 内部池转私海 | 不允许 | 允许 | 允许 |
| 私海回收 | 不能直接做 | 允许 | 允许 |
| 跨业务线转派 | 不允许 | 通常不允许 | 允许 |
| 查看审计 | 仅自己的动作 | 本业务线 | 全局 |

## 6. 建议的数据库概念

现有 `salespersonId` 可以继续保留，但还需要补这些概念：

- `businessLine`: `direct` / `channel`
- `poolType`: `public` / `internal` / `private`
- `ownerType`: `pool` / `team` / `user`
- `ownerId`
- `ownerTeamId`
- `assignedAt`
- `assignedBy`
- `claimedAt`
- `claimedBy`
- `reclaimedAt`
- `reclaimedBy`
- `assignmentStatus`
- `assignmentReason`

## 7. 推荐的治理原则

1. 一个客户在任何时刻只有一个主归属。
2. 公海、内部池、私海不是三个页面，而是三个状态。
3. 内销和分销不能混用同一套分配规则。
4. 经理可以管理，但每次操作都要留痕。
5. 销售不能绕过经理直接改别人名下客户。

## 8. 和当前系统的关系

当前系统已经有这些基础：

- `segment: direct | channel | mixed`
- `manager_direct / manager_channel`
- `salespersonId`
- CRM 页面中的 `my/public` 视图概念

所以这份方案不是从零发明，而是把现有雏形补成正式规则。

## 9. 结论

如果要让 CRM 真正适合这套系统，下一步不能再只写“公海 / 私海”。

正确顺序应该是：

1. 先定业务线：内销 / 分销
2. 再定池子：公海 / 内部池 / 私海
3. 再定角色：销售 / 经理 / 管理员
4. 最后定动作：分配 / 领取 / 回收 / 转派 / 审计
