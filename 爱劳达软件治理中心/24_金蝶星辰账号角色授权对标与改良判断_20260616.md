# 金蝶星辰账号角色授权对标与改良判断

日期：2026-06-16

## 1. 结论

当前登录、员工账号创建、角色授权的改法不能简单判定为“完全没问题”。

更准确的判断是：

- P0 安全底线：当前方向是对的。
- P0 审计证据：当前已经通过。
- 商业成熟度：还没有达到金蝶星辰/金蝶云星空这类成熟 ERP 的完整权限体验。

所以后续不能继续“为了能用而能用”，需要按成熟 ERP 的权限模式补齐产品细节，但不能一次性重构成复杂系统。

## 2. 外部对标要点

参考金蝶公开资料与产品手册，成熟 ERP 的账号/角色/权限体系通常具备：

1. 角色驱动授权
   - 用户通过角色获得系统使用权限。
   - 角色可以授权业务对象功能权限。

2. 功能权限、数据权限、字段权限分层
   - 不只是菜单能不能看。
   - 还要控制数据范围、字段可见性、金额敏感字段等。

3. 用户与业务身份关联
   - 用户可关联员工、供应商、客户联系人。
   - 这种关联能服务于业务数据过滤，比如“当前用户对应业务员”。

4. 组织范围与多组织授权
   - 多组织模式下，用户需要组织范围。
   - 角色可在组织下批量追加或删除。

5. 子管理员/安全管理员/审计管理员分离
   - 成熟系统会区分系统管理员、安全管理员、审计管理员。
   - 避免一个 admin 拥有所有配置、授权和审计权。

6. 权限报表与查询
   - 管理员需要能查询角色权限。
   - 最好能输出“某角色到底有什么权限”的报表。

7. 批量操作与权限复制
   - 批量添加角色。
   - 批量删除角色。
   - 权限包复制到新门店/新组织。

## 3. 当前系统现状

当前系统已经具备：

- 员工个人账号创建。
- 首次登录强制改密。
- 停用账号后禁止登录。
- 动态角色列表。
- 角色权限勾选。
- 角色权限保存前复核。
- 角色权限变更结构化审计差异。
- 默认演示账号不能进入业务区。

这些已经满足 P0 发布安全底线。

## 4. 当前主要差距

### 4.1 用户目前是单角色模型

当前用户主要是一个 `role` 字段。

风险：

- 成熟 ERP 通常支持一个用户拥有多个角色。
- 单角色会导致实际企业中“销售主管兼审批人”“仓库主管兼盘点员”等场景难表达。

判断：

- 不建议在当前冻结前立即改成多角色模型。
- 这是数据库与权限计算层重构，风险很大。
- 应作为 P2/P3 架构升级项。

### 4.2 权限层次还不够立体

当前主要是：

- 功能权限
- 数据范围 `dataScopes`

不足：

- 字段权限还不完整。
- 金额权限、敏感字段权限、导出权限、审批权限之间的边界仍需细化。

判断：

- P1 可以先补“敏感权限提示”和“权限分组说明”。
- P2 再设计字段级权限和金额权限。

### 4.3 创建员工账号流程偏技术化

当前创建员工账号直接输入：

- 登录账号
- 初始密码
- 邮箱
- 角色
- 业务线

不足：

- 没有清楚地区分“员工资料”和“登录账号”。
- 没有提示“员工拿到初始密码后必须首次改密”。
- 没有给管理员一个创建成功后的交付提示。

判断：

- P1 应优化文案和流程提示。
- 不需要重构，只要把人类使用路径讲清楚。

### 4.4 授权方式缺少“权限报表/预览”

当前已有变更复核，但还不够像成熟 ERP。

应补：

- 角色权限摘要。
- 已选权限数量。
- 高风险权限标记。
- 保存后审计记录入口或提示。

判断：

- P1 可做轻量增强。
- 不要做复杂权限树重构。

### 4.5 管理员职责分离仍需强化

当前已有角色权限和审计，但成熟 ERP 会拆分：

- 系统管理员
- 安全管理员
- 审计管理员

判断：

- 当前 P0 不必拆。
- P2/P3 应补“安全管理员/审计管理员”预置角色与权限边界。

## 5. 对当前改法的判断

### 可以保留

- 默认账号不能直接进入业务区。
- 员工账号首次登录强制改密。
- 创建员工账号后 `mustChangePassword = true`。
- 角色保存前复核。
- 角色变更写结构化审计。
- 审计脚本使用临时审计管理员，而不是默认 admin。

### 需要优化

- 登录页要更清楚地区分“演示默认账号”和“正式员工账号”。
- 团队管理页要增加更明确的新手引导。
- 创建账号成功后要提示管理员交付账号和初始密码，并提醒员工首次改密。
- 角色授权页要增加权限摘要、高风险权限标识、已选数量。
- 权限变更复核弹窗要展示更像“授权确认单”的内容。

### 暂不建议马上重构

- 多角色模型。
- 多组织授权。
- 字段级权限引擎。
- 子管理员授权模式。
- 权限批量导入导出。

这些属于 P2/P3，当前直接做会扩大风险。

## 6. 后续改良顺序

### P1：不改模型，只优化可用性

1. 登录页增加正式账号/演示账号区别提示。
2. 员工账号创建成功后给管理员明确交付提示。
3. 角色授权页增加权限摘要和高风险权限提示。
4. 角色保存复核弹窗改成“授权确认单”口径。

### P2：补权限管理能力

1. 角色权限报表。
2. 敏感权限清单。
3. 数据范围说明。
4. 审计记录入口。

### P3：架构升级

1. 多角色。
2. 多组织。
3. 字段级权限。
4. 子管理员/安全管理员/审计管理员分离。

## 7. 反幻觉结论

- P0 通过不代表体验成熟。
- 不能照搬金蝶完整权限体系，否则会把当前系统改成高维护成本架构。
- 当前正确策略是：先保留安全底线，再按成熟 ERP 的权限体验逐步补“可理解、可复核、可追踪”的产品细节。
