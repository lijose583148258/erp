# 权限同类读入口收口包 2026-04-18

## 一、目标

在完成结构目录与运行链梳理后，按当前有效运行链继续处理后端读接口的同类风险：

- 前端菜单隐藏不等于后端安全。
- 后端 `authenticate` 只证明已经登录，不证明角色有权读取该模块。
- 本包只收口读入口角色门禁，不改业务状态机、不改历史归档、不删除用户数据。

## 三、角色口径

本包按 `components/Layout.tsx` 当前菜单权限对齐后端读入口：

| 模块 | 可读角色 | 明确拒绝 |
|---|---|---|
| 订单 | `admin`、`manager`、`sales`、`finance` | `warehouse` |
| 合同 | `admin`、`manager`、`sales`、`finance` | `warehouse` |
| 发货物流 | `admin`、`manager`、`sales`、`warehouse` | `finance` |
| 售后 | `admin`、`manager`、`sales` | `finance`、`warehouse` |
| 样品 | `admin`、`manager`、`sales`、`warehouse` | `finance` |

说明：

- 销售角色的记录级范围仍由控制器/服务层继续限制，路由层只做第一道角色门。
- 财务可以读订单与合同，是为了回款、对账和合同收款节点闭环。
- 仓库可以读发货与样品，是为了发货/寄样执行闭环。
- 仓库不应直接读取订单全量列表；发货候选订单仍走 `/api/orders/shipping-ready` 的专用入口。

## 五、反思

这次没有继续往 UI 或新功能发散是正确的。结构梳理后暴露的最大同类风险不是“页面看不见”，而是“登录后直接打 API 能不能越权读”。本包把一批只认证不授权的读入口先收口，并用角色矩阵脚本固定为回归证据。

仍需继续的点：

1. `dashboard.routes.ts` 虽然所有角色可进，但还需要继续做“角色看到的数据是否符合岗位”的专项审计。
2. `procurement`、`production`、`warehouse` 等模块还要继续做同样的路由层 + 记录级权限双层扫描。
3. 当前 `lint` 仍有 108 个 warning，虽然不阻断运行，但会影响长期维护，需要后续分包降噪。
4. CRM 菜单仍允许 `finance` 看到入口，但后端已禁止完整 CRM 数据；后续应做财务专用客户摘要接口，避免菜单和后端口径不一致。

## 六、结论

本包已完成。当前不是“完美上线”，但权限读入口比上一版更稳，且验证证据覆盖了构建、运行、API、数据库、浏览器和乱码闸门。
