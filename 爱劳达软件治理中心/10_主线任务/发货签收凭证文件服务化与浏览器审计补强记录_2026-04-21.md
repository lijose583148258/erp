# 发货签收凭证文件服务化与浏览器审计补强记录

日期：2026-04-21

## 背景

全局结构扫描显示 `shipping.controller.ts` 仍有 884 行，且直接承载发货、出库、签收、差异、库存、订单状态同步等多条链路。

本轮没有贸然重写发货主链，而是先拆低风险但关键的签收凭证文件处理：

- 文件类型白名单。
- base64 data URL 校验。
- 文件魔数校验。
- 上传目录落盘。
- 存储路径穿越防护。

这些逻辑不应长期留在控制器顶部，否则会干扰业务链路阅读，也不利于后续扩展真实文件上传、EXE 本地壳和服务器部署。

## 本轮改动

新增文件：

- `backend/src/services/shipping-receipt-file.service.ts`

迁移职责：

- `RECEIPT_MIME_EXT`
- `storeReceiptFile`
- data URL 解码。
- MIME 与文件签名校验。
- 文件大小限制。
- 上传路径安全校验。

调整文件：

- `backend/src/controllers/shipping.controller.ts`

控制器变化：

- 不再直接引入 `fs`、`path`、`getUploadDir`。
- 不再内联签收文件解码和落盘逻辑。
- 上传凭证业务仍保持原有调用方式，行为不变。

## 浏览器审计补强

本轮发货浏览器审计首次出现：

- `create-shipment-via-ocr exceeded 25000ms`

复核结论：

- 发货 API 审计通过。
- 独立浏览器诊断确认 OCR 应用按钮可以触发 `POST /api/shipping`，接口返回 201，发货单可回读。
- 该红灯发生在 OCR 创建发货单阶段，还没有进入签收凭证上传阶段，因此不是本次文件服务拆分导致。

补强脚本：

- `scripts/shipping-browser-audit-v1.cjs`

变化：

- OCR 应用按钮点击前等待可见并滚动到视口。
- 点击后监听 `POST /api/shipping`。
- 若接口返回非 2xx，报告直接输出接口状态。
- 若接口没有触发，再进入回读轮询，不再只给一个含糊的 25 秒超时。

## 收益

- `shipping.controller.ts` 从 884 行降到 838 行。
- 发货上传文件安全逻辑形成独立服务边界。
- 浏览器发货审计的 OCR 创建阶段不再只报笼统超时，能区分点击、接口、回读问题。
- 后续做真实文件上传、服务器部署、EXE 本地壳时，可以优先复用 `shipping-receipt-file.service.ts`。

## 后续约束

- 不得在 `shipping.controller.ts` 重新内联文件魔数、base64 解码和路径校验。
- 发货浏览器审计红灯必须先看 `shipping-audit-report-v1.json` 和截图，不能用 API 通过替代浏览器失败。
- 后续再拆发货主链时，应优先选择“发货出库扣减库存服务”和“签收回单事件服务”，不要一口气重写整个控制器。
