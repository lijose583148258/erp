# 发货 OCR 回归闸门与低信息量超时收口记录 2026-04-21

## 结论

上一包修复了发货 OCR “识别成功但不落库”的真实问题。本包继续把该问题固化成制度化闸门，避免后续再次出现类似假完整。

本包不改变业务功能和 UI 风格，只增强验收链：

1. 新增轻量 OCR 规则回归脚本。
2. 将 OCR 回归纳入阶段 3 准入。
3. 增强发货浏览器审计，在“点击应用后没有 POST”时输出明确原因和页面证据，不再只等 25 秒超时。

## 新增闸门

新增命令：

```bash
npm run audit:shipping:ocr
```

覆盖场景：

- `客户名称: 公司名`
- `公司名称: 公司名`
- `Ship To: company name`
- `客户名称:`、`名称:`、`customer:`、`ship to:`、`公司名称:` 等标签残留仍可进入客户匹配。

该闸门的定位是快速发现 OCR 解析/客户匹配退化，不替代浏览器级真实点测。

## 浏览器审计增强

原问题：

```text
create-shipment-via-ocr exceeded 25000ms
```

这个错误信息不够好，因为它只说明“最后没有回读到单据”，不能说明到底是：

- 没点到按钮；
- 客户匹配失败；
- 前端校验拦住；
- 没有发出 `POST /api/shipping`；
- 后端返回失败；
- 或者只是回读慢。

本包增强后：

- 点击“应用到表单”前保存 OCR 预览文本。
- 监听 `POST /api/shipping`。
- 如果没有 POST，立即记录 `shipping-ocr-submit-request-evidence`，包含预期客户名、追踪号、预览文本和页面文本摘录。
- 如果 POST 返回非 2xx，明确报 `OCR shipment create failed: <status>`。
- 如果 POST 成功，记录 `status: 201`，再继续列表回读。

## 反思

本包中间出现过一次假红灯：我将 `npm run build` 和 `check-runtime.ps1` 并行执行，构建过程会清理并重建 `dist`，运行资源检查同时读取静态资源，导致两个资源短暂 500。

结论：

- 构建和运行资源检查不能并行。
- 只读扫描可以并行。
- 会改变 `dist`、数据库、端口、运行进程的命令必须串行。

该经验后续纳入阶段 3 执行习惯，避免把人为测试顺序错误误判为系统缺陷。
