# 回款中心全局架构决策

日期：2026-04-16

状态：已定稿，作为后续回款中心与货抵中心统一改造的基线。

## 一、这次不再凭感觉改
本次决策基于成熟收款/催收产品的共通模式：

- SAP Collections Management：以 `worklist / worklists` 作为日常入口，再进入 `Process Receivables / Process Accounts` 处理当前客户或账户，在过程中查看未清项、最近付款、承诺付款、争议、联系记录等。
- Oracle PeopleSoft Collections Workbench：核心是 `central workspace / complete view of each customer`，在一个中心工作台里处理动作，但不是把全部内容堆在单侧窄区。
- Microsoft Dynamics 365 Finance Collections：用 `customer pools / list pages / all collections information for a customer is on one page` 的思路组织工作，强调“列表组织工作 + 客户详情统一动作”。

## 二、调研后的结论
### 1. 对的方向

- 必须有一个统一的“当前业务对象焦点”。
- 回款、承诺、争议、拦截、合同节点，应该围绕同一个订单 / 客户上下文联动。
- 台账与动作不能脱钩。

### 2. 不该做的事

- 不应该把所有模块信息都硬塞进左侧动作栏。
- 不应该让左侧既是动作区，又承担完整明细区和完整历史区。
- 不应该把“当前订单工作流”和“全局台账浏览”混成一层。

### 3. 更优结构

回款中心应采用三层结构：

1. 工作清单层
   - 逾期清单
   - 收款台账
   - 合同节点
   - 全局承诺表
   - 全局争议表
   - 全局拦截表
2. 当前订单详情层
   - 当前订单主数据
   - 回款流水
   - 承诺记录
   - 争议记录
   - 拦截状态
   - 合同节点
3. 高动作层
   - 催收提醒
   - 承诺付款
   - 发起争议
   - 核销最近一笔 / 选中一笔
   - 释放拦截

## 三、爱劳达系统里的最终形态
### A. 左侧区域

左侧只保留：

- 当前订单摘要
- 订单总额 / 已收 / 未收 / 状态
- 高频动作按钮
- 最多一小段风险 / 拦截建议

左侧不承担：

- 全量承诺表
- 全量争议表
- 全量拦截表
- 多个大表堆叠

### B. 中间主区域

中间主区域承担“当前订单详情层”，做成稳定标签：

- `回款流水`
- `承诺记录`
- `争议记录`
- `拦截状态`
- `合同节点`

这一部分是“当前订单专属详情区”，不是全局表。

### C. 下方或右下区域

保留全局台账：

- 全部收款台账
- 全部承诺记录
- 全部争议记录
- 全部拦截记录

这一部分服务于财务浏览、筛选、导出和批量处理。

## 四、和货抵中心的统一原则

后续回款中心与货抵中心统一采用同一种交互语义：

- 主单：总额、累计、剩余、状态
- 子记录：每次实际执行
- 动作：审批、核销、过账、冲销、提醒
- 详情：当前主单的执行明细
- 全局表：所有主单或所有执行记录的检索台账

换句话说：

- 回款：`订单主单 + PaymentRecord`
- 货抵：`协议主单 + 批次执行`

前端不再各做各的页面哲学。

## 五、接下来必须按这个顺序推进
### P0 现在就做

- 保留已经完成的“订单焦点同步”。
- 不再把承诺 / 争议 / 拦截整块硬塞左侧。
- 新建“当前订单详情区”组件。

### P1 紧接着做

- 当前订单详情区的五个标签：
  - 回款流水
  - 承诺记录
  - 争议记录
  - 拦截状态
  - 合同节点

### P1 同步验收

- 浏览器级审计：
  - 从逾期清单点一单
  - 焦点同步到详情区
  - 新增承诺
  - 新增争议
  - 核销一笔回款
  - 详情区与全局表同步回读

### P2 后续治理

- 全局文案清污
- 多语言口径统一
- 导出文件命名统一
- 订单 / 回款 / 货抵共享状态色与标签

## 六、对“是否更好”的最终判断
不是“把所有相关东西都挂到左侧”更好。

真正更好的，是：

- `同一个订单焦点` 必须统一
- `动作区` 必须简洁
- `详情区` 承担当前对象的完整信息
- `全局台账` 保持独立

这才是更适合爱劳达 ERP + CRM 的长期结构。
