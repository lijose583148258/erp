# 系统全盘梳理与风险台账 2026-04-18

## 结论先行

当前爱劳达 ERP+CRM 不是“框架方向错了”，而是已经形成了一个可运行的 React + Vite 前端、Node + Express + Prisma 后端、SQLite 本地运行库的模块化单体。但它仍处在“主链路逐步闭环 + 治理收口”的阶段，不能直接宣布商业上线级完美。

本轮全盘梳理确认：

- 前端构建通过：`npm run build`，约 12 秒完成。
- 后端 TypeScript 构建通过：`npm run build:backend`，约 14 秒完成。
- 数据库结构审计通过：`npm --prefix backend run db:audit`，`tableCount=43`，`issueCount=0`。
- 当前健康接口通过：`GET http://127.0.0.1:5001/api/health` 返回 200。
- 当前 CDP 核心页面烟测通过：18 个核心路由，0 失败，0 console error。
- lint 已从“假红”修正为有效源码/脚本边界，当前 `npm run lint` 为 0 error、109 warning。

严肃边界：

- 以上只能证明“启动、构建、核心页面加载、数据库结构、若干主链路验收”可用。
- 不能证明所有业务流程已经 100% 商业闭环。
- 仍需继续做 CRM 权限/AI 隔离、订单多次回款、采购分批入库、生产 10 原料 BOM、仓储批次台账、货抵分批结算、备份恢复、并发长跑等深测。

- Excel 能力：依赖 `xlsx`，适合订单明细、BOM、导入导出、台账类模块继续深化。

### 后端

- 框架：Express + TypeScript。
- ORM：Prisma 5。

- 线上迁移准备：已有 `pg`、Postgres 迁移脚本和 `db:pg` 命令，但仍需迁移演练和备份恢复验收。
- 安全中间件：helmet、cors、rate-limit、JWT、audit middleware。

### 统一性判断

当前主框架基本统一：前端 React/Vite/TS，后端 Express/TS/Prisma。主要不统一点不是语言，而是：

- 前端页面仍有“老页面大组件 + 新 UI primitives”并存。
- 后端部分 controller/service 太大，领域边界没有完全拆开。
- scripts 既有新 CDP 规范，也有旧 Playwright launch guard 脚本，需要继续统一到 CDP 优先。
- lint 原先把 `output`、治理文档、隔离区扫进来，已在本轮修正为有效边界。

## 九、真实不足清单

### P0：立刻影响维护/验收可信度

1. lint 原先扫描边界错误，已修正；但 109 个 warning 仍是维护债。
2. `backend/backups` 为空，而根目录 `backups` 有历史备份；备份口径需要统一，否则恢复时容易找错地方。
3. 旧浏览器脚本仍有一部分使用 `browser-launch-guard`，新标准应该逐步统一到 CDP 优先、可见浏览器/后台浏览器分层。
4. `mockAdapter.ts` 仍偏大，必须防止“真实 API 失败后被假数据掩盖”。
5. 大 controller/service 仍多，未来修复容易牵一发动全身。

### P1：会影响上线/长期本地稳定

1. CRM 客户池、公海/私海、内销/分销、AI 数据隔离需要浏览器级角色切换深测。
2. 订单三轴状态、分次回款、回款核销、订单详情读回需要继续做浏览器闭环。
3. 采购分批入库、收货差异、入库凭证、供应商权限需要继续做冲突和回读。
4. 生产 10 原料 BOM、少耗料禁止、完工扣料、成品入库、成本凭证需要继续极限测试。
5. 仓储批次、库位、库存台账、调账、反向冲销需要继续做库存守恒验证。
6. 货抵支付/换货贸易分批抵扣已经有方向，但还需要和采购/发货/库存/财务完全打通。
7. 汇率联网更新有服务入口，但本地离线、联网失败、汇率缓存、审计留痕仍需验收。
8. EXE 本地壳需要独立验证：禁止 CDN、禁止远程字体、端口检测、数据库路径、备份路径、日志路径都要固定。

### P2：美化治理/降低维护成本

1. UI-P0 底座已有，但页面迁移不完整，任意 Tailwind 值仍很多。
2. translations 可以按模块拆分，减少三语文件 1000 行级维护压力。
3. 旧临时脚本可以继续进入治理隔离清单，不删除但降权。
4. 命令搜索、页面标题、状态徽章、空状态文案需要全模块统一。
5. 报告 JSON 字段需要继续统一，避免 `status`、`formulaStatus`、`paymentStatus` 等混淆。

## 十二、反思

方向没有偏离：这轮不是继续堆功能，而是把“系统到底是什么、哪里真绿、哪里假绿、哪里维护成本高”重新照清楚。

更好的做法是：接下来每个业务包都必须同时交付四件东西：

1. 业务闭环代码。
2. API 读回验收。
3. 浏览器真实点测验收。
4. 治理中心记录。

如果只有 build、只有 HTTP 200、只有截图，都不能算完成。
