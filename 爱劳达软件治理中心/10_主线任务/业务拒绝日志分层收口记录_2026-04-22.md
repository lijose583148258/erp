# 业务拒绝日志分层收口记录

## 背景

阶段 3 和 full release 已经能通过，但 `logs/error.log` 长期混入大量负向审计故意触发的业务拒绝，例如：

- 超额应收调整。
- 采购单非法状态流转。
- 生产 BOM 未覆盖全部原料即完工。
- 发货重复签收。
- 货抵重复过账或重复批次。

这些并不是系统崩溃，却会把错误日志刷红，导致后续人工判断“真 BUG / 预期拦截”时被误导。

## 三步法

1. 翻译现象：
   - release 通过，但 `error.log` 仍不断出现预期业务拒绝栈。
2. 判断层级：
   - API 和业务规则是正确的。
   - 问题在日志分层：控制器 catch 后统一 `logger.error`，没有区分业务拒绝和系统异常。
3. 修复：
   - 不改 API 响应。
   - 不放宽业务规则。
   - 不删除负向审计。
   - 在 logger 层识别明确的预期业务拒绝，将其降为 `warn`，保留在 combined 日志中，但不再进入 `error.log`。

## 改动

- `backend/src/utils/logger.ts`
  - 新增 `isExpectedBusinessRejection`。
  - 明确识别业务拒绝码和常见业务拦截文本，例如 `*_NOT_FOUND`、`*_INVALID`、`*_NOT_ALLOWED`、`*_ALREADY`、`*_REQUIRES`、`*_EXCEEDS`、`DUPLICATE`、`ProductionCompletionValidationError`、`No available stock`。
  - 保留系统异常信号，例如 `PrismaClient`、`TypeError`、`ReferenceError`、`SyntaxError`、`DATABASE_ERROR`、数据库连接/启动失败，这些仍进入 `error.log`。

## 验收证据

- `npm --prefix backend run build`：通过。
- `npx tsc --noEmit`：通过。
- `node scripts/effective-source-mojibake-gate-v1.cjs`：通过。
- `npm run audit:receivable:adjustment`：通过，且 `logs/error.log` 字节数无变化。
- `npm run verify:release`：通过，21/21，且 `logs/error.log` 字节数无变化。

## 结论

本包降低了长期试运行时的误判成本：以后 `error.log` 更接近真实系统异常，负向审计仍保留业务证据，但不会继续污染错误日志。
