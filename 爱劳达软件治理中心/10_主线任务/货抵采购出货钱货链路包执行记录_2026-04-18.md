# 货抵 / 采购 / 出货 / 库存钱货链路包执行记录

日期：2026-04-18  
目标：减少钱货链路中的“假通过”、重复入库/出库、误扣库位、越权可见、API 绿但业务不闭环等风险。

## 本包范围

- 货抵：销售角色只能看到和操作自己可触达的客户/订单相关货抵记录，不能枚举经理创建的公共/供应商货抵记录。
- 采购：采购单不能在创建时直接设为“已收货”，必须通过收货状态推进生成真实库存凭证。
- 出货：发货扣库存只能从成品区 `LOC-FG` 扣减，不能因为同名批次在原料区存在就误扣原料库存。
- 库存：业务闭环型库存凭证增加幂等保护，避免重复收货、重复出货、货抵重复过账造成重复库存变动。
- 并发：库存余额更新从“读旧值后覆盖写入”收敛为增量/条件更新，降低并发丢失更新和超卖风险。

## 关键修复

1. 库存凭证幂等限定在业务闭环型来源：
   `production_consumption`、`production_output`、`procurement_receipt`、`shipping_issue`、`barter_receipt`、`barter_issue`、`barter_receipt_reversal`、`barter_issue_reversal`。

2. 没有对 `warehouse_adjustment` 做一刀切幂等。
   反思原因：同一个库存余额可能多次人工调整，如果按 `sourceType + sourceRef` 全局唯一，会误伤正常业务。

3. Runtime schema repair 增加安全唯一索引：
   `stock_entries_source_type_ref_status_key`。
   如果历史数据已经存在重复业务凭证，不强行失败启动，而是记录 `skipped`，避免把旧数据问题变成启动事故。

4. 出货扣库限定 `LOC-FG`：
   发货不再从任意库位找库存，避免同名批次在 `LOC-RAW` 原料区时被误扣。

5. 采购创建禁止直接 `received`：
   已收货必须经过状态推进，确保库存凭证和审计日志真实生成。

6. 销售查看物流范围优化：
   销售可以看到自己创建、自己订单、自己私海客户相关的物流记录；仍不能越权改物流状态。

## 反思

- 正确方向：本包没有继续堆 UI 补丁，而是回到底层钱货链路，优先修库存凭证、状态推进、库位边界、权限范围。
- 已纠偏点：最初考虑对所有 `sourceType + sourceRef` 做幂等，随后发现会误伤人工库存调整，已改为只保护业务闭环型来源。
- 风险仍在：如果历史运行库已经存在重复业务库存凭证，runtime repair 会跳过唯一索引而不是强制启动失败。后续需要单独做“历史重复库存凭证清理/对账报告”，只报告和隔离，不自动删除。
- 仍需补强：采购和出货目前是“整单收货/整单发货”粒度，后续成熟商业模式应扩为分批收货、分批发货、批次质检、在途库存、到货差异处理。

## 下一步建议

1. 做“历史库存凭证重复扫描与对账包”，只生成报告，不删除数据。
2. 做“分批采购收货 / 分批出货 / 在途库存”模型补强。
3. 做“浏览器逐页钱货链路点测”，重点测试采购、出货、仓储、货抵四页的表单输入、刷新回读和角色切换。
4. 做“长时运行与并发包”，连续运行 30-60 分钟，专盯 SQLite 写锁、重复提交、页面切换和库存金额一致性。
