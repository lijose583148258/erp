# 模块职责冲突收口补包：仓储 / 货抵 / CRM / AI 2026-04-26

## 本包目标

本包继续按多智能体推进，但最终由主控重新跑证据链，不直接采信子任务报告。

目标不是扩功能，而是把上一轮残余的职责冲突继续压下去：

- 仓储“手动入库”容易被误当成采购收货、生产入库、货抵入库。
- 货抵支付里协议总额、本次执行批次、过账流水容易混在一个输入语境。
- CRM 客户池动作容易被散按钮误操作，缺少动作、原因、影响预览、确认记录。
- AI 助手即使安全上下文已经裁剪，规则引擎仍不能再按旧数组明细口径回复。

## 主控复核过程

本轮出现过一次假失败：

- 主控曾将 `E:\爱劳达纯净系统\scripts\start-stable-v2.ps1` 和 `npm run audit:package:origin` 并行执行。
- origin 审计抢在新监听 PID 和 origin 报告稳定前运行，误报 `no listener found on port 5001`。
- 随后串行复核确认：当前监听 PID 与 E 盘 origin 报告一致，属于审计时序误判，不是系统跑到旧入口。

这条已纳入后续规则：启动、重启、部署、origin 审计必须串行，不与浏览器或包来源审计并行。

## 当前结论

本轮可以认为：

- 页面级职责冲突继续明显下降。
- 仓储补录不再被表达成普通入库入口。
- 货抵执行批次不再脱离协议上下文。
- CRM 客户池动作不再是散按钮直点直交。
- AI 助手不再用旧明细数组口径做统计回复。

但仍不能说“所有模块职责冲突 100% 清完”。

## 剩余风险

| 优先级 | 剩余问题 | 原因 |
| --- | --- | --- |
| P1 | 仓储补录还没有后端 `source/reason/note` 强字段 | 当前 `createStockBalance` 合同没有这些字段，本包只做前端边界提示，没有扩后端合同 |
| P1 | 货抵仍是双方各一组 item 输入，不是完全动态多明细行 | 本包不扩后端合同，只补协议选择、批次余额和保存约束 |
| P1 | 调整单库存/批次过账后，成本台账失败可能只记录 warn | 仍需要进入事务或返回 `ledgerRecorded:false` |
| P1 | 回款核验、应收调整提交后同步客户状态失败可能造成假失败 | 仍需要事务内同步或 outbox |
| P1 | 财务应收调整还需要继续叠加订单/客户 data scope | 权限脚本通过不等于所有财务写入口已完成最小可见范围 |
| P1 | 团队业绩接口还需要继续按 segment/team scope 裁剪 | 防止经理看到过多全员信息 |
| P2 | CRM 客户池确认记录目前是前端确认意图，权威记录仍以后端池历史为准 | 后续可把确认理由和影响预览进一步落进审计事件 |

## 反思

- 本轮方向没有偏离：没有继续乱扩功能，而是收口“用户不知道在哪里输入、输入后到底影响什么”的问题。
- 子智能体能提高速度，但主控复核仍是必要的；仓储包曾短暂出现 TypeScript 重复属性问题，主控复跑发现并确认已修。
- 浏览器、人工作流、启动、origin 审计不能无脑并行；启动类任务必须串行，否则会产生假失败。
- 当前系统已更适合进入本地试跑，但还不是商业完美闭环。下一包应优先处理后端合同级职责：仓储补录来源原因、货抵动态多明细、调整/回款事务一致性、团队数据范围。
