# 阶段 3 角色权限超管分配收口记录

## 结论

- 本轮修正的核心不是“让业务员看懂更多”，而是反过来：业务员默认不应看到库存流水、生产成本、角色权限等敏感能力。
- 角色权限已经从“内置角色常量硬放行”收束为“数据库运行时策略为准”，超级管理员可以通过角色权限管理入口分配或收回敏感权限。
- 前端隐藏只作为体验辅助，真正的准入由后端 `authorizePermission` 和 Casbin/DB 权限表判定。

## 已修正的问题

| 问题 | 修正 |
| --- | --- |
| 内置角色权限由常量直接放行，DB 收权后仍可能被放行 | Casbin 正常运行时只读取 `auth_role_permissions`，常量仅作首启兜底 |
| 内置角色不可编辑，超级管理员无法调整 sales/warehouse/finance 等基础角色权限 | `updateRole` 支持系统角色权限和数据范围调整，角色编码和启用状态仍锁定 |
| 角色管理复用 `team.write`，团队成员管理和权限治理边界不够清楚 | 新增 `authorization.roles.manage`，角色权限分配独立于普通团队成员管理 |
| 库存流水只用 `warehouse.read` 控制，粒度太粗 | 新增 `warehouse.ledger.read`，库存流水接口独立授权 |
| 生产成本台账只用 `production.read` 控制，成本数据过宽 | 新增 `production.cost.read`，批次成本接口独立授权 |
| 角色默认策略每次 seed 会覆盖人工调整 | 系统角色只在无权限时初始化默认权限，后续变更通过一次性策略迁移补齐，不覆盖超管后续调整 |

## 权限边界

| 权限点 | 默认拥有角色 | 默认无权角色 | 用途 |
| --- | --- | --- | --- |
| `authorization.roles.manage` | admin | manager / sales / warehouse / finance | 分配角色和权限点 |
| `warehouse.ledger.read` | admin / manager / warehouse | sales / finance | 查看库存凭证、调拨记录、生产耗用、出入库追溯 |
| `production.cost.read` | admin / manager / finance | sales / warehouse | 查看批次成本台账和生产成本核算 |

## 固定反偏规则

- 以后新增敏感功能，不能只挂到大权限如 `warehouse.read`、`production.read`、`finance.read`。
- 必须先判断是否需要独立权限点，再由超级管理员分配。
- 角色权限变更必须有 API 回读、拒绝态、授权态、收回态四段证据。
- 前端菜单隐藏不能替代后端 403。
- 阶段 3 主闸门必须由主控重新跑，不能只信子任务报告。

## 2026-04-23 补充：团队成员分配角色防提权

- `team.write` 只代表普通团队成员资料维护能力，不等于角色分配权。
- 新建团队成员时，如果目标角色不是默认 `sales`，必须额外具备 `authorization.roles.manage`。
- 修改团队成员时，只改邮箱、头像、启停等资料仍由 `team.write` 控制；只要发生角色变更，必须额外具备 `authorization.roles.manage`。
- `/api/auth/register` 作为受保护的团队建号桥接入口同样遵守该规则，避免绕过 `/api/team`。
- 新增审计脚本：`scripts/role-assignment-escalation-audit-v1.cjs`。
- 新增 npm 闸门：`npm run audit:permissions:role-assignment`。
- 已接入阶段 3 主闸门：`role-assignment-escalation-chain`。

### 该补充要防住的真实业务风险

- 未来超级管理员可能创建一个“人事/团队资料管理员”角色，只给 `team.write`，让他维护头像、邮箱、账号启停。
- 如果不加这条边界，该角色可能在创建或修改用户时把别人提升为 `admin`、`finance`、`warehouse` 或任意自定义高权角色。
- 这属于权限提权漏洞，不是 UI 问题，必须由后端强制拒绝，并由 API 审计证明。
