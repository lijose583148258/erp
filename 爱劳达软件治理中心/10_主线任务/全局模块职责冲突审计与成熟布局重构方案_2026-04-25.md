# 全局模块职责冲突审计与成熟布局重构方案

日期：2026-04-25

## 0. 本轮结论

当前系统不是单纯“功能不够”，而是部分页面把多个业务对象和多个用户任务塞在同一个视觉区域里，导致用户一眼看不出：

- 我现在是在找记录、建记录、改记录，还是审批/过账？
- 我填完这块以后会生成什么业务对象？
- 生成后去哪里回读、核对、冲销、审计？
- 哪些是主数据，哪些是明细行，哪些是执行流水？

这就是 BOM 管理与 BOM 明细冲突背后的同类问题。后续不能继续靠页面内补丁堆功能，必须按“业务对象 + 用户任务 + 状态流”重排。

## 1. 成熟商业软件调研基准

### SAP Fiori / S/4HANA

- List Report 用来筛选、查看、处理同一种业务对象的列表。
- Object Page 用来查看、编辑、创建一个具体业务对象。
- 多内容布局可以展示多个业务对象，但创建对象应回到对象页，避免一个列表页里同时塞太多创建逻辑。
- 参考：SAP Fiori List Report and Object Page、List Report Content Area。

### Microsoft Dynamics 365 Finance & Operations

- Workspace 应围绕一个重要业务活动，而不是一个大而全的部门菜单。
- 工作台只放常用动作，动作必须服务于整个工作台，不应该让局部区域互相抢动作。
- 过滤器数量要克制，最多 0-5 个，主要内容纵向分区、可折叠。
- 参考：Dynamics 365 Workspace form pattern。

### Salesforce Lightning

- List Layout 适合大数据列表、筛选、排序、批量动作。
- Record Layout 适合单条记录详情，常见结构是页头、主内容、侧栏。
- Master-Detail 适合一边选队列，一边看/编辑详情。
- 参考：Salesforce Lightning Design System Layout Guidelines。

### Odoo / ERPNext / Dynamics MRP 对 BOM 的共同启发

- BOM/Formula 是一个业务对象。
- Header/主数据定义产品、版本、单位、生效期、状态。
- Component/Formula Lines 只定义组成行和用量。
- Operations、By-products、Quality、Costing 是对象下的分区，不应和组件行混成一个表单。

## 2. 爱劳达全局布局原则

### 页面只允许四类

| 页面类型 | 用途 | 允许内容 | 不允许内容 |
|---|---|---|---|
| 工作台 Workspace | 一个业务活动总览 | KPI、今日任务、常用入口、异常队列 | 大量编辑表单、规则配置大表 |
| 列表页 List | 找对象、筛选、批量操作 | 一个主对象的表格、搜索、状态视图 | 多个不同对象混表、复杂新建表单 |
| 对象页 Object | 看/改一个对象 | 主数据、明细、状态、相关记录、审计 | 无关对象的新建入口 |
| 执行动作页/弹窗 Action | 审批、过账、签收、冲销、完工 | 本次动作字段、影响预览、确认按钮 | 主数据维护、历史大列表 |

### 同一区域禁止抢职责

- `列表区` 只能找和选择记录，不能同时承担复杂编辑。
- `主数据区` 只定义对象身份，不放流水动作。
- `明细区` 只维护对象的子行，不放全局规则。
- `动作区` 只做一次明确动作，如过账、签收、冲销、完工。
- `审计区` 只回看，不能编辑。

### 用户路径固定成 5 步

1. 找对象：列表/搜索/过滤。
2. 看对象：对象页或右侧详情。
3. 改对象：编辑模式或新建弹窗。
4. 执行动作：独立动作弹窗，显示影响预览。
5. 回读核对：保存后自动定位到对象详情或流水。

## 3. 当前职责冲突风险矩阵

| 优先级 | 模块 | 当前冲突 | 用户困惑 | 目标形态 |
|---|---|---|---|---|
| P0 | 生产 | 配方/BOM、工单、批次、质检、调账堆在同一工作台 | 不知道是在建配方、排工单、完工扣料还是调库存 | 顶层拆为 `配方库 / 工单执行 / 批次追踪 / 生产调整` 四个任务标签 |
| P0 | 货抵支付 | 新建协议、协议列表、执行批次、审批过账、冲销流水同屏 | 协议总额和本次批次容易混淆 | 改为 `协议库 -> 协议详情 -> 执行批次 -> 过账流水` |
| P0 | 仓储 | 仓库主数据、库存台账、库存流水、手动入库、调拨弹窗同模块 | 不清楚是维护仓库、查库存、还是做库存交易 | 保留工作台，但顶层任务改成 `仓库结构 / 库存台账 / 入库登记 / 调拨 / 流水审计` |
| P1 | 回款中心 | 回款、承诺、争议、追款拦截、原则说明同页过长 | 用户不知道先处理哪一类异常 | 改为队列优先：`今日应收任务` 主视图，承诺/争议/拦截作为同一对象的分视图 |
| P1 | 应收调整 | 创建调整、过账、冲销、台账在一个面板 | 容易和“真实回款”混淆 | 改成 `应收调整凭证` 独立对象页，强调不是回款 |
| P1 | 收发货差异 | 差异队列和容差规则同页 | 处理差异和维护规则是两种角色 | 队列页与规则配置页分离，规则归治理/设置 |
| P1 | 采购 | 供应商主数据、采购订单、收货批次在同模块 | 基本合理，但收货抽屉需要更像动作页 | 供应商和采购订单继续分标签，收货作为订单动作弹窗 |
| P1 | 发货物流 | OCR、物流看板、物流列表、签收批次、资产流同页 | OCR导入、物流跟踪、签收动作、资产流边界不清 | 拆为 `物流列表 / 签收动作 / OCR导入 / 资产流` |
| P2 | CRM | 列表、客户详情、池归属、AI洞察、联系人地址同抽屉 | 详情抽屉信息多但对象边界还算清楚 | 详情页分为 `主数据 / 地址 / 联系人 / 归属池 / 审计`，AI只做侧栏建议 |
| P2 | 销售订单 | 列表、编辑弹窗、回款弹窗、历史、承诺/争议入口同页 | 功能多但以订单对象为中心，风险可控 | 保留列表+弹窗，增强对象详情页 |
| P2 | 团队权限 | 用户管理和角色权限靠面板组织 | 超管能用，普通人不应看到复杂权限 | 保留给管理员，普通角色隐藏 |

## 4. 第一阶段重排顺序

### 第一包：生产

目标：把 BOM 问题的同类根因彻底处理。

- 顶层改为四个标签：`配方库`、`工单执行`、`批次追踪`、`生产调整`。
- `配方库` 内部按对象页组织：`已保存版本列表`、`BOM对象主数据`、`原料明细`、`工艺/质检/备注`、`版本回读`。
- `工单执行` 内部只处理工单创建、工序、完工扣料。
- `批次追踪` 内部只看批次和追溯。
- `生产调整` 只做生产域调账，不混入仓储主调拨。

### 第二包：货抵支付

目标：防止协议与执行批次混淆。

- 协议是主对象。
- 批次是协议下的执行流水。
- 过账/冲销是批次动作。
- 列表只负责选择协议，不直接编辑批次。

### 第三包：仓储

目标：把仓库主数据和库存交易分开。

- 仓库结构：仓库/库位维护。
- 库存台账：查库存余额。
- 入库登记：新增库存交易。
- 调拨：从库存行发起动作。
- 流水审计：只读，不编辑。

## 5. 后续页面设计排布模板

### 模板 A：对象库 + 对象详情

适合：客户、供应商、BOM、协议、合同、订单。

布局：

- 顶部：模块名 + 一句话说明 + 主动作按钮。
- 左侧或上方：对象列表、搜索、状态筛选。
- 主体：对象详情分区。
- 底部或右侧：审计/历史/相关流水。

### 模板 B：任务队列 + 动作抽屉

适合：回款异常、差异处理、审批、签收、完工。

布局：

- 顶部：待办数量、风险级别、筛选。
- 主体：任务队列。
- 点击行：右侧动作抽屉。
- 动作抽屉：影响预览 + 必填原因 + 确认按钮。

### 模板 C：交易录入 + 回读台账

适合：采购订单、入库、发货签收、应收调整、货抵批次。

布局：

- 左/上：简版新建表单。
- 中：明细表格或 Excel 网格。
- 右/下：保存后回读台账。
- 保存后必须自动定位刚创建记录。

### 模板 D：规则配置

适合：权限、容差、风控规则。

布局：

- 仅管理员可见。
- 不和业务队列同屏抢视觉。
- 规则页必须显示“规则会影响哪些业务动作”。

## 6. 验收制度

每个重排包必须通过：

- 视觉职责检查：同一区域不出现两个主动作。
- 输入结果检查：每个输入区写明“保存后生成什么”。
- 回读检查：保存后自动定位新记录。
- 角色检查：不该看到的角色看不到动作。
- 乱码三步法：源码 UTF-8 正常、报告显示层不误判。
- E 盘纯净版验收：`http://127.0.0.1:5001/` 跑通后才算完成。

## 8. 决策

从下一包开始，优先重排 `生产` 和 `货抵支付`。这两个模块最容易因为“主对象、明细行、执行流水、过账动作”混在一起造成真实业务误录。

不再用“页面里补一块卡片”的方式继续扩功能。新增功能必须先归入四类页面之一：工作台、列表页、对象页、动作页。

## 中国中小企业高频软件调研补充

### 为什么必须补这一层

前一版调研主要参考 SAP Fiori、Microsoft Dynamics、Odoo、Salesforce，这些适合提供企业软件的架构纪律，但不完全适合直接照搬到爱劳达。爱劳达的目标是本地稳定运行、老板和业务人员能快速上手、后续再平滑迁移服务器，所以必须补充中国中小企业常见软件的使用习惯。

### 国内参考对象

| 软件 | 参考价值 | 爱劳达吸收方式 |
| --- | --- | --- |
| 金蝶云星辰 / KIS / 精斗云 | 小微企业常用的业财税、进销存、库存、销售、生产协同 | 财务、采购、销售、仓库要做成业务单据自动流转到财务口径，避免用户重复录入 |
| 畅捷通 T+Cloud | 中小企业云 ERP，强调库存、生产、经营看板、业财融合 | 页面要保留老板看板和财务联动，不做只有一线录入能看懂的页面 |
| 速达 3000 / 5000 / ERP | 进销存、POS、财务、生产、CRM 一体化，偏开单式操作 | 销售、采购、仓储、收款应坚持“开单 + 明细表格 + 保存回读 + 台账”的低学习成本模式 |
| 管家婆 / 任我行 | 中小微企业进销存、财务、生产加工、移动开单习惯明显 | 界面必须减少解释成本，入口名称用业务语言，不用过多技术化或管理学术语 |

### 对爱劳达的新增设计准则

1. 大型 ERP 负责约束结构：列表、对象、动作、台账、审批必须分开。
2. 国内中小企业 ERP 负责约束手感：开单要快，表格要直观，保存后必须立刻回读。
3. 任何页面只要用户第一眼看不出“我现在应该填什么”，就算 UI 没崩也判为交互失败。
4. 单据型模块优先采用“单据头 + 明细行表格 + 底部保存 + 保存后台账回读”。
5. 主数据型模块优先采用“列表搜索 + 简版新建 + 详情分区 + 高级字段折叠”。
6. 动作型模块必须独立成按钮、抽屉或独立页，不要混在主数据编辑区。
7. 台账型模块默认只读，允许筛选、导出、查看来源，不允许在台账表格里偷偷改业务主数据。
8. 老板/经理视角不看录入细节，默认看经营看板、异常、待审批、资金和库存风险。

### 后续页面重排的国内化判断

| 模块 | 应参考的国内软件习惯 | 后续调整方向 |
| --- | --- | --- |
| 销售订单 | 速达 / 管家婆开单 | 单据头、客户联想、商品明细、收款状态、发货状态清晰分离 |
| 采购 | 金蝶 / 畅捷通采购入库链 | 供应商主数据、采购订单、收货、差异、应付不要抢一个输入区 |
| 回款中心 | 金蝶 / 管家婆往来账 | 回款像一张收款单，支持一单多次回款，核销后台账只读 |
| 仓储 | 速达 / 管家婆库存 | 库位、余额、调拨、盘点、流水分开；库存余额不能直接等同库存流水 |
| 生产 BOM | 畅捷通 / 速达生产 | BOM 是配方主数据，工单是执行单，完工扣料是库存动作，三者不能混在一个录入区 |
| 货抵支付 | 往来账 + 结算单习惯 | 协议总额、分批抵扣、审批过账、冲销台账拆开 |

### 固定结论

爱劳达不应做成 SAP/Odoo 那种重型复杂系统，也不应做成只有漂亮卡片的轻壳。正确方向是：

- 架构像成熟 ERP：对象清楚、状态清楚、台账可追溯。
- 操作像国内进销存：开单快、表格清楚、保存回读明确。
- 管理像老板看板：异常、资金、库存、订单、生产进度一眼可见。
- 后续每次改 UI，都必须同时问两个问题：这个结构是否符合成熟 ERP？这个输入方式是否符合中国中小企业真实使用习惯？

## 2026-04-25 第四包落地记录：人本交互组件化
