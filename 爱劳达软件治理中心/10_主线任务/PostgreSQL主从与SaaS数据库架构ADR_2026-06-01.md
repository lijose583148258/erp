# PostgreSQL 主从与 SaaS 数据库架构 ADR

日期：2026-06-01

## 状态

采纳，作为云 SaaS 与私有化服务器版的目标数据库架构。SQLite 继续仅用于本地单机版。

## 背景

当前 SQLite 单机文件适合本地运行包和低并发试点，但不适合云 SaaS 的并发写入、读写扩展、备份恢复、监控和多租户运营分析。

## 决策

目标架构采用 PostgreSQL：

```text
应用层
  ├─ 写入 / 事务 / 库存扣减 / 审批流 / 财务入账  -> PostgreSQL Primary
  ├─ 列表 / 报表 / 看板 / 历史查询              -> PostgreSQL Read Replica
  └─ 灾备 / 恢复                               -> Standby + WAL 归档 + 定时备份
```

关键边界：

- Primary 是唯一写入口。
- Replica 只承载可接受复制延迟的读请求。
- Standby 不等同于备份，必须另有备份和恢复演练。
- SaaS 核心表默认使用 `tenant_id` 逻辑隔离。
- 大客户可升级为独立 schema 或独立数据库的混合隔离模式。

## 实施规则

### 写库规则

以下请求必须走 Primary：

- 登录态变更、用户权限变更。
- 新增、修改、删除业务单据。
- 订单提交、审批、驳回、撤回。
- 库存入库、出库、调拨、盘点、成本流水。
- 财务收款、核销、调整、应收应付变更。
- 任何事务内的读后写。

### 读库规则

以下请求可走 Replica：

- Dashboard 统计。
- 列表分页查询。
- 历史审计查询。
- BI 宽表查询。
- 不影响当前操作确认的报表。

### 写后读规则

用户提交成功后的短时间内，不允许立即从 Replica 读取关键确认数据。

策略：

- 事务返回的对象直接用于页面确认。
- 提交后的详情页默认读 Primary。
- 用户会话可在短窗口内粘滞到 Primary。
- 报表类刷新可以继续读 Replica，并明确接受延迟。

### 连接池规则

Node 后端必须控制数据库连接数。

要求：

- SaaS 部署引入 PgBouncer 或等价连接池策略。
- Primary 与 Replica 使用独立连接配置。
- 健康检查必须区分主库、读库、迁移状态。

### 备份恢复规则

要求：

- 开启 WAL 归档。
- 配置定时全量 / 增量备份。
- 明确 RPO 与 RTO。
- 每个正式发布周期至少做一次恢复演练。
- 恢复演练结果进入发布记录。

## 多租户规则

默认逻辑隔离：

- 核心业务表包含 `tenant_id`。
- 查询层必须注入租户上下文。
- 后台平台接口需要显式超级权限。
- 测试必须覆盖跨租户越权读取和写入。

混合隔离：

- 普通租户共享 PostgreSQL。
- 大客户可独立 schema 或独立数据库。
- 平台分析通过事件表、宽表或同步任务统一聚合。

## 首批落地包

### DB-P0-01 配置分线

- 本地版：SQLite 默认。
- 私有化版：PostgreSQL 默认。
- 云 SaaS：PostgreSQL Primary + Replica 配置必须存在。

验收：启动时根据部署形态校验必填环境变量。

### DB-P0-02 查询路由

- 新增数据库访问层读写路由。
- 写请求强制 Primary。
- 报表查询可指定 Replica。

验收：核心写链路不得连接 Replica。

### DB-P0-03 写后读保护

- 提交单据后的详情确认读 Primary。
- 关键业务确认不依赖 Replica 延迟。

验收：模拟 Replica 延迟时，订单、库存、审批确认仍然正确。

### DB-P0-04 备份恢复演练

- 配置 WAL 与定时备份。
- 建立恢复脚本。
- 记录恢复耗时与数据完整性校验。

验收：能从备份恢复到新库，并通过核心链路读写校验。

## 暂不做

- 不在 P0 阶段直接拆微服务。
- 不在未完成租户模型前扩大 SaaS 客户规模。
- 不把 Replica 当成强一致读取来源。
- 不把 Standby 当成唯一备份策略。
