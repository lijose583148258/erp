## 拆分原则

- 先补证据，再拆文件。
- 先拆纯函数、formatter、validator，再拆状态机。
- 金额、库存、权限、客户名展平、回款回读不得无测试拆分。
- 每次拆分后主控必须重跑相关 API/浏览器闭环，不能只信子任务报告。
- 拆分不是为了变漂亮，而是为了减少“改一点又丢 CSS、乱码、入口错”的复发。

## 2026-04-23 Phase 3 浏览器验收回归修复记录

范围：
- `backend/src/controllers/rma.controller.ts`
- `services/rma.service.ts`
- `scripts/samples-rma-browser-audit-v1.cjs`
- `scripts/phase3-readiness-audit-v1.cjs`

现象：
- `npm run verify:phase3` 核心链路通过，29/29 PASS。
- `npm run verify:phase3:browser` 首轮失败在 `samples-rma-browser-chain`，失败信息为 `open-and-verify-rma-page exceeded 20000ms`。
- API 直接查询确认新建 RMA 记录存在，未发生数据丢失。

三步法判断：
- 翻译现象：浏览器打开 RMA 页面后没有在默认可见列表里看到刚刚创建的 RMA 原因文本。
- 判断层级：不是源码乱码，不是写入失败，而是列表排序与分页可见性问题。
- 修复层级：只修 RMA 列表读取口径，不重写页面，不改业务状态机。

根因：
- 运行库里有历史版本写入的混合 `createdAt` 字符串格式。
- 后端原来使用 `createdAt desc` 排序，导致新写入的 RMA 不稳定地排到第一页之后。
- 前端表格默认首屏只显示 10 行，浏览器验收等待新 RMA 文本时超时。

处理：
- 后端 RMA 列表改为 `id desc`，以自增主键作为运行库兼容场景下的最新记录排序依据。
- 前端 RMA 服务读取改为 `/rma?pageSize=100`，降低因默认分页导致验收或人工回读漏看的概率。
- 未删除历史数据，未改变 RMA 创建、审批、状态流转和写入结构。

验证证据：
- `npm run build:backend` PASS。
- `npm run build` PASS，生产 CSS/JS 正常生成。
- `node scripts/effective-source-mojibake-gate-v1.cjs` PASS，530 个有效源码文件 0 findings。
- `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-stable-v2.ps1` PASS，稳定入口为 `http://127.0.0.1:5001`，运行库为 `D:\AilaoDaRuntime\stable.db`。
- RMA API 回读：默认、`pageSize=20`、`pageSize=100` 三种请求均返回最新 RMA id 55、54 位于第 1、2 位。
- `npm run check:runtime` PASS，首页、manifest、service worker、核心 JS/CSS 资源均 200。
- `npm run audit:ui:samples-rma` PASS，报告路径：`output/playwright/samples-rma-browser-audit-report-v1.json`。
- `npm run verify:phase3:browser` PASS，36/36 PASS，0 failed，0 stuck，报告路径：`output/audit/phase3-readiness-audit-v1.json` 和 `output/audit/phase3-readiness-audit-v1.md`。

反思：
- 这类问题不能只看 API 200，因为 API 写入成功但浏览器首屏仍可能看不到新数据。
- 对历史运行库必须考虑旧数据格式、排序稳定性和分页可见性。
- 以后凡是“新建后刷新回读”的浏览器验收，必须同时确认：写入成功、默认排序正确、第一页可见、刷新后仍可见。
