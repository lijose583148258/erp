# 启动验收与打包新鲜度治理

日期：2026-04-23

## 目标

把容易导致“假绿”的启动、验收、打包脚本收束成更明确的治理链，避免以下问题反复出现：

- 名称叫 dual-port，但实际在 3000 未运行时降级成 5001 单端检查。
- 名称叫 health/timebox，但实际会 build 后端并创建数据库备份。
- 打包 EXE/稳定包时直接复制已有 dist，可能把旧页面、旧 CSS、旧接口产物打进去。

## 本次改动

### 1. 双端审计语义拆开

- `audit:stable-api`：只验证稳定运行端 `127.0.0.1:5001` 的 API 链路。
- `audit:dual-port`：强制要求 `localhost:3000` 可用，再做 3000 与 5001 的双端对比。
- `test:acceptance:dual-port`：保留为真正双端对比，不再允许静默降级成单端。

### 2. 健康检查改为诚实命名

- `check:timebox` 保留兼容。
- 新增 `check:preflight:side-effect`，明确这是带副作用的预检。
- 脚本启动时会提示：它会 build 后端并创建数据库备份；纯运行检查应使用 `npm run check:runtime`。

### 3. 打包前增加新鲜度闸门

- `scripts/package-stable.ps1` 新增 `-CheckOnly`。
- 新增 `audit:package:freshness`，只检查不复制、不改名、不删除。
- 打包前必须确认：
  - `dist/index.html` 存在。
  - `dist/assets/index-*.js` 存在。
  - `dist/assets/index-*.css` 存在。
  - `backend/dist/server.js` 存在。
  - 前端源码不能比前端 dist 更新。
  - 后端源码不能比后端 dist 更新。

### 4. Phase 3 总验收纳入新鲜度闸门

- `verify:phase3` 的静态脚本检查现在要求存在 `audit:package:freshness`。
- `verify:phase3` 的运行步骤现在包含 `package-freshness-gate`。
- 这样后续即使没有单独执行打包审计，Phase 3 也会阻止旧前端/旧后端产物被误认为可发布。

## 乱码三步法记录

### 现象

PowerShell 直接读取 `scripts/phase3-readiness-audit-v1.cjs` 时，终端输出曾显示类似乱码的报告文案。

### 判断

用 Node 按 UTF-8 读取源码后，实际内容为正常中文，例如：

- `历史归档`
- `文档归档`
- `.env.production.example 缺失`
- `index.html 存在外部 CDN 或 Google Fonts 依赖`
- `runtime.ts 未显式支持`

### 处理

这是终端显示层问题，不是源码损坏，因此没有重写该文件的中文文案，只补充 Phase 3 新鲜度闸门。

## 使用原则

- 判断系统是否正在稳定运行：先跑 `npm run check:runtime`。
- 判断稳定 API 是否可用：跑 `npm run audit:stable-api`。
- 判断 3000 与 5001 是否一致：必须启动 3000，再跑 `npm run audit:dual-port`。
- 判断是否可以打包：跑 `npm run audit:package:freshness`。
- 需要完整带副作用预检时，才跑 `npm run check:preflight:side-effect`。

## 反思

这一包没有动业务功能，方向没有偏到“重写系统”。它解决的是过去反复出现的“脚本看起来绿，但实际语义不清”的问题。

后续所有治理脚本都要遵守同一规则：

- 脚本名必须描述真实行为。
- 报告必须区分单端、双端、浏览器、API、打包、备份。
- 不能把降级结果伪装成完整验收。
- 不能把旧产物复制进稳定包。
- 不能为了通过检查去删除历史文件或用户数据。
