# ERP 可信体系总蓝图与优化重构判断准则（2026-06-02）

## 目的

这份文档是后续产品、研发、测试、架构评审的总入口。三份负面反馈清单已经说明：贸易型 ERP、生产型 ERP、货物兑换系统真正被客户否定的原因，不是“功能不够多”，而是数据不可信、单据不闭环、库存成本对不上、权限职责不清、岗位操作低效、报表不能追溯。

后续所有优化和重构，都按本文判断：

- 能在现有结构内补证据、补约束、补状态、补体验的，走优化。
- 如果当前模型无法表达真实业务、无法保证一致性、无法追溯责任，走重构。
- 如果只是为了页面更好看、模块更多、指标更多，但不提升业务可信度，降级或暂缓。

## 总原则

1. 每一笔业务必须能追溯。
2. 每一次库存变化必须有凭证。
3. 每一次财务变化必须有依据。
4. 每一次审批必须有责任人。
5. 每一次冲回必须能反向闭环。
6. 每一个报表数字必须能点回原始单据。
7. 任何“只登记、未过账”的动作不得命名为“已过账”。
8. 任何“看板/BI/预警”不得脱离真实单据和数据范围。
9. 任何“自动化审批”在未接真实领域服务前，只能称为待办/提醒，不能称为业务闭环。

## 六条主线

### 1. 数据可信

目标：客户、供应商、物料、批次、库存、订单、工单、回款这些源头数据必须可信，否则后续所有审批、库存、成本、BI 都不可信。

内部注意点：

- 物料不能长期依赖 `productName + batchNo` 自由文本，应逐步升级到物料编码、规格、单位、换算率。
- 客户和供应商导入前必须做重复检测和字段质量预检。
- 批次必须贯穿采购、生产、仓库、发货、签收、货物兑换、RMA。
- 库存余额必须能由库存流水反推。
- 导入功能必须提供预检报告、失败原因和回读证据。

需要优化：

- 表单校验、导入错误提示、重复检测、字段质量提示。
- 客户/供应商/物料列表的搜索和筛选。
- 批次字段的必填策略和错误提示。

需要重构：

- 多个模块各自用自由文本记录物料，导致无法跨模块对账。
- 库存余额不是由流水统一计算或校验。
- 批次字段只作为备注，无法建立真实追溯链。

### 2. 单据闭环

目标：关键业务不是“有页面、有表、有状态”，而是能完整完成业务动作，并能反向冲回。

必须打穿的闭环：

- 销售订单：订单 -> 发货 -> 签收 -> 回款 -> 售后。
- 采购订单：采购 -> 收货 -> 差异 -> 入库 -> 应付/扣款。
- 货物兑换：申请 -> 估值 -> 收货/发货 -> 质检 -> 财务过账 -> 冲回。
- RMA：申请 -> 审核 -> 退货入库/换货出库/应收调整 -> 结案。
- 生产工单：BOM 快照 -> 领料 -> 报工 -> 完工 -> 成本 -> 入库。

内部注意点：

- 单据状态必须和真实业务动作对应。
- 状态名称必须区分“登记、审批、过账、结案”。
- 关键动作完成后必须生成证据页。
- 冲回不能直接改历史流水，必须产生反向凭证。
- 同一单据重复提交必须有幂等控制。

需要优化：

- 在现有单据上补状态解释、下一步动作、审计日志、错误提示。
- 给关键动作补回读证据，例如库存影响、应收影响、批次影响。
- 补重复提交保护和冲回原因。

需要重构：

- 当前单据模型无法表达真实业务阶段。
- 审批通过后没有调用领域服务，只改 workflow 表。
- 一个状态同时代表“已审核、已收货、已过账、已结案”。
- 业务动作横跨多个模块但没有事务边界。

### 3. 库存与成本可信

目标：贸易型 ERP 要库存可信；生产型 ERP 还要成本可信。库存和成本不可信，系统会被直接否定。

内部注意点：

- 所有库存变化必须来自库存凭证/流水。
- 手工调整必须有来源单号和原因。
- 换入/退回/质检未通过货物不得进入可用库存。
- 工单完工必须校验耗料、成品入库、批次余额、成本台账。
- 标准成本、实际成本、差异成本必须分开。
- 货物兑换必须同时影响库存、应收/应付、成本和审计。

需要优化：

- 库存可信面板。
- 批次余额对账。
- 手工调整原因码。
- 完工后对账摘要。
- 货物兑换过账证据页。

需要重构：

- 业务直接改库存余额，没有库存流水。
- 工单完工只改状态，不写耗料、入库、成本。
- 货物兑换只抵应收或只改库存，没有双落账。
- productBatch、stockBalance、stockMovement 多套口径无法对齐。

### 4. 权限与审批治理

目标：先把高风险审批点做扎实，不急着做“大而全工作流引擎”。

优先审批点：

- 货物兑换估值。
- 货物兑换过账/冲回。
- RMA 结案。
- 库存调整。
- BOM 变更。
- 工单异常完工。
- 大额应收调整。
- 角色权限变更。

职责分离原则：

- 销售可发起，不能最终财务过账。
- 仓库确认实物，不能确认抵扣金额。
- 财务确认应收/应付影响，不能改实物数量。
- 质检确认可用状态，不能改财务金额。
- 管理员也必须留审计，不应成为无痕后门。

需要优化：

- 细化权限点。
- 高风险操作二次确认。
- 角色变更和改密审计。
- 审批意见和附件。

需要重构：

- 权限只按角色粗粒度判断，无法限制关键动作。
- 业务权限和数据范围完全脱节。
- 角色权限可被非治理角色批量覆盖。
- 审批和真实业务状态没有连接。

### 5. 岗位化体验

目标：真实用户不是按模块工作，而是按岗位任务工作。系统必须降低一线操作成本。

岗位入口：

- 销售：客户、订单、回款登记、货抵申请、售后申请。
- 财务：回款核销、应收调整、货抵过账、账龄、异常对账。
- 仓库：收货、入库、发货、签收、调拨、盘点、批次追溯。
- 采购：供应商、采购单、收货差异、供应商换货。
- 车间：工单、领料、报工、完工、异常。
- 质检：待检批次、不合格、让步接收、冻结/放行。
- 管理层：经营总览、审批、风险、异常处理。

内部注意点：

- 高频作业页面优先密度和可读性，不追求展示型美观。
- 移动端/PDA/平板必须避免 hover 依赖。
- 表格操作必须常显或有明确更多菜单。
- 导入失败、保存失败、状态错误必须告诉用户下一步怎么做。
- 空态不能只写“暂无数据”，要说明下一步。

需要优化：

- 页面密度、移动布局、错误提示、空态、导入反馈。
- 工作台“今日待办”和“下一步动作”。
- 扫码、快捷键、批量录入。

需要重构：

- 一个页面塞入多个岗位的复杂动作，导致所有人都难用。
- 关键作业流程必须在多个无关页面跳转才能完成。
- 业务入口按模块堆叠，无法支持岗位任务。

### 6. 报表和 BI

目标：BI 必须建立在可信数据和可信读模型上。没有可信流水，BI 越漂亮风险越大。

正确顺序：

1. 可信流水。
2. 可信读模型。
3. 报表口径。
4. 经营分析。
5. 预警和主动推送。

BI 必须带：

- 数据来源。
- 统计口径。
- 更新时间。
- 数据范围。
- 异常数据提示。
- 可 drill-down 到原始单据。

需要优化：

- 指标口径说明。
- 点击指标到明细。
- 预警生成待办。
- 报表更新时间。

需要重构：

- 看板直接全表统计，绕过角色和数据范围。
- 指标无法追溯到原始单据。
- BI 页面使用演示数据冒充真实数据。
- 预警不能关闭、不能处理、不能审计。

## 关键模块蓝图

### 货物兑换系统

必须具备：

- 兑换类型：客户换货、供应商换货、以货抵应收、以货抵应付、内部调换。
- 估值依据：市场价、合同价、历史成交价、附件、估值人。
- 库存状态：待检、冻结、可用、报废、返修、让步接收。
- 财务影响：应收、应付、回款抵扣、成本、差额、税务附件。
- 反向冲回：原单和反向凭证一一对应。
- 批次追溯：换出批次、换入批次、仓库、库位、数量。

判断：

- 如果只是补文案、补附件、补审批意见，走优化。
- 如果过账无法同时写库存、应收/应付、成本和审计，走重构。

### 生产系统

必须具备：

- BOM 版本快照。
- ECO 工程变更。
- 工单状态分支。
- 标准耗料和实际耗料。
- 超耗/少耗原因。
- 完工入库和成本台账。
- 质检和冻结库存。
- 批次谱系。

判断：

- 如果当前工单只缺少状态提示、字段校验、移动端入口，走优化。
- 如果工单不锁 BOM 版本，完工不写成本/库存，耗料无法追溯，走重构。

### 贸易系统

必须具备：

- 客户/供应商主数据治理。
- 订单、发货、签收、回款、售后闭环。
- 采购、收货、差异、入库、应付/扣款闭环。
- 应收、回款、货抵、调账统一口径。
- 库存可信面板。

判断：

- 如果只是页面密度、错误提示、导入预检，走优化。
- 如果订单、发货、回款、售后之间没有统一状态和回读证据，走重构。

## 优化 vs 重构判断表

| 评审问题 | 优化 | 重构 |
|---|---|---|
| 是否已有正确领域模型？ | 有，只缺字段/约束/提示 | 没有，真实业务无法表达 |
| 是否已有事务边界？ | 有，只需补校验和证据 | 没有，多模块动作无法一致 |
| 是否能追溯原始单据？ | 能，只需补链接和页面 | 不能，数据关系缺失 |
| 是否能冲回？ | 能，只需补原因/审批 | 不能，历史记录被直接覆盖 |
| 是否只是 UI 难用？ | 优化页面和交互 | 若流程本身错乱，重构 |
| 是否只是文案误导？ | 改文案和状态解释 | 如果状态本身混用，重构 |
| 是否影响库存/财务/成本？ | 小心优化，加测试 | 优先重构事务和凭证 |
| 是否跨多个核心模块？ | 先做证据页和对账 | 如果跨模块无统一模型，重构 |

## 每次需求评审必须回答的问题

1. 这个需求会不会改变库存？
2. 会不会改变应收/应付/成本？
3. 会不会改变批次状态？
4. 会不会影响订单、采购、工单、RMA、货抵等主单据状态？
5. 是否需要审批？
6. 是否需要冲回？
7. 是否有审计日志？
8. 是否能在页面上看到过账证据？
9. 是否能按角色和数据范围隔离？
10. 是否能被报表追溯？

如果 1-4 任意一个为“是”，不能只做前端页面，必须进入后端闭环设计。

如果 5-8 任意一个缺失，高风险功能不得标记为完成。

如果 9-10 缺失，不得进入商业化交付。

## 推荐执行路线

### 第一阶段：可信底座

- 主数据治理。
- 库存流水统一。
- 批次追溯。
- 审计日志增强。
- 关键错误提示和导入预检。

### 第二阶段：关键闭环

- 货物兑换闭环。
- RMA/差异闭环。
- 生产工单闭环。
- 采购收货闭环。

### 第三阶段：权限审批

- 高风险审批点。
- 职责分离。
- 冲回机制。
- 过账证据页。

### 第四阶段：岗位体验

- 销售工作台。
- 仓库工作台。
- 财务工作台。
- 采购工作台。
- 车间/质检工作台。

### 第五阶段：经营分析

- 库存可信看板。
- 应收可信看板。
- 生产成本看板。
- 货物兑换对账看板。
- 异常预警和处理闭环。

## 禁止事项

1. 禁止用演示指标冒充真实经营数据。
2. 禁止把“登记”命名为“过账”。
3. 禁止无来源调整库存。
4. 禁止用备注替代凭证字段。
5. 禁止审批只更新 workflow 表，不回写业务单据。
6. 禁止高风险动作无审计。
7. 禁止旧 token 在改密、禁用、降权后继续有效。
8. 禁止触屏页面依赖 hover。
9. 禁止关键报表无口径说明。
10. 禁止为了新增模块破坏已有闭环。

## 结论

这套系统后续判断“优化还是重构”，核心不是看代码量，而是看可信度：

- 数据可信，流程正确，只是体验和证据不足，优化。
- 数据关系缺失，状态混用，库存/财务无法一致，重构。
- 页面漂亮但业务不能闭环，重构。
- 功能可用但用户难操作，优化。

后续所有 P0/P1/P2 分包，都应从这份蓝图派生，不再以“新增模块”为目标，而以“可信闭环”为目标。
