# 货抵结算过账 / 冲销并发幂等加固记录

日期：2026-04-22

## 范围

本包只处理货抵支付 / 换货贸易的结算单状态竞争，不改 UI 风格、不改业务表单、不删除历史文件。

涉及文件：

- `backend/src/services/barter.service.ts`
- `scripts/barter-concurrency-reconcile-audit-v1.cjs`
- `package.json`

新增命令：

```bash
npm run audit:barter:concurrency
```

## 真实风险

原链路存在一个高风险竞争窗口：

1. 结算单处于 `approved`。
2. A 请求开始过账，B 请求开始冲销。
3. B 在读取到 `approved` 后，旧逻辑允许用 `status in ['approved', 'posted']` 把记录直接改成 `reversed`。
4. 如果 A 已经先把结算单改成 `posted` 并写入库存 / 抵扣凭证，B 仍可能继续按自己早先读取到的 `approved` 快照执行。
5. 结果可能出现：状态是 `reversed`，但库存 / 财务过账副作用没有被完整冲回。

这类问题不是编译能发现的，也不是单次点击能稳定复现，必须用并发冲突和库存对账验证。

## 修复原则

本次没有做大范围重写，只把状态领取改成可验证的 CAS。

- `postSettlement`：只允许从当前快照状态领取过账权；领取失败后重新读取数据库真实状态，分别提示已过账、已冲销或状态已变化。
- `reverseSettlement`：只允许从当前快照状态领取冲销权，不再允许“读到 approved 后又领取 posted 状态”这种跨快照冲销。
- `reverseSettlement` 对已经 `reversed` 的重复冲销保持幂等返回。
- 所有库存、抵扣凭证、冲销日志仍沿用原有服务，不引入第二套业务口径。

## 新增并发审计

新增脚本：`scripts/barter-concurrency-reconcile-audit-v1.cjs`

覆盖 3 个场景：

| 场景 | 验证目标 | 期望 |
| --- | --- | --- |
| 双过账竞争 | 两个过账请求同时提交 | 只能成功一次；库存出入库和抵扣凭证只能写一次 |
| 双冲销竞争 | 已过账结算单被两个冲销请求同时提交 | 最终只保留一次冲销日志；库存恢复到冲销前 |
| 过账 vs 冲销竞争 | `approved` 状态下过账和冲销同时提交 | 只能出现完整过账或完整冲销，不允许半状态 |

## 反思

本包没有解决“所有业务都完美”的问题，只解决一个明确的高风险点：货抵结算在并发过账 / 冲销时不能产生半状态。

这次方向没有偏离主线，因为它同时满足：

- 触及金额、库存、状态流转，属于 Phase 3 前必须加固的核心链路。
- 没有新增第二套货抵业务模型，维护成本没有扩散。
- 新增的是可重复运行的审计脚本，而不是只靠一次人工描述。
- 证据链包含静态、构建、稳定入口、业务并发、库存对账、权限、Phase 3。

后续同类模块必须沿用这个标准：状态领取要 CAS，副作用要幂等，对账要读数据库真实结果，不能只看 HTTP 成功。
