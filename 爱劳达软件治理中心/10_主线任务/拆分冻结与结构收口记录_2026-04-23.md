当前阶段不再继续做无边界拆分。

## 为什么要冻结

用户已经多次指出：重复补丁、重复乱码、重复丢 CSS、旧入口误导、运行链不清，会让项目越来越像屎山代码。

所以现在的治理重点从“继续拆”改成：

- 稳定入口。
- 稳定运行。
- 稳定打包。
- 稳定验收。
- 稳定证据链。
- 有真实 BUG 才小刀式拆分。

## 闸门规则

### 运行层源码

- 500 行以上：观察，不自动拆。
- 650 行以上：阻断继续大功能开发，必须先写拆分计划和验收链。
- 金额、库存、回款、订单状态、权限相关文件，不允许无证据拆分。

### 审计脚本

- 审计脚本可以比业务文件长。
- 只有出现重复误判、卡住、旧入口误导时才抽公共工具。
- 不为了行数漂亮而拆测试脚本。

### 翻译文件

- 翻译文件不按普通业务代码行数拆。
- 只有出现三语口径混乱、键名归属混乱、加载性能问题时才拆。

## 后续执行原则

1. 不再因为文件超过 500 行就拆。
2. 不再为了“看起来架构更漂亮”拆。
3. 只有真实 BUG、重复维护成本、状态机不清、权限边界不清、读写回读不一致时才拆。
4. 每次拆分必须由主控重新跑对应 API 和浏览器链，不信子任务报告。
5. 每次拆分必须更新结构目录或主线台账。

## 反思

前面已经做过拆分，继续拆会偏离“本地稳定两个月 + 后续服务器可迁移”的阶段 3 目标。

现在更重要的是：

- EXE 打包打开后真的进入爱劳达。
- CSS 和图标不丢。
- 数据库写入、重启、备份恢复不丢。
- 浏览器人工流和 API 回读一致。
- 旧入口和旧接口不会误导运行。

所以本轮把“拆分”从默认动作改成受控动作。
