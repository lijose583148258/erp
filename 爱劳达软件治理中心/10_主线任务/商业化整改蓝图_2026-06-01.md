# 爱劳达 ERP+CRM 商业化整改蓝图

日期：2026-06-01

## 0. 结论

当前系统可以继续作为“本地版 / 私有化部署版”打磨和试点，但不能直接包装为成熟云端 SaaS 商业化上线。

核心判断：

- 本地版路线可以保留 SQLite、单机运行包、客户现场交付能力。
- 云 SaaS 路线必须重建租户隔离、数据库、审批流、可观测性、安全发布和测试门槛。
- 继续堆功能会放大交付风险。下一阶段重点应从“功能数量”转为“业务闭环、平台能力、可运维性、可验证发布”。

建议产品线拆分：

- A 线：本地 / 私有化部署版。目标是稳定交付、低成本试点、数据在客户本地。
- B 线：云 SaaS 版。目标是可规模化、多租户、可观测、可灰度发布、可持续运营。

## 1. 不可妥协的商业化门槛

### 1.1 安全门槛

生产环境不得存在默认管理员密码、默认 JWT 密钥、硬编码数据库路径、硬编码运行目录。

验收标准：

- 启动时强制校验 `JWT_SECRET`、管理员初始化凭据、数据库连接串。
- 未配置生产密钥时进程直接失败，并输出明确错误。
- 默认账号只能用于开发模式，且必须有显式 `NODE_ENV=development` 或等价开关。
- CI 加入密钥扫描和硬编码路径扫描。

### 1.2 数据库门槛

SQLite 仅作为本地版 / 单机版默认数据库，不作为云 SaaS 主数据库。

验收标准：

- 产品文档明确区分 SQLite 本地版与 PostgreSQL SaaS 版。
- SaaS 数据库以 PostgreSQL 为目标基线。
- 所有新核心表设计必须包含租户隔离策略。
- 数据迁移脚本必须有回滚方案、幂等校验和测试数据验证。

### 1.3 租户模型门槛

云 SaaS 不能继续只依赖“主库 + dealer_*.db”的物理分库模式。

目标策略：

- 默认采用逻辑隔离：核心业务表包含 `tenant_id`。
- 大客户或强隔离场景支持混合隔离：独立数据库 / 独立 schema。
- 平台运营分析基于统一租户维度聚合。

验收标准：

- 形成租户模型 ADR。
- 明确哪些表全局共享，哪些表租户隔离，哪些表可混合隔离。
- 后端查询层禁止绕过租户过滤。
- 至少完成一个核心链路的租户隔离测试。

### 1.4 审批流门槛

B 端商业化版本必须有统一 Workflow Engine，不能只靠单据状态字段直接跳转。

验收标准：

- 支持多级审批、会签、或签、条件分支、撤回、驳回、转交。
- 审批规则可按单据类型、金额、部门、角色、租户配置。
- 审批动作必须进入审计日志。
- 采购、销售、出入库至少各接入一个审批流样例。

### 1.5 测试与发布门槛

不能再出现复杂业务系统“npm test 无测试”的状态。

验收标准：

- CI 至少执行 lint、类型检查、构建、核心后端链路测试。
- 库存、订单、采购、财务金额计算有单元测试。
- 登录、开单、审核、出入库、查询有端到端冒烟测试。
- 每个发布包必须保留构建版本、迁移版本、验证记录。

### 1.6 用户效率门槛

ERP/CRM 的主界面必须以高频操作效率为优先，不以展示站风格为优先。

验收标准：

- 提供紧凑模式 / 高密度表格模式。
- 关键操作不依赖 hover 才可发现。
- 移动端和平板端允许合理缩放。
- 错误提示能定位到单据行、字段、原因和建议修正动作。

## 2. 目标架构

### 2.1 产品形态

| 产品线 | 目标客户 | 数据库 | 部署方式 | 商业重点 |
| --- | --- | --- | --- | --- |
| 本地版 | 小团队、试点客户、数据敏感客户 | SQLite / 可选 PostgreSQL | Windows 本地包、私有服务器 | 快速交付、低运维 |
| 私有化版 | 中大型客户 | PostgreSQL | 客户服务器 / 容器 | 权限、审批、数据隔离 |
| 云 SaaS 版 | 多租户订阅客户 | PostgreSQL | 云端集群 | 规模化、运营分析、可观测 |

### 2.2 租户与数据库

建议采用混合多租户：

- 普通租户：共享 PostgreSQL，表级 `tenant_id` 逻辑隔离。
- 高价值租户：独立 schema 或独立数据库。
- 平台运营数据：通过事件表、宽表或 BI 同步任务统一汇总。

关键设计要求：

- 所有业务查询默认带租户上下文。
- 租户上下文从认证令牌、会话或服务端上下文注入。
- 后台管理和平台运营接口需要显式超级权限。
- 数据导出、报表、搜索、审批、审计都必须包含租户边界。

### 2.3 Workflow Engine

建议新增统一审批流模块，而不是在每个业务模块内继续扩展状态机。

核心模型：

- `workflow_definition`：流程定义。
- `workflow_node`：审批节点、条件节点、结束节点。
- `workflow_transition`：节点流转规则。
- `workflow_instance`：某张单据的一次流程实例。
- `workflow_task`：待办审批任务。
- `workflow_action`：审批、驳回、撤回、转交、加签等动作记录。

接入方式：

- 业务单据提交后创建 `workflow_instance`。
- 审批通过后由 Workflow Engine 回调业务模块更新单据状态。
- 所有审批动作写入审计日志和通知中心。

### 2.4 数据驱动运营

业务系统不只记录单据，还需要形成运营抓手。

基础能力：

- 事件表 / Outbox：记录关键业务事件。
- BI 宽表：面向销售、库存、客户、采购、财务的查询模型。
- 预警规则：库存呆滞、库存不足、客户流失、应收超期、毛利异常。
- 通知通道：站内信优先，后续扩展邮件、企业微信、钉钉。

### 2.5 可观测性

云 SaaS 和私有化版必须具备基础可观测性。

基础栈：

- 日志：结构化 JSON，包含 request_id、tenant_id、user_id。
- 指标：HTTP 延迟、错误率、数据库耗时、队列积压、任务失败数。
- 链路：OpenTelemetry trace。
- 面板：Prometheus / Grafana 或等价方案。

### 2.6 模块边界

短期不建议直接拆微服务。更务实的路线是先完成模块化单体：

- 认证与权限
- 租户与组织
- CRM
- 销售订单
- 采购
- 库存
- 财务
- Workflow
- 通知
- 报表 / BI

每个模块应有明确 API、数据边界和测试边界。只有当某模块出现独立扩容、独立团队、独立发布需求时，再拆服务。

## 3. 分包执行台账

### P0-01 产品形态分线与配置清理

目标：明确本地版、私有化版、云 SaaS 版的边界，停止架构摇摆。

改造对象：

- 产品文档
- 环境变量模板
- 启动脚本
- 打包脚本
- 部署说明

验收证据：

- 有一份明确的产品形态矩阵。
- 本地包不会自称云 SaaS。
- SaaS 配置不再默认 SQLite。
- Windows 路径全部从配置读取。

退出标准：

- 新机器可按文档启动本地版。
- SaaS 版配置缺失时会失败并提示缺失项。

### P0-02 安全红线移除

目标：消除默认账号密码、默认密钥和硬编码敏感配置。

改造对象：

- 管理员初始化脚本
- JWT 配置
- 数据库管理脚本
- CI 安全扫描

验收证据：

- `admin/admin123` 只能在开发模式或测试 fixture 中存在。
- 生产环境无 `your-secret-key` fallback。
- 密钥扫描通过。
- 初始化管理员必须走一次性引导或命令行显式创建。

退出标准：

- 生产模式下缺少密钥无法启动。
- 安全扫描结果归档到发布记录。

### P0-03 PostgreSQL 与租户模型基线

目标：建立 SaaS 数据库方向和租户隔离基线。

改造对象：

- Prisma schema
- 数据迁移策略
- 租户上下文中间件
- 查询封装
- 租户测试数据

验收证据：

- 完成租户模型 ADR。
- 至少一个核心业务链路可在 PostgreSQL + `tenant_id` 下跑通。
- 跨租户越权查询测试失败即拦截。

退出标准：

- SaaS 新功能只允许基于 PostgreSQL 目标模型设计。

### P0-04 测试与发布底线

目标：让每次发包都有最低限度自动验证。

改造对象：

- Jest / Vitest 配置
- Playwright 冒烟测试
- 后端核心链路测试
- 发布验证脚本

验收证据：

- `npm test` 不再是空测试。
- 登录、创建单据、审批、库存变更、查询可自动跑通。
- 发布包包含验证报告。

退出标准：

- 没有通过核心测试不得打正式包。

### P1-01 Workflow Engine MVP

目标：替代散落在业务模块里的状态机审批。

改造对象：

- Workflow 数据模型
- 流程定义 API
- 待办任务 API
- 审批动作 API
- 采购 / 销售 / 库存接入样例

验收证据：

- 支持串行审批、金额条件分支、驳回、撤回。
- 审批记录可审计。
- 前端有待办列表和审批详情。

退出标准：

- 三类核心单据至少各接入一个可配置审批流。

### P1-02 通知中心与预警引擎

目标：从被动查询转为主动运营提醒。

改造对象：

- 站内信表
- 通知 API
- 预警规则表
- 定时任务
- 前端通知入口

验收证据：

- 库存不足、应收超期、审批待办可产生站内信。
- 通知包含租户、用户、业务对象和已读状态。

退出标准：

- 用户不进入报表页也能收到关键业务提醒。

### P1-03 BI 读模型

目标：建立面向经营分析的读模型，而不是直接压业务表。

改造对象：

- 事件表 / Outbox
- 销售宽表
- 库存宽表
- 客户宽表
- 同步任务

验收证据：

- Dashboard 不直接依赖复杂业务表 join。
- 平台方可按租户聚合查看基础经营指标。

退出标准：

- 至少完成销售、库存、客户三个主题的基础宽表。

### P1-04 高密度工作台

目标：提升销售、仓管、财务的高频操作效率。

改造对象：

- 表格密度
- 单据录入页
- 快捷键
- 错误提示
- 平板适配

验收证据：

- 表格支持紧凑模式。
- 单据错误能定位到具体行和字段。
- 关键按钮在触屏设备可直接点击。
- 页面允许合理缩放。

退出标准：

- 仓管盘点、财务对账、销售查库存三个场景完成走查。

### P2-01 可观测性与运维面板

目标：降低线上排错成本。

改造对象：

- 结构化日志
- Metrics endpoint
- Trace middleware
- 健康检查
- Grafana 面板

验收证据：

- 任一接口错误可通过 request_id 追踪。
- 可查看接口延迟、错误率、数据库耗时。

退出标准：

- 私有化和 SaaS 环境均可部署监控面板。

### P2-02 容器化与环境标准化

目标：摆脱固定 Windows 物理路径，支持服务器部署。

改造对象：

- Dockerfile
- docker-compose
- 环境变量模板
- 文件存储目录配置
- 数据库连接配置

验收证据：

- Linux 服务器可启动后端和前端。
- Windows 本地包仍可运行。
- 路径配置全部外置。

退出标准：

- 同一代码库可生成本地包和服务器部署包。

## 4. 首个 14 天执行计划

### 第 1 周

- 完成产品形态矩阵：本地版、私有化版、云 SaaS 版。
- 清点硬编码账号、密钥、路径。
- 移除生产环境默认 JWT 密钥。
- 建立生产环境配置校验。
- 建立基础测试目录和第一批登录 / 健康检查测试。
- 输出 PostgreSQL 与租户模型 ADR 初稿。

### 第 2 周

- 完成租户隔离核心链路设计。
- 搭建 Workflow Engine 数据模型草案。
- 建立通知中心最小数据模型。
- 建立发布验证脚本。
- 选择一个高频页面改造成紧凑模式样例。
- 形成第一版商业化发布门槛清单。

## 5. 暂停事项

在 P0 完成前，暂停以下动作：

- 继续堆新增业务模块。
- 把当前 SQLite 本地包宣传为云 SaaS。
- 新增硬编码 Windows 路径。
- 新增不进入 CI 的一次性脚本。
- 新增绕过权限、租户、审计的后台接口。
- 新增只能靠人工点击验证的核心业务功能。

## 6. 最低验证命令

现阶段每次发包前至少执行：

```powershell
npm run lint
npx tsc --noEmit
npm run build
npm run build:backend
npm test
npm run verify:release:core
```

如果仓库实际脚本名称不同，应建立等价命令，并写入发布记录。
