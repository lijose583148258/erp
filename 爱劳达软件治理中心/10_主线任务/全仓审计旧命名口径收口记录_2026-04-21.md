# 全仓审计旧命名与重复名口径收口记录 2026-04-21

## 1. 本次问题

全仓审计 `scripts/full-codebase-audit-v1.cjs` 之前会把所有包含 `clean`、`legacy` 等命名的有效文件统一计入 `legacyNamedFiles`，也会把所有重复文件名统一计入 `duplicateNameGroups`。

这导致三个受治理允许的脚本也进入“旧命名文件”数量：

1. `scripts/clean-dist-v1.cjs`
2. `scripts/clean-dist-v1.ps1`
3. `scripts/legacy-interface-disconnect-audit-v1.cjs`

这些文件不是旧业务入口，也不是未隔离坏文件：

1. `clean-dist-v1.*` 是构建前清理 `dist` 的受控脚本。
2. `legacy-interface-disconnect-audit-v1.cjs` 是验证旧木材接口已经断开并返回 410 的审计脚本。

因此原报告的 `legacyNamedFiles: 3` 会造成误导，容易让人以为当前运行仍被旧接口干扰。

同样，原报告的 `duplicateNameGroups: 7` 也会造成维护焦虑。实际这 7 组均为受控重复名，例如前端 `services/*.service.ts` 与后端 `backend/src/services/*.service.ts` 的分层对应、前后端 `utils` 同名领域函数、以及常见的 `index.ts` barrel 入口，不是可疑复制粘贴残留。

## 2. 本次修复

本次没有改业务逻辑，只修正全仓审计报告的分类口径：

| 字段 | 含义 |
| --- | --- |
| `legacyNamedFiles` | 当前仍可疑、需要治理的旧命名有效文件数量 |
| `legacyNamedFilesAll` | 所有命中旧命名模式的有效文件数量 |
| `governedNamedActiveFiles` | 命中旧命名模式但已受治理白名单约束的有效文件数量 |
| `structure.suspiciousLegacyNamedFiles` | 可疑旧命名有效文件清单 |
| `structure.governedNamedActiveFiles` | 受治理允许的旧命名/clean 命名文件清单 |
| `duplicateNameGroups` | 当前仍可疑、需要治理的重复名有效源码组数 |
| `duplicateNameGroupsAll` | 所有重复名有效源码组数 |
| `governedDuplicateNameGroups` | 受治理允许的重复名组数 |
| `structure.suspiciousDuplicateNames` | 可疑重复名清单 |
| `structure.governedDuplicateNames` | 受治理允许的重复名清单和原因 |

修复过程中还发现一个新的维护风险：直接往 `scripts/full-codebase-audit-v1.cjs` 里追加 Markdown 报告渲染逻辑，会让审计脚本自己超过 600 行阈值。已将报告渲染拆到 `scripts/lib/full-codebase-audit-report.cjs`，避免审计器本身变成新的大文件。

## 4. 后续规则

1. 审计脚本不能只报一个模糊数量，必须区分“可疑项”和“受治理允许项”。
2. 旧接口如果不能接入主链路，必须断开并用 410 审计证明，而不是留下半连接。
3. 受控治理脚本可以保留带 `legacy` 的语义，但必须在审计报告中明确为 governed，不得混入可疑旧文件数量。
4. 如果后续 `legacyNamedFiles` 再次大于 0，优先看 `structure.suspiciousLegacyNamedFiles`，不要凭文件名猜测。
5. 如果后续 `duplicateNameGroups` 再次大于 0，优先看 `structure.suspiciousDuplicateNames`，不要把前后端同名分层误判为屎山重复。
6. 审计脚本新增能力时也要遵守大文件治理，超过阈值前优先拆 `scripts/lib/*` helper。
