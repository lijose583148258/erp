# 全仓审计旧命名口径收口记录 2026-04-21

## 1. 本次问题

全仓审计 `scripts/full-codebase-audit-v1.cjs` 之前会把所有包含 `clean`、`legacy` 等命名的有效文件统一计入 `legacyNamedFiles`。

这导致三个受治理允许的脚本也进入“旧命名文件”数量：

1. `scripts/clean-dist-v1.cjs`
2. `scripts/clean-dist-v1.ps1`
3. `scripts/legacy-interface-disconnect-audit-v1.cjs`

这些文件不是旧业务入口，也不是未隔离坏文件：

1. `clean-dist-v1.*` 是构建前清理 `dist` 的受控脚本。
2. `legacy-interface-disconnect-audit-v1.cjs` 是验证旧木材接口已经断开并返回 410 的审计脚本。

因此原报告的 `legacyNamedFiles: 3` 会造成误导，容易让人以为当前运行仍被旧接口干扰。

## 2. 本次修复

本次没有改业务逻辑，只修正全仓审计报告的分类口径：

| 字段 | 含义 |
| --- | --- |
| `legacyNamedFiles` | 当前仍可疑、需要治理的旧命名有效文件数量 |
| `legacyNamedFilesAll` | 所有命中旧命名模式的有效文件数量 |
| `governedNamedActiveFiles` | 命中旧命名模式但已受治理白名单约束的有效文件数量 |
| `structure.suspiciousLegacyNamedFiles` | 可疑旧命名有效文件清单 |
| `structure.governedNamedActiveFiles` | 受治理允许的旧命名/clean 命名文件清单 |

## 4. 后续规则

1. 审计脚本不能只报一个模糊数量，必须区分“可疑项”和“受治理允许项”。
2. 旧接口如果不能接入主链路，必须断开并用 410 审计证明，而不是留下半连接。
3. 受控治理脚本可以保留带 `legacy` 的语义，但必须在审计报告中明确为 governed，不得混入可疑旧文件数量。
4. 如果后续 `legacyNamedFiles` 再次大于 0，优先看 `structure.suspiciousLegacyNamedFiles`，不要凭文件名猜测。
