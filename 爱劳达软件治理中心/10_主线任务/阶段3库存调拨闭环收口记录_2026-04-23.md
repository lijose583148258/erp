# 阶段 3 库存调拨闭环收口记录_2026-04-23

## 本轮目标

库存主链此前已经具备仓库、库位、手动入库、库存调整、库存凭证和台账审计，但缺少长期运行中非常常见的“库位调拨”闭环。

本轮补齐的目标不是直接改余额，而是坚持库存凭证原则：

- 来源库位扣减
- 目标库位入库
- 两条库存流水
- 一张调拨凭证
- 重复请求不得二次扣减
- 超量调拨不得落凭证

## 已完成改动

### 1. 后端调拨 API

新增接口：

- `POST /api/warehouses/stock-balances/:id/transfer`

入参：

- `toLocationId`
- `quantity`
- `requestId`
- `note`

行为：

- 校验仓储权限。
- 校验来源库存是否存在。
- 校验目标库位是否存在。
- 目标库位不能等于来源库位。
- 数量必须大于 0。
- 超过可用库存时返回 409，且不写库存凭证。
- 正常调拨时通过 `StockMovementService.postStockEntry` 写入一张 `warehouse_transfer` 凭证和两条流水。

### 2. 库存幂等策略

新增库存来源类型：

- `warehouse_transfer`

已加入幂等来源集合：

- `IDEMPOTENT_SOURCE_TYPES`

新增运行时唯一索引修复：

- `stock_entries_warehouse_transfer_ref_status_key`

该索引用于约束：

- `source_type = warehouse_transfer`
- `source_ref` 非空
- `status = posted`

目的：

- 同一个 `requestId` 重试时不能重复扣减。
- 网络抖动或按钮重复点击不会造成库存重复转移。

### 3. 前端服务层预留

新增前端服务方法：

- `warehouseService.transferStockBalance(...)`

说明：

- 当前先完成后端闭环和验收脚本。
- 后续 UI 可以在仓储库存表中挂“调拨”按钮和弹窗，不需要再重新设计 API。

### 4. 验收脚本

新增脚本：

- `scripts/warehouse-transfer-api-audit-v1.cjs`

新增命令：

- `npm run audit:warehouse:transfer`

已接入阶段 3 总闸门：

- `warehouse-transfer-api-chain`

验收链路：

1. 仓储账号登录。
2. 读取默认仓库和库位：`WH-MAIN`、`LOC-RAW`、`LOC-WIP`。
3. 原料区手动入库 100 kg。
4. 从原料区调拨 30 kg 到半成品区。
5. 使用相同 `requestId` 重试，确认不重复扣减。
6. 回读库存，原料区剩 70 kg，半成品区新增 30 kg。
7. 回读数据库，确认同一 `sourceRef` 只有 1 张调拨凭证和 2 条流水。
8. 超量调拨返回 409，确认没有写入凭证。
9. 同库位调拨返回 400。

## 反思

方向没有偏离。

这次没有重写库存系统，而是在现有库存凭证架构上补一个真实商业系统必需的小闭环。它能独立运行，也能被阶段 3 总闸门反复验证。

下一步如果继续库存主线，优先做：

1. 调拨 UI 弹窗和浏览器人工点测。
2. 盘点单 API 和凭证化差异处理。
3. 冻结库存，防止质检/争议批次被发货或生产耗用。
