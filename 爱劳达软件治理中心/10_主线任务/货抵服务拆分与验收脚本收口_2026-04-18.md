## 反思

这包方向正确：先拆纯类型、计算、状态断言、库存凭证辅助，保留 `BarterService` 的事务编排和外部 API 不变，避免把货抵状态机拆乱。

更重要的是，浏览器脚本暴露了此前验收的两个风险：一是“看到按钮点了就算通过”，二是“旧 UI 脚本没有跟随产品主线升级”。本包已经把这两个风险收进脚本制度：必须等接口响应、必须按当前主线 UI 验收、必须准备符合库存规则的测试数据。

## 剩余风险

1. `barter.service.ts` 仍有 1000+ 行，下一阶段可继续拆 `agreement repository`、`settlement posting workflow`、`reversal workflow`，但必须逐段配套 API/库存/浏览器验收。
2. 浏览器验收目前覆盖协议创建、两批执行、审核、过账、库存种子；还没覆盖冲销后的 UI 回读。
3. 旧直接结算 UI 已不再是默认入口，如果业务确实还需要“无协议直接结算”，应作为产品决策重新设计，不应让旧脚本暗中代表现状。
4. Lint 仍保留 100 个 warning，会持续增加维护噪音，但本包没有引入新的 error。
