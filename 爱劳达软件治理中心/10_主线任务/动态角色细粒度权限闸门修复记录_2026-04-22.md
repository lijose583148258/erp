# 动态角色细粒度权限闸门修复记录

## 背景

执行 `npm run verify:release` 时，full release 在 `dynamic-role-rbac-chain` 暴露失败：

- 前 17 步通过。
- 第 18 步动态角色 RBAC 失败。
- 失败点：自定义角色新增 `procurement.read` 后访问 `/api/procurement/suppliers?pageSize=1` 仍返回 403。

## 三步法

1. 翻译现象：
   - 验收脚本认为 `procurement.read` 足够读取供应商列表。
   - 后端实际返回 `requiredPermissions: ["procurement.suppliers.read"]`。
2. 判断层级：
   - 不是登录、token、角色创建、权限刷新、Casbin 失效。
   - 也不是后端路由坏了。
   - 是验收脚本的权限点口径落后于真实细粒度路由。
3. 修复：
   - 不放宽后端权限。
   - 不把供应商路由降级成粗权限。
   - 将动态角色审计脚本升级为显式验证 `procurement.suppliers.read`。

## 改动

- `scripts/dynamic-role-rbac-audit-v1.cjs`
  - 权限注册表检查增加 `procurement.suppliers.read`。
  - 更新角色权限时同时授予 `procurement.read` 和 `procurement.suppliers.read`。
  - 重新登录后同时断言两个权限点存在。
  - 禁用角色时保留同一权限集合，继续验证旧 token 失效和 refresh 被拒绝。

## 验收

- `node scripts/dynamic-role-rbac-audit-v1.cjs`：通过。
- `node scripts/effective-source-mojibake-gate-v1.cjs`：通过。
- `npx tsc --noEmit`：通过。
- `npm run verify:release`：通过，21/21。

## 结论

本次修复把动态角色验收从“粗粒度采购读权限”拉回到真实商业系统更合理的“模块读 + 子资源读”组合，避免后续误判 RBAC 能力。
