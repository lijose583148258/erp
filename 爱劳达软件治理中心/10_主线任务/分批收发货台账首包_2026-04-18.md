范围：采购分批收货、物流分批签收、库存凭证幂等、旧全量接口防重复  
结论：后端闭环已通过 API 验收，前端批次化 UI 入口尚未作为本包范围完成。

## 一、为什么做这一包

真实业务里，采购到货和客户签收经常不会一次完成：

- 一张采购单可能分两次到货，其中一批合格、一批短缺或待检。
- 一张发货单可能分多次被客户签收，不能因为第一批签收就把整单标记完成。
- 旧的“直接改成已收货/已签收”容易造成库存重复入账、状态假完成、后续对账找不到依据。

本包目标不是重做采购/物流页面，而是先把后端业务台账闭合，确保后续 UI 接上去不会建在假逻辑上。

## 二、本包新增与调整

### 1. 采购分批收货

新增运行时表：

- `purchase_receipts`

新增接口：

- `GET /api/procurement/orders/:id/receipts`
- `POST /api/procurement/orders/:id/receipts`

关键规则：

- 每次收货必须记录 `quantity / acceptedQuantity / rejectedQuantity`。
- `acceptedQuantity + rejectedQuantity` 必须等于本次收货数量。
- 已有部分收货且未收满时，旧状态接口不能直接推进到 `received`。
- 只有合格数量会生成 `procurement_receipt` 库存入库凭证。
- 收满后采购单状态推进到 `received`。

### 2. 物流分批签收

新增运行时表：

- `shipment_receipts`

新增接口：

- `GET /api/shipping/:id/receipts`
- `POST /api/shipping/:id/receipt-events`

关键规则：

- 分批签收必须先完成发货出库，不能在 `pending` 状态直接记录分批签收。
- 每次签收必须记录 `quantity / acceptedQuantity / rejectedQuantity`。
- `acceptedQuantity + rejectedQuantity` 必须等于本次签收数量。
- 已有分批签收记录后，旧的整单签收上传接口会被拦截，避免重复完成。
- 分批签收不再重复扣库存；库存只在发货出库时扣减一次。
- 全部正常签收后，发货单推进到 `delivered`，关联订单同步到 `delivered`。

### 3. 旧接口兼容原则

旧接口没有删除：

- 无分批记录时，旧的整单签收上传仍可用于“一次性签收”的简单场景。
- 无分批记录时，采购单旧状态推进到 `received` 仍会走既有全量入库逻辑。
- 一旦出现分批记录，必须继续走分批接口，防止新旧链路混用造成重复入账。

## 五、下一包建议

按价值排序继续推进：

1. 采购页面右侧新增“收货批次”抽屉：显示已收、剩余、合格、差异，并允许新增收货批次。
2. 发货页面新增“签收批次”抽屉：显示分批签收、凭证、剩余数量，并禁止混用整单签收。
3. 把采购差异数量接入质检/异常处理：短缺、破损、退货、待检分别走不同后续动作。
4. 把物流异常签收接入 RMA/售后：客户拒收、部分签收、补发、退款要能独立追踪。
5. 浏览器人工点测补充分批收发货 UI 截图证据，避免 API 绿但页面不可用。
