# 回款中心并发幂等对账审计记录（2026-04-21）

## 本包目标

本包只处理回款中心的并发、幂等和对账风险，不扩大到 UI 重构或业务口径重写。

核心目标：

1. 验证逾期同步多次并发不会造成金额漂移。
2. 验证同一笔回款多次并发核验不会重复入账。
3. 验证承诺付款终态只能有一个赢家。
4. 验证争议处理终态只能有一个赢家。
5. 将以上检查固化为可重复运行的审计脚本。

## 发现的真实问题

首轮 `audit:collection:concurrency` 发现争议终态存在竞态：

- 并发请求 `resolved / rejected / withdrawn` 时，系统曾接受 2 个成功状态。
- 最终状态会被后到请求覆盖，属于典型“先读后写”的状态机竞态。
- 影响范围：回款争议处理、发货冻结释放、客户回款状态刷新。

承诺付款在本轮样本中没有复现多赢家，但原实现同样是先读后写，因此一起加固，避免后续在高并发或 SQLite 锁竞争下复发。

## 修复方式

修改文件：

- `backend/src/services/collection-mutation.service.ts`

修复原则：

1. 状态迁移前先按原有状态机规则判断是否允许迁移。
2. 写入时使用 `updateMany({ id, status: 当前刚读到的状态 })` 做数据库级条件更新。
3. 如果条件更新没有抢到锁，立即回读最新状态。
4. 如果最新状态已经是同一目标状态，按幂等成功处理。
5. 如果最新状态是其他终态，返回冲突，不允许覆盖。
6. 对 SQLite 短暂锁或事务冲突使用 `withDbRetry` 做有限重试。

这样可以保证同一条承诺/争议记录在并发终态竞争中只有一个真正状态赢家。

审计内容：

1. 6 次并发 `/collections/sync-overdue`。
2. 5 次并发核验同一笔回款。
3. 3 个承诺付款终态并发竞争。
4. 3 个争议处理终态并发竞争。
5. 每一步都回读订单、承诺、争议列表确认最终状态。

## 乱码三步法记录

本包过程中 PowerShell `Get-Content` 一度把脚本中的中文测试名显示成乱码。

三步法结论：

1. 翻译意图：疑似“客户”“胶水”测试名乱码。
2. 判断层级：使用 Node 按 UTF-8 读取源码后确认文件真实内容为正常中文，问题在终端显示层。
3. 修复动作：没有重写文件；仅将越南语测试名升级为带音标的 `Khách hàng`，提高三语输入覆盖。

## 当前结论

回款中心本包的并发幂等风险已从“可复现多赢家”收口为“终态单赢家 + 幂等回读 + 冲突拒绝”。

后续如果继续做回款中心，只应沿着以下方向推进：

1. 将同样的 CAS 状态迁移模式扩展到其他高风险状态机。
2. 将并发审计加入阶段 3 常规验收队列。
3. 对更多金额链路补充“写入后汇总回读”断言。
