# 阶段3 认证审计与改密服务化收口_2026-04-23

## 背景

上一包已经把 Token 黑名单和 refresh token 存储从 `auth.controller.ts` 拆到服务层。本包继续处理认证控制器里的两个高频维护点：

| 问题 | 风险 |
| --- | --- |
| 登录、注册、登出、改密都直接写 `auditLog` | 审计口径分散，后续容易漏字段或改错 resource/action |
| 改密逻辑直接写在控制器里 | 密码校验、哈希、审计和 HTTP 返回耦合，维护成本高 |
| 注册/改密缺独立端到端审计 | 只靠登录/refresh 不能证明账号生命周期完整 |

## 本轮改动

| 文件 | 改动 |
| --- | --- |

## 反思

本包仍属于“降低维护成本”的拆分，不是新增业务能力。认证链路的关键不是控制器行数，而是每次拆分后必须证明：

1. 登录还能返回权限。
2. refresh token 能轮换。
3. 登出能让 token 失效。
4. 注册能创建真实用户。
5. 改密后旧密码失效，新密码可用。
6. 权限审计和 AI 隔离不受影响。

以上链路本轮都已纳入阶段 3。

## 后续约束

1. 后续继续拆 `auth.controller.ts` 时，优先拆 session/registration，不再碰已经验证的 Token store 和 password service。
2. 改认证、注册、改密、权限中间件时必须跑 `audit:auth:session-token` 和 `audit:auth:account-lifecycle`。
3. 账号生命周期审计会写入临时测试用户，属于运行证据数据；后续如做数据保洁，应先建立审计用户清理策略，不能直接删除业务用户。
