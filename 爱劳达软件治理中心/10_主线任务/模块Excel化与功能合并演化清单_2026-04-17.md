# 模块 Excel 化与功能合并演化清单

日期：2026-04-17

## 总原则

不是所有模块都应该 Excel 化。

成熟 ERP/CRM 的规律是：

- 主数据列表适合批量导入，但详情维护要表单化。
- 单据头适合表单化，单据明细行适合 Excel 网格化。
- 审批、状态流转、权限分配、财务确认必须表单化。
- 报表和台账适合导出，不能反向随意导入覆盖。
- 批量导入必须有模板、字段映射、唯一键、预校验、失败行回执、导入历史。

## 对标依据

- Odoo：任何业务对象可用 Excel/CSV 导入，明细行通过多行关联，支持 External ID / Database ID 避免重复。
- Zoho CRM：导入时要求权限、字段映射、唯一字段、重复处理、失败记录下载、导入历史。
- ERPNext：库存移动用 Stock Entry，单据头表单化，Items 明细表格化。
- Cin7：仓库侧强调扫码、批次、效期、实时库存、拣货和补货，而不是把仓储动作全部变成大表。

## 必须 Excel 化的模块

### P0：销售订单明细行

当前形态：

- 已有 `SalesOrderLineGrid`。
- 已支持粘贴 Excel 明细。

目标形态：

- 保持“订单头表单 + 明细行 Excel 网格”双轨。
- 明细行字段：品名、规格、数量、单位、单价、折扣、税额、尺寸、重量、体积、备注。
- 支持从客户历史订单联想带入常用产品。

原因：

- 销售订单明细天然多行重复录入。
- 业务员经常从微信、Excel 报价单复制明细。

### P0：生产 BOM 原料明细

当前形态：

- 已有 `ProductionBomLineGrid`。
- 已支持粘贴 Excel。

目标形态：

- 保持“BOM 主信息表单 + 原料明细 Excel 网格”。
- 化工行业字段保留：主树脂、固化剂、溶剂、颜填料、助剂、回用料、包材、损耗率、工艺阶段、替代组、收率贡献。
- 后续增加模板下载和导入预校验。

原因：

- BOM 明细是配方和成本核心，批量录入最省时间。
- 化工配方常从旧 Excel 或实验记录迁移。

### P0：仓储库存盘点/期初库存

当前形态：

- 仓储有手动入库。
- 还缺统一库存交易凭证和盘点导入。

目标形态：

- 建立“库存交易凭证”后，盘点/期初库存支持 Excel 导入。
- 字段：仓库、库位、产品、批号、数量、单位、生产日期、效期、成本单价、备注。
- 导入不能直接覆盖余额，必须生成盘点差异或期初入库凭证。

原因：

- 单机版上线前最常见需求是导入现有库存。
- 不能让用户一条条手输库存。

### P1：客户与供应商主数据

当前形态：

- 客户已有批量导入/导出。
- 客户/供应商已经朝“多名、多址、多联系人”演进。

目标形态：

- 主记录支持 Excel 导入。
- 多地址、多联系人作为子表导入，必须支持父级唯一键关联。
- 不能搜索客户时混出供应商，二者可共用组件，不共用查询结果。

原因：

- 跨国公司会有中文名、越文名、英文名，多地址、多联系人。
- 新系统上线时主数据迁移量大。

### P1：采购订单明细与收货明细

当前形态：

- 采购页面存在，但采购到仓储收货闭环仍需加强。

目标形态：

- 采购单头表单化。
- 采购明细、分批到货明细 Excel 网格化。
- 收货确认和质检动作表单化。

原因：

- 采购订单与收货经常多行、多批、多次发生。

### P1：货抵支付/换货贸易批次抵扣

当前形态：

- 已有货抵模块。
- 还需要更完整“协议-批次-抵扣-差额”模型。

目标形态：

- 协议头表单化。
- 双方货物估值明细、分批交付、分批抵扣明细 Excel 网格化。
- 每次抵扣确认表单化，保留市场价快照。

原因：

- 换货贸易不是一次性交割，批次记录适合表格。

## 必须表单化的模块

### 客户分配、公海/私海/内池操作

原因：

- 涉及权限和责任归属，不能通过 Excel 批量乱改。
- 每次分配、释放、回收必须有操作者、原因、时间、审计。

### 回款核验、财务确认

原因：

- 金额确认必须有人负责。
- 可支持导入银行流水，但“认领到哪笔订单”必须表单化确认。

### 审批、风控、异常调整、反审核

原因：

- 这是控制点，不是录入点。
- 必须保留理由、附件、审批人和前后状态。

### 完工扣料确认

原因：

- 可由 BOM 自动建议，但最终扣哪批库存、扣多少，需要确认。
- 不能纯 Excel 覆盖库存。

## 双轨入口模块

### 销售订单

- 简版新建：客户、订单号、币种、交期、备注。
- 明细网格：产品行。
- 高级折叠：尺寸、重量、佣金、税、风控提示。

### 采购订单

- 简版新建：供应商、币种、交期、采购负责人。
- 明细网格：产品/原料行。
- 高级折叠：税率、付款条款、B2B 关联。

### BOM

- 主信息表单：产品名、版本、类型、状态、标准批量。
- 明细网格：原料行。
- 高级折叠：工艺、质检、替代料、损耗、成本影响。

### 仓储

- 表单入口：建仓、建库位、单笔入库。
- Excel 入口：期初库存、盘点、批量入库。
- 操作确认：调拨、报废、冻结、解冻。

### 货抵支付/换货贸易

- 协议表单：交易双方、币种、估值日期、结算方式。
- 明细网格：双方货物估值。
- 批次网格：分批交付与抵扣。
- 确认表单：差额现金、审批、对账。

## 不建议 Excel 化的模块

- 登录、角色切换、语言切换。
- 用户权限和角色授权。
- 客户分配/回收/释放。
- 审批动作。
- AI 设置和数据授权。
- 备份恢复。
- 运行状态和系统配置。

这些动作一旦批量导入，风险大于收益。

## 可合并的重复功能逻辑

### P0：导入导出能力合并

当前问题：

- 客户导入导出、AI 表格解析、BOM 粘贴、订单粘贴、回款导出分散存在。

目标：

- 建立统一 `ImportExportCenter` 或 `importExport.service`。
- 前端统一：模板下载、粘贴导入、文件导入、预览、错误行。
- 后端统一：行数限制、字段映射、唯一键、失败报告、导入历史。

收益：

- 不再每个模块重复写解析逻辑。
- 降低后续新增模块的维护成本。

### P0：库存余额和库存流水合并到交易凭证模型

当前问题：

- 仓储余额、资产批次、生产扣料、成本台账存在交叉。

目标：

- 库存变化都走 `StockMovement / StockEntry`。
- `StockBalance` 只作为汇总读模型。

收益：

- 可以对账。
- 可以追溯。
- 可以做反审核和恢复。

### P1：客户/供应商主数据交互组件合并

当前问题：

- 两边都需要多名、多址、多联系人。

目标：

- 共用“多名、多址、多联系人”组件和校验。
- 查询作用域必须隔离：客户搜索只出客户，供应商搜索只出供应商。

收益：

- 减少重复开发。
- 避免规则不一致。

### P1：状态机与审计日志合并

当前问题：

- 订单、回款、货抵、异常调整、生产、采购都有状态变化。

目标：

- 提炼统一状态变更工具：校验前态、写新态、写审计、返回回读。

收益：

- 减少“前端显示完成但后端没闭环”的假完成。

### P2：导出报表组件合并

当前问题：

- 回款中心、财务台账等各自写导出。

目标：

- 合并成统一 `exportRows(filename, columns, rows)` 工具，并支持 CSV/XLSX。

收益：

- 小收益，但能降低噪声。

## 信息降噪原则

### 页面结构

每个复杂页面默认分五区：

- 主数据
- 明细行
- 状态与动作
- 关联记录
- 审计/历史

### 默认展示

- 默认只展示日常必填字段。
- 高级字段折叠。
- 明细多于 3 行时进入网格。
- 只在需要时展示审计，不要把审计混在主录入区。

### 搜索规则

- 客户、供应商、产品、批次必须作用域明确。
- 支持手填、联想、扫码、粘贴，但最终要落到明确主数据。

## 第一批执行建议

1. 建统一导入导出契约：模板、字段映射、唯一键、失败行、导入历史。
2. 给仓储补“期初库存/盘点导入”的设计和 API，不直接覆盖余额。
3. 更新生产浏览器审计脚本，覆盖新 BOM 网格。
4. 把采购单改成“单头表单 + 明细 Excel 网格 + 收货闭环”。
5. 开始抽公共多地址/多联系人组件，客户先用，供应商复用。
6. 建 `StockMovement / StockEntry`，让仓储、生产、采购、销售最终接入同一库存凭证。

## 多智能体审计补充

### Excel 化输入审计员结论

- `SalesOrders` 已具备头表单和明细网格，是最适合沉淀为标准双轨模式的模块。
- `Production/BOM` 已具备粘贴 Excel、智能导入、按批量换算单耗，是最高价值 Excel 化模块。
- `客户/供应商主数据` 应该表单主导，批量导入导出辅助，避免多名、多址、多联系人被平铺得难维护。
- `Procurement` 适合“供应商表单校验 + 采购明细网格”。
- `Barter/货抵` 适合协议表单 + 估值/交付/抵扣明细网格，不能纯 Excel 化。
- `Collections/回款` 适合导出，不适合 Excel 主录入。
- `Warehouse` 适合表单化动作，期初库存和盘点可以后续 Excel 化。

### 重复逻辑合并审计员结论

- `useCRM.ts`、`ProductionWorkspace.tsx`、`BarterWorkspace.tsx`、`AdjustmentCenter.tsx` 是兼容壳，应固定为“只转发，不长业务”。
- `collection.service.ts`、`production.service.ts`、`finance.service.ts` 这类 facade 不是垃圾重复，而是稳定门面，Phase 0-2 前不建议删除。
- CRM 前端权限门禁和后端 `authorize` 是双层保护，不应合并掉后端权限。
- `SalesOrders` 已经是合理拆分，不应回滚成大文件。

### 商业闭环与信息密度审计员结论

- `ProductionWorkspaceV2.tsx` 同时承载 BOM、工单、详情、批次、调账，属于 P0 信息密度风险。
- `CollectionCenterView.tsx` 同时承载账龄、核销、承诺、争议、拦截、导出，属于 P0 财务闭环混杂风险。
- `WarehouseWorkspace.tsx` 需要后续拆成仓库主数据、库位管理、库存台账、库存动作。
- `BarterWorkspace.clean.tsx` 需要拆成协议、执行批次、结算流水。
- `CRMCustomerDrawer.tsx` 应继续落实主数据、地址、联系人、归属池、审计五区块。
