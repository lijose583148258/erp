# 采购状态机并发幂等加固记录（2026-04-21）

## 本包目标

本包接续回款中心并发修复，检查采购状态机是否存在“先读状态再写状态”的同类风险。

目标不是重写采购模块，而是保持现有采购业务链路不变，在状态写入点补强并发单赢家能力。

## 涉及链路

采购主状态链：

1. `pending`
2. `approved`
3. `in_transit`
4. `received`
5. `cancelled`

高风险动作：

1. 审批采购单。
2. 发货在途。
3. 收货入库。
4. B2B 销售状态同步到采购状态。
5. 收货状态触发库存凭证和成本台账。

## 修复点

修改文件：

- `backend/src/services/procurement-status.service.ts`

修复内容：

1. 将采购状态写入从 `purchaseOrder.update({ where: { id } })` 改为 `updateMany({ where: { id, status: 当前刚读到的状态 } })`。
2. 如果第一轮 CAS 没有抢到，立即回读最新状态。
3. 如果最新状态已经等于目标状态，按幂等成功返回。
4. 如果最新状态到目标状态不合法，返回冲突。
5. 对 B2B 同步这类 `enforceTransition=false` 的链路，允许在回读最新状态后再进行一次条件更新，但仍然要求基于最新状态 CAS 成功。

## 为什么这样做

采购收货不是单纯改状态，它会联动：

1. `purchase_receipts`
2. `stock_entries`
3. `stock_movements`
4. `stock_balances`
5. `inventory_cost_ledgers`

如果状态迁移没有 CAS，极端情况下可能出现：

1. 状态被后写覆盖。
2. 两个请求都认为自己可以收货。
3. 库存凭证或成本台账重复。
4. 前端看起来成功，但库存和财务对不上。

本次修复把采购状态更新收束为“基于当前状态的一次性条件写”，并保留既有的收货凭证 `sourceRef=PO-id` 幂等保护。

## 证据读取注意事项

本包过程中，使用 PowerShell `Get-Content` 读取 UTF-8 JSON 再管道给 Node 时，曾出现 JSON.parse 失败。

三步法判断：

1. 翻译意图：疑似报告文件内 `原料区` 乱码或控制字符污染。
2. 判断层级：Node 直接 `fs.readFileSync(..., 'utf8')` 读取并解析成功，报告文件本身有效。
3. 修复动作：不改报告文件，不重写源码；以后解析验收 JSON 时优先由 Node 直接读取文件，避免 PowerShell 显示层误解码进入管道。
