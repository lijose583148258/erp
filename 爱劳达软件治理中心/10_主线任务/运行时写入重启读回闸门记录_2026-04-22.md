# 运行时写入重启读回闸门记录 2026-04-22

## 目标

本包继续收口阶段 3 的本地稳定运行风险：不仅证明重启不会丢已有业务数据，还要证明“重启前新写入的一笔数据”确实落在 active runtime DB，并能在重启后读回。

这条闸门专门防止以下假绿：

- 服务能打开，但写入落到临时库。
- 服务能打开，但写入落到旧影子库。
- 服务能打开，但重启后读不到刚写入的数据。
- 运行资源正常，但业务核心表被副作用改动。

## 本次修正

- 新增公共库 `scripts/lib/runtime-stable-restart.ts`，集中处理稳定运行重启、健康等待和资源检查。
- 重构 `scripts/runtime-restart-persistence-audit-v1.ts`，复用公共库，减少重复启动器逻辑。
- 新增 `scripts/runtime-write-read-restart-audit-v1.ts`。
- 新增 `npm run audit:runtime:write-restart`。
- 将 `runtime-write-read-restart` 接入 `verify:phase3` 和 `verify:release`。

## 闸门判断

写入-重启-读回闸门必须同时满足：

- active runtime DB 存在，且路径为当前运行库。
- 向 `audit_logs` 写入一条带唯一 `probeId` 的审计探针。
- 写入后立即按 `probeId` 读回同一行。
- 运行 `start-stable-v2.ps1` 重启稳定运行层。
- 重启后仍按同一 `probeId` 读回同一行。
- 重启前后 DB 路径不变化。
- 重启前后 43 张业务核心表指纹不变化。
- 前端运行资源检查无失败项。

## 反思

上一包证明“已有数据不会因重启漂移”，这一包证明“新写入数据确实跨重启持久化”。  
两条闸门组合后，能覆盖本地 EXE 和后续服务器迁移中最容易产生误判的两个问题：读旧库、写错库。

后续涉及启动器、数据库路径、备份恢复、迁移、打包 EXE 的改动，都必须保留这两条闸门。
