# 订单 / 回款 / 承诺付款链路拉正记录 2026-04-20

## 目标

按系统工程方法修正销售订单人工流，不再用“能点击”代替“业务闭环通过”。

本轮只处理订单、回款、承诺付款相关的真实断点，不改变现有 UI 风格，不删除用户数据。

## 发现的问题

1. 浏览器审计脚本用商品名定位销售订单行，但销售订单列表不展示商品明细，导致测试锚点偏离真实页面结构。
2. 销售订单页挂载 `CollectionActionModal` 时仍使用旧接口属性，缺少 `open`，并传入已淘汰的 `onSaved`，导致承诺付款弹窗链路存在旧接口脱钩风险。
3. 提交承诺付款后，前端曾用订单列表快照覆盖订单详情；列表接口只带回款状态，不带完整回款金额和备注，导致历史弹窗可能显示 `0.00`。
4. 订单详情接口没有返回订单关联的承诺付款记录，历史弹窗无法形成“订单 -> 承诺付款 -> 回读”的小闭环。
5. 浏览器脚本填承诺付款时，误把备注写到了联系人字段，不能证明备注真实保存。

## 修复策略

1. 销售订单列表补稳定行级测试锚点：`sales-order-row-*`。
2. 行操作按钮补稳定测试锚点：回款、历史、编辑。
3. 承诺付款弹窗挂载改为当前组件契约：`open` + `onSubmitted`。
4. 提交承诺付款后刷新订单详情，而不是用列表快照覆盖详情。
5. 订单详情接口增加 `collectionPromises`，并在前端 `SalesOrder` 类型和 `order.service.ts` 映射层补齐。
6. 历史弹窗增加“承诺付款记录”区块，展示承诺单号、金额、时间、备注。
7. 浏览器审计脚本改为用本轮唯一客户名定位新订单行，并要求回款备注和承诺备注都在页面回读。
8. 脚本增加动作后 console/API 错误硬失败判断，避免按钮点击成功但后端 400 被误判为通过。

## 反思

本轮不是单纯修按钮，而是修正了一个典型的“假完整”链路：

- 列表不是详情，不能用列表快照覆盖详情。
- HTTP 成功不等于业务闭环，必须看金额、备注、状态是否回读。
- 测试锚点必须贴合页面真实展示字段，不能用列表不展示的商品名定位行。
- 旧接口属性必须尽快断开或显式兼容，否则会造成“页面看似挂载，实际永远不开”的隐性问题。

后续同类页面默认按这个标准处理：先确定业务可见证据，再写测试锚点，再跑浏览器回读。
