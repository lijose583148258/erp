# 阶段3角色分配策略服务化收口_2026-04-23

## 背景

权限体系已经接入动态角色、权限点和 Casbin，但身份创建与团队成员管理里仍重复维护角色分配判断：

- `auth.controller.ts`
- `team.controller.ts`

重复点包括：

- 用户 `segment` 默认规则
- 是否允许分配非销售角色
- 是否需要 `authorization.roles.manage`

这类逻辑如果继续分散，后续超级管理员授权、内销/分销角色、动态角色禁用等改动容易只修一边，造成权限绕过或误拒绝。

## 本次改动

| 文件 | 作用 |
| --- | --- |
| `backend/src/services/role-assignment-policy.service.ts` | 新增角色分配策略服务，集中 `resolveUserSegment`、`isRoleAssignmentChange`、`canAssignPrivilegedRoles` 和 `ROLE_ASSIGNMENT_PERMISSION`。 |
| `backend/src/controllers/auth.controller.ts` | 删除本地重复策略函数，注册用户时改用公共策略判断。 |
| `backend/src/controllers/team.controller.ts` | 删除本地重复策略函数，创建/更新团队成员时改用公共策略判断。 |

## 边界

本轮没有改变权限语义：

- 默认 `sales` 角色仍可由具备团队写权限的入口创建。
- 分配或变更非 `sales` 角色仍需要 `authorization.roles.manage`。
- `segment` 仍按原规则：销售默认 `direct`，其他角色默认 `mixed`。
- 没有调整 Casbin fallback。
- 没有调整内置角色禁用语义。
- 没有拆分 `auth.controller.ts` 的 token、登录、密码和刷新逻辑。

这些属于后续单独包，不能和策略抽取混在一起。

## 当前结论

权限主框架仍在正确方向上：路由权限、动态角色、角色分配防提权和系统权限 UI 均通过专项验证。本轮只做公共策略收口，降低维护成本，不扩展权限能力。

下一步权限治理建议：

1. 单独处理 `audit.controller.ts` 内部 `admin` 硬编码与 `audit.read` 动态权限的语义冲突。
2. 单独评估 Casbin fallback：上线环境不能因为动态权限表异常而静默回退内置策略。
3. 单独处理 token 黑名单和 refresh token 内存存储，后续服务器部署应迁到持久化或 Redis 类存储。
4. 再拆 `auth.controller.ts`：session、registration、password、token-store 分开。
