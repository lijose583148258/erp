## 后端服务化

原来 `shipping.controller.ts` 同时承担：

- 发货单查询和写入。
- 签收凭证处理。
- 发货状态推进。
- 成品区库存查找。
- 出库库存凭证生成。
- 幂等防重复出库。

本次将库存扣减相关逻辑拆到 `shipping-stock-issue.service.ts`：

- `hasShippingIssuePosted`
- `resolveShippingIssueStock`
- `postShippingIssueIfMissing`

保留原业务口径：

- 出库来源仍为 `shipping_issue`。
- 来源引用仍为 `shipmentNo`。
- 已存在出库凭证时不重复扣减。
- 默认从 `LOC-FG` 成品区扣减。
- 无库存时仍抛出 `No available stock for shipment ...`，控制器继续映射为 409。

## OCR 红灯三步法

### 1. 翻译现象

阶段 3 带浏览器验收首次失败：

```text
shipping-browser-chain failed
create-shipment-via-ocr exceeded 25000ms
```

截图显示：

- 页面进入的是爱劳达发货物流页，不是智仔页面。
- OCR 预览已出现客户、产品、数量、批次号。
- 但点击“应用到表单”后没有出现 `POST /api/shipping`。
- 脚本只是在不断 `GET /api/shipping?pageSize=50` 回读，直到超时。

### 2. 判断层级

不是后端库存扣减失败，也不是源码乱码。

排查结果：

- API 发货链先前已通过。
- 浏览器截图没有页面级乱码。
- Node 按 UTF-8 读取 `useShipping.ts` 为正常中文，PowerShell `Get-Content` 的乱码属于终端显示层误解码。
- OCR 解析曾将 `客户名称: xxx` 的客户名误伤为 `名称: xxx`，后续又暴露出客户列表状态可能慢于按钮点击的时序问题。

### 3. 修复动作

`services/smartFormService.ts`：

- 将客户标签匹配改成长标签优先。
- 增加 `stripOcrCustomerLabel`，统一剥离 `客户名称`、`公司名称`、`名称`、`ship to`、`customer` 等标签。
- `matchCustomer` 对输入名也先做标签剥离，避免人工粘贴带字段名时匹配失败。

`pages/shipping/useShipping.ts`：

- OCR 应用时先用当前客户池匹配。
- 如果匹配失败，立即重新读取客户池再匹配一次。
- 第二次仍失败才提示“未识别到可匹配的客户名称”。

这个修复不绕过权限；它只避免前端状态列表慢半拍导致的假失败。

## 反思

本次方向没有偏离阶段 3：

- 没有重写发货页面。
- 没有改变品牌 UI。
- 没有删除历史资料。
- 没有绕开权限。
- 没有只用 build 证明完成。
- 保留了 API 和浏览器双证据。

暴露出的关键经验：

- 浏览器验收必须放在组合验收里跑，单独脚本 PASS 不代表组合链 PASS。
- OCR/AI 类入口最容易出现“识别成功但业务不落库”的假完整，必须验证 POST 和回读。
- 终端乱码与源码乱码要严格区分，不能看到 PowerShell 乱码就直接重写文件。

## 后续建议

1. 把发货模块剩余的签收批次、物流资产、发货列表列定义继续拆成更小服务或 hook。

3. 将组合验收中的“先红后绿”案例纳入反幻觉检查表，作为 AI 编程容易漏掉的典型缺陷。
