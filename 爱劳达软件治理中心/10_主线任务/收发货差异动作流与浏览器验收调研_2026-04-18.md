# 收发货差异动作流与浏览器验收调研

日期：2026-04-18

## 调研目标

本次调研解决两个问题：

1. 当前浏览器验收被 `spawn EPERM` 阻断后，应该怎么恢复真实点测证据。
2. 收发货差异工作台下一步应该怎么从“能看、能新增规则”升级成成熟商业 ERP 的异常处置闭环。

## 一、外部成熟方案要点

### 1. 浏览器验收层

Playwright 官方 `BrowserType` 支持三类相关能力：

- `launch`：直接启动浏览器。
- `connect`：连接由 Playwright `launchServer` 启动的浏览器。
- `connectOverCDP`：通过 Chrome DevTools Protocol 连接已有 Chromium 浏览器，例如 `http://localhost:9222/`。

当前环境中 `launch` 被 `spawn EPERM` 阻断，因此继续反复启动浏览器没有价值。更稳的备选是增加 CDP 连接模式：由用户或启动脚本打开一个带远程调试端口的 Edge/Chrome，审计脚本优先连接这个已存在的浏览器，而不是自己创建进程。

来源：

- Playwright BrowserType API：https://playwright.dev/docs/api/class-browsertype

### 2. 收货数量差异

Microsoft Dynamics 365 对 over/under receiving 的处理不是简单报错，而是先按整单金额容差、再按行数量百分比容差判断。差异在不同场景下会生成：

- over/under transaction
- movement journal
- 新采购订单或负数采购订单
- 需要人工处理的差异记录

这说明爱劳达当前的 `ReceiptToleranceRule` 方向正确，但还缺“规则命中解释”和“后续动作单据”。

来源：

- Dynamics 365 Process over/under transactions：https://learn.microsoft.com/en-us/dynamics365/supply-chain/landed-cost/over-under-transactions

### 3. 产品收货与纠正

Dynamics 365 的采购收货要求有 product receipt identifier，通常对应供应商装箱单/送货单，用于把供应商单据、实收、库存/费用核对起来。对产品收货的纠正，官方明确说通常只能减少已收数量；如果要增加数量，应再过一张新的产品收货记录。

这对爱劳达的启发是：不要让差异处理直接改原始收货，应追加“处置单/调整单/新收货单”，保留原始记录。

来源：

- Dynamics 365 Product receipt against purchase orders：https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/product-receipt-against-purchase-orders

### 4. 质量检验与不合格品

Dynamics 365 的质量订单可以关联 Inventory、Sales、Purchase、Production 等来源；不合格品要记录不合格类型、问题类型、审批状态、隔离区域、处置动作和纠正措施。

这说明爱劳达不能把“质量拒收”仅作为差异类型，它应该可以转成质量/不合格记录，并能反查来源单据。

来源：

- Dynamics 365 Quality orders：https://learn.microsoft.com/en-us/dynamics365/supply-chain/inventory/quality-orders
- Dynamics 365 Quality and nonconformance management overview：https://learn.microsoft.com/en-us/dynamics365/supply-chain/inventory/quality-management-processes

### 5. 客户退货、RMA 与处置码

Dynamics 365 的客户退货区分 physical return 和 credit only。退货过程包括：创建退货单、入库检验、决定处置、生成装箱/发货或入库记录、生成发票/贷项。处置码决定财务影响、库存去向和是否创建替换订单。

爱劳达已有 `Rma` 表，但目前更像售后申请，缺少成熟系统里的处置码、入库检验、替换订单、贷项/退款、库存动作之间的显式连接。

来源：

- Dynamics 365 Sales returns：https://learn.microsoft.com/en-us/dynamics365/supply-chain/sales-marketing/sales-returns
- Dynamics 365 Return reason codes and disposition codes：https://learn.microsoft.com/en-us/dynamics365/supply-chain/sales-marketing/disposition-and-return-reason-codes

### 6. 供应商退货与贷项

NetSuite 把 Vendor Return Authorization 定义为非过账交易，用于跟踪退给供应商的物品、数量、审批状态、发货状态，以及供应商退款或贷项金额。供应商退货流程包括创建授权、审批/取消、发货、贷记。

SAP Business One 的采购退货和 A/P Credit Memo 也强调：如果已经有发票，贷项通知用于冲销应付；如果有实际退货，库存和财务应有明确来源单据。

这说明爱劳达不应该让“采购拒收/退供”只停留在差异单关闭，而要形成“供应商退货授权/退货单/应付扣减或贷项”的链。

来源：

- NetSuite Vendor Return Authorization：https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N3199760.html
- SAP Business One A/P Credit Memo：https://help.sap.com/docs/SAP_BUSINESS_ONE/68a2e87fb29941b5bf959a184d9c6727/44fc225c1d3c6c30e10000000a114a6b.html

## 二、对当前爱劳达系统的判断

当前已有底座：

- `ReceiptDiscrepancyCase`：差异单主记录。
- `ReceiptToleranceRule`：容差规则。
- `Rma`：客户售后/退货申请。
- `AdjustmentRecord`：库存/生产/财务调账。
- `StockEntry` / `StockMovement` / `StockBalance`：库存凭证、流水、余额。
- `AuditLog`：审计日志。

当前主要缺口：

- 差异单关闭后只是状态变化，缺少正式处置动作。
- RMA 与差异单没有统一来源关系。
- 供应商退货授权/退供单缺失。
- 客户退货的处置码缺失。
- 质量/不合格记录缺失独立模型。
- 财务扣减/贷项/索赔没有形成独立、可审计的记录。
- 容差规则没有命中解释和冲突检查。
- 浏览器验收脚本只能 `launch`，没有 CDP 连接备选。

## 三、建议的爱劳达落地模型

### 1. 保留差异工作台作为入口，不把它做成万能单据

差异工作台只负责：

- 收集异常。
- 显示来源。
- 显示规则命中。
- 发起处置动作。
- 跟踪处置状态。

它不直接改库存、不直接改账、不直接生成退款。

### 2. 新增统一处置动作表

建议新增 `ReceiptDiscrepancyAction`，作为差异单后续动作的母表：

- `caseId`
- `actionType`
- `status`
- `sourceModule`
- `sourceRef`
- `targetModule`
- `targetId`
- `quantity`
- `amount`
- `currency`
- `reasonCode`
- `dispositionCode`
- `createdBy`
- `approvedBy`
- `postedAt`

推荐 actionType：

- `quality_check`：转质检/不合格。
- `supplier_return`：退给供应商。
- `customer_rma`：客户退货/RMA。
- `replacement_shipment`：补发/换货。
- `credit_or_deduction`：贷项/扣款/索赔。
- `stock_adjustment`：库存调整。
- `accept_with_concession`：让步接收。
- `close_no_action`：无需动作关闭。

### 3. 先做最小闭环，不一次性做全商业系统

下一包优先实现：

1. 差异单详情动作区。
2. `ReceiptDiscrepancyAction` 表和 API。
3. 动作类型先支持 4 个：
   - 转质检
   - 创建客户 RMA
   - 创建库存调账草稿/已过账
   - 标记为财务扣减待处理
4. 每个动作必须写 `actionRef` 回差异单。
5. 每个动作必须 API 读回。
6. 不做自动财务过账，先做待处理凭证或调账入口，避免误改金额。

### 4. 浏览器验收层恢复方案

新增浏览器启动策略优先级：

1. 先尝试连接 `BROWSER_CDP_URL`。
2. 如果没有，再尝试原有 `launchBrowserWithGuard`。
3. 如果两者都失败，脚本快速失败并输出环境判定，不等待 5 分钟。

建议启动方式：

```powershell
msedge.exe --remote-debugging-port=9222 --user-data-dir=D:\AilaoDaRuntime\browser-profile
```

审计脚本使用：

```text
BROWSER_CDP_URL=http://127.0.0.1:9222
```

注意：不要用用户日常浏览器默认 Profile，避免污染用户数据和登录态。

## 四、下一包执行优先级

### P0：浏览器验收恢复

原因：没有浏览器证据，UI 相关结论都不够硬。

交付：

- `scripts/lib/browser-connect-or-launch.cjs`
- 所有后续浏览器审计脚本优先支持 `BROWSER_CDP_URL`
- 增加 `browser-cdp-probe.cjs`
- 输出清楚区分：
  - CDP connected
  - launch passed
  - spawn EPERM
  - target refused

### P1：差异处置动作母表

原因：成熟 ERP 的关键不是“关闭差异”，而是“差异去向可追踪”。

交付：

- Prisma 模型 `ReceiptDiscrepancyAction`
- 后端 API：
  - `POST /api/receipt-discrepancies/:id/actions`
  - `GET /api/receipt-discrepancies/:id/actions`
- 差异单返回时附最近动作摘要。
- API 验收覆盖创建、读回、权限、状态不可重复关闭。

### P2：动作连接现有模块

原因：当前系统已经有 RMA、调账、库存流水，不应该重造。

交付：

- `customer_rma` 动作调用现有 RMA 创建链。
- `stock_adjustment` 动作调用现有 Adjustment 链。
- `quality_check` 先落为动作记录，不急着新建完整质量模块。
- `credit_or_deduction` 先落为待财务处理动作，不自动改账。

### P3：页面动作区

原因：使用者需要在差异工作台里看到“下一步干什么”，不是只看到状态按钮。

交付：

- 差异队列行操作改为“打开处理抽屉”。
- 处理抽屉分区：
  - 来源信息
  - 差异数量/金额
  - 容差命中
  - 推荐动作
  - 人工处置动作
  - 已生成关联单据

## 五、反思

这条路线是正确的，但要避免两个反方向偏离：

1. 不要把差异工作台做成一个巨大页面，把质量、财务、库存、RMA 全塞进去。
2. 不要为了“看起来闭环”直接自动改账、自动改库存。

正确做法是：

- 差异单做入口。
- 动作表做桥。
- 质量/RMA/库存/财务各自保持独立单据。
- 所有动作都能从差异单反查，也能从目标单据反查差异来源。
