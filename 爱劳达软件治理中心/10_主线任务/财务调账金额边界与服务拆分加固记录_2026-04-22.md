# 财务调账金额边界与服务拆分加固记录_2026-04-22

## 本包目标

本包聚焦“调账中心”中的财务调账小闭环，避免调账绕过回款核验的金额保护，导致订单已收金额、调账记录、回款中心和风控状态出现不一致。

## 三步法结论

1. 翻译：本轮 PowerShell 输出中出现的乱码，多数是终端显示层把 UTF-8 中文误解码；用 Node 直接按 UTF-8 读取源码与 JSON 报告后，确认有效源码乱码闸门通过。
2. 判断：真实问题不是源码乱码，而是财务调账把 `amountDelta` 直接累加到订单 `paidAmount`，允许超出订单金额，也允许负数调账被 `Math.max(0)` 静默截断。
3. 修复：改为以“分”为单位计算金额边界，超额或小于 0 时返回 409；并用订单当前 `paidAmount` 做乐观并发条件，防止服务器部署后并发调账造成记录与订单金额漂移。

## 真实复现

本轮先用真实 API 创建销售客户与订单，再用经理角色做调账，复现两个风险：

- 100 元订单可以被财务调账直接调成已收 150 元。
- 20 元已收可以被 -40 元调账静默夹到 0，调账记录显示 -40，但实际只影响 -20。

这两个都属于上线后账务对账才容易暴露的问题，不能只靠前端表单限制。

## 当前边界

- 财务调账当前仍定义为“调整订单已收金额”，不是“修改订单最终应收金额”。
- 减免、折让、坏账核销如果要影响应收本金，后续应单独建“应收调整/坏账核销”子类型，不能继续复用 paidAmount 调账。
- pending 超额调账允许先登记，但 apply 时必须拒绝；本轮脚本已覆盖并在测试后冲销清理 pending 单。

## 反思

本轮没有把终端显示乱码误判成源码损坏，这是正确方向。真正有价值的修复是金额边界、并发冲突、错误码语义和服务拆分。后续如果继续做财务治理，优先补“应收调整类型化”，而不是继续把所有财务差异都塞进 paidAmount。

## 2026-04-22 追加：应收语义边界

### 调研结论

成熟 ERP / 会计系统通常把三类动作分开：

- 真实回款：进入收款、核销、银行或现金流链路，影响已收金额。
- 贷项、折让、减免：属于 credit memo / credit note / allowance，影响应收余额或开票口径，不等同于客户已经付款。
- 坏账核销：属于 write-off / allowance / journal 动作，需要审批、原因、凭证和审计，不应伪装成收款。

### 本包决策

本包不改数据库结构，不改订单原始金额，不新增半成品应收模块；只先把危险入口堵住：

- `bad_debt_writeoff`
- `credit_memo`
- `discount_allowance`
- `ar_writeoff`
- `short_payment_writeoff`

以上原因分类如果从“财务调账 / 已收金额调账”入口提交，后端统一返回 409，并提示走应收调整专用流程。

### 为什么这样更稳

- 避免把“客户少付、折让、坏账”错误写成 `paidAmount`。
- 不破坏当前订单、回款、财务分析、催收和风控现有口径。
- 为后续新增“应收调整 / 坏账核销 / 贷项凭证”模块留出边界，不继续把逻辑堆进调账中心。

### 后续应收模块建议

下一阶段如果继续补，应独立建 `ReceivableAdjustment` 或等价子模块，字段至少包含：

- 调整类型：贷项、销售折让、短款核销、坏账核销、汇差调整。
- 关联订单 / 客户 / 发票号。
- 调整金额、币种、汇率、税务口径。
- 审批状态、凭证号、附件、原因、经办人与审批人。
- 是否影响应收余额、是否影响收入、是否影响现金流。

本阶段只做边界保护，不做假完整。
