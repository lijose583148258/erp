# 运行时重启持久化指纹闸门记录 2026-04-22

## 目标

本包收口“本地稳定运行两个月 + 后续服务器可迁移”的运行时重启风险。

过去仅用健康检查或页面 200 判断启动成功不够，因为启动器如果误选旧 SQLite 影子库，系统仍可能正常打开，但业务数据已经被旧库覆盖。  
因此本包把验收标准升级为：重启前后同一运行库路径、同一业务数据指纹、同一前端静态资源可访问。

## 本次修正

- 修正 `scripts/start-stable-v2.ps1` 的运行库选择策略。
- 如果 `D:/AilaoDaRuntime/stable.db` 等 active runtime DB 已存在，启动器直接使用该库。
- 只有 active runtime DB 不存在时，才允许从候选库或 seed 库初始化。
- 新增 `scripts/runtime-restart-persistence-audit-v1.ts`。
- 新增 `npm run audit:runtime:restart`。
- 将 `runtime-restart-persistence` 接入 `verify:phase3` 和 `verify:release`。

## 闸门判断

重启持久化闸门必须同时满足：

- `start-stable-v2.ps1` 在 5 分钟内完成。
- 重启前后运行库路径不变化。
- 43 张业务核心表的数量与金额汇总指纹一致。
- `/health`、`/`、`/manifest.json`、`/icon.svg`、`/sw.js` 和首批 JS/CSS 资源均可访问。
- 不允许发现外部资源地址作为本地 EXE 运行依赖。

## 反思

本次不是为了再增加一个报告，而是堵住一个真实上线前风险：服务能启动不代表数据没有漂移。

后续所有涉及启动器、迁移、备份、恢复、打包 EXE 的改动，都不能只跑 `check:runtime`，必须保留这条重启持久化指纹闸门。它负责防止“看起来打开了，实际上接错库或回退旧数据”的假绿。
