# 采购入库库存闭环执行记录 2026-04-17

## 本包目标

- 把采购主链路从“采购单发货 in_transit”推进到“确认收货 received 后真实入库”。
- 让 B2B 销售状态同步到采购收货时，也能生成库存凭证。
- 让审计脚本不再假绿：必须回读库存余额、库存凭证、原料区库位。
- 按默认制度执行：5 分钟限时、禁乱码闸门、API + 浏览器 + DB 三层证据。

## 发现的问题

| 问题 | 判断 | 风险 |
|---|---|---|
| `sync-b2b/:salesOrderId` 使用旧 `idParamSchema` | 路由参数名是 `salesOrderId`，但校验期待 `id`，会导致同步接口被校验层挡住 | P1 |
| B2B 同步到 `received` 时没有统一走采购入库凭证逻辑 | 状态可以变成已收货，但库存台账可能没有入账 | P0 |
| 采购 API 审计只测到 `in_transit` | API 报告可能误判采购链路已完成 | P1 |
| 采购浏览器审计只测到 `in_transit` | 页面点测可能假绿，没有验证“收货并入库” | P1 |
| 库存凭证接口只能看最近记录 | 审计依赖最近 200 条，后续数据多了会不稳定 | P2 |
| 审计脚本复用随机客户 | 容易被真实信用额度/风控状态污染，导致测试不稳定 | P2 |

## 保留风险

| 风险 | 当前处理 | 后续建议 |
|---|---|---|
| 采购未来如果要支持分批收货 | 当前仍是单次收货模型 | 后续应做 `purchase_receipts` 子表，支持一次采购单多次收货、质检、差异入库 |
| 库存凭证数据库级幂等 | 当前用状态更新事务 + 凭证存在检查，浏览器/API 已验证不会重复入库 | 若上线 PostgreSQL，建议设计 `idempotencyKey`，而不是简单全局唯一 `sourceType/sourceRef` |
| UI 收货后没有显示库存凭证卡片 | 审计已能回读，但普通用户看不到凭证详情 | 后续采购页面可增加“入库凭证/库存位置”只读区 |
| 采购与应付账款尚未完整闭环 | 当前重点是库存入账，不是财务应付 | 后续应补采购应付、发票、付款、对账 |

## 反思结论

- 本包没有删除任何文件或任务。
- 本包没有改变原有 UI 风格，只补强真实业务链路和验收脚本。
- 本包纠正了“只到发货就算完成”的假闭环。
- 当前采购“下单到入库”小闭环可作为后续发货、换货、生产领料的验收模板继续复制。
