# 动态角色权限 UI 闭环执行记录

日期：2026-04-18  
主线：权限、角色、AI 隔离  
本包目标：把“动态角色权限”从后端能力补到团队管理页面，形成可操作、可保存、可回读的管理入口。

## 一、边界确认

- 本包只处理组织权限与团队管理入口，不改销售、仓储、生产、采购、货抵等交易逻辑。
- 不删除旧文件、不清理用户数据、不重置数据库。
- 遇到乱码按“三步法”：先确认含义，再判断层级，再最小修复。
- 本包发现 `role.routes.ts`、`types.ts`、`permissionRegistry.ts` 在 PowerShell 显示层可能出现乱码观感，但 Node 按 UTF-8 读取为正常中文，因此未做错误重写。

## 二、调研依据

- Casbin：RBAC 支持角色、权限、域/租户边界，适合服务端统一鉴权模型。
- OpenFGA：强调“按业务域建模，不做过度抽象的元模型”，适合后续做客户归属池、组织范围、对象级权限。
- NocoBase：角色、资源、动作、菜单访问分开配置，证明低代码/企业后台里“动态角色 + 权限点勾选”是成熟形态。
- Directus：角色和权限作为后台管理的一等对象，支持 Admin 权限与普通策略分离，适合本系统的管理员入口。

结论：爱劳达当前适合采用“内置角色兜底 + 自定义角色动态授权 + 前端菜单按权限显隐 + 后端 API 强制校验”的阶段性方案，不适合一次性引入过重的外部 IAM 服务。

## 三、改动清单

- `services/role.service.ts`
  - 新增角色与权限 API 客户端。
  - 支持读取角色、读取权限点、创建角色、更新角色。

- `pages/team/RoleManagementPanel.tsx`
  - 新增独立角色权限管理面板。
  - 支持角色列表、自定义角色创建、权限点搜索、权限勾选、数据范围勾选、启停状态保存。
  - 系统内置角色只读，避免误改基础权限。
  - 增加稳定 `data-testid`，便于后续浏览器级人工/自动验收。

- `pages/TeamManagement.tsx`
  - 团队成员创建表单从固定 5 个角色改成读取真实角色列表。
  - 新建成员按钮与角色管理面板只对 `team.write` 权限可见。
  - 新建用户时可选择自定义角色，保存后列表回读。

- `services/team.service.ts`
  - 创建成员的 `role` 从固定枚举放宽为字符串，匹配后端动态角色模型。

- `app/permissions.ts`
  - 补齐后端已有权限码，例如 `team.write`、`customers.create`、`orders.payment.verify`、`warehouse.write`、`procurement.write`。
  - 前端菜单显隐仍保留原有兼容读权限，不破坏现有页面入口。

- `scripts/role-management-ui-browser-audit-v1.cjs`
  - 新增浏览器级验收脚本。
  - 自动登录、进入团队管理、新建角色、新建自定义角色用户、浏览器内 API 回读角色和用户。

## 五、反思

- 方向没有偏离：本包仍在“权限、角色、AI 隔离”主线内，且没有触碰交易主链。
- 这不是补丁式隐藏问题，而是把动态角色能力补成了可操作入口，并留了验收锚点。
- 当前仍不是最终企业级 IAM：还缺权限变更审计明细、角色复制、角色模板、角色与组织/地区绑定、对象级权限策略。
- 当前前端权限码与后端权限码已经开始合流，但历史菜单仍有 `barter.read`、`risk.read`、`samples.read` 等前端兼容权限，后续需要统一一张权限注册表，避免双表漂移。

## 六、下一步建议

1. 做“权限注册表统一包”：从后端 `permissionRegistry` 生成或校验前端 `MENU_PERMISSION_BY_MODULE`，消灭权限码双写。
2. 做“AI 数据隔离包”：AI 助手调用前必须按当前用户权限过滤客户、订单、回款、库存和财务数据。
3. 做“角色审计包”：记录谁创建/修改/停用了角色，保存修改前后权限差异。
4. 做“组织范围包”：把 `dataScopes` 从展示字段推进到客户、公海、订单、仓储等真实数据查询过滤。
