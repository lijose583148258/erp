# 阶段 3 十包治理本轮改动边界 2026-04-21

## 1. 为什么要写这份边界

本轮目标不是继续堆功能，而是把重复出现的问题收束成可维护的边界：

1. 业务主链路只允许小范围、可解释、可回滚的修复。
2. 验收脚本只负责发现问题和留证据，不允许替代业务逻辑。
3. 运行入口固定为 `http://127.0.0.1:5001/`，不再用 `3000/5173` 判断当前系统。
4. 报告乱码必须按三步法判断，不能把终端显示层误判为源码损坏。
5. 后续修复先看这份边界，避免“哪里都能改，哪里都不知道坏”的屎山状态。

| 分层 | 文件范围 | 本轮职责 | 维护原则 |

## 3. 本轮没有做什么

1. 没有删除历史包、用户资料、数据库、备份。
2. 没有改品牌视觉风格。
3. 没有把旧系统入口重新接回主链路。
4. 没有把生产大页面一次性重写。
5. 没有声明“两个月稳定已完成”，两个月稳定只能靠后续每日证据累计。

## 4. 本轮关键修复点

### 4.1 生产 BOM 与完工

已修复的问题：

1. Excel 粘贴时首列物料名留空会被 `trim()` 吃掉，导致保密代号列错位。
2. 完工弹窗中后端报错曾被前端吞掉，容易造成“失败却像成功”的假闭环。
3. 原料只存在 `StockBalance`、没有 `ProductBatch` 时，库存扣减凭证应继续成立。
4. 浮点小数会造成库存足够但被误判不足。
5. 只耗用 1 种原料时，浏览器审计必须确认后端阻止完工。

### 4.3 报告乱码判断

本轮再次确认：

1. Node 用 UTF-8 解析审计 JSON 正常。
2. PowerShell 不指定 `-Encoding UTF8` 时，可能把中文路径和中文 stdout 显示成乱码，甚至导致 `ConvertFrom-Json` 误报。
3. 这属于报告读取层/终端显示层，不是源码层，不允许因此重写源码。

固定规则：

```powershell
Get-Content -LiteralPath '<report.json>' -Encoding UTF8 -Raw | ConvertFrom-Json
```

或使用：

```powershell
node -e "JSON.parse(require('fs').readFileSync('<report.json>','utf8')); console.log('OK')"
```

## 5. 后续维护时先看哪里

| 症状 | 先看文件/脚本 | 不要先做什么 |
| --- | --- | --- |
| 页面又像裸 HTML/CSS 丢失 | `scripts/check-runtime.ps1`、`dist/index.html`、`dist-entry-asset-audit-v1.cjs` | 不要先改页面样式 |
| 点击后出现乱码 | `effective-source-mojibake-gate-v1.cjs`、浏览器截图、API JSON | 不要直接重写文件 |
| 生产 BOM 完工异常 | `production-browser-audit-v1.cjs`、`production-mutation.service.ts`、`stock-movement.service.ts` | 不要绕过后端校验 |
| 客户/供应商搜索串库 | `supplier-permission-api-audit-v1.cjs`、CRM/采购服务层 | 不要把两边搜索合成一个大接口 |
| AI 可能越权回答 | `ai-security-regression.ts`、权限服务 | 不要只在前端隐藏按钮 |
| 旧入口又影响当前系统 | `active-source-inventory-v1.cjs`、`legacy-interface-disconnect-audit-v1.cjs`、`dual-port-audit-v2.cjs` | 不要用 3000/5173 验当前版 |
| 报告 JSON 解析失败 | 先用 Node UTF-8 验证，再用 PowerShell `-Encoding UTF8` | 不要把显示层乱码当源码坏 |

## 6. 禁止再犯清单

1. 禁止一次性重写大页面来修一个小 bug。
2. 禁止把测试探针逻辑写进业务组件。
3. 禁止只跑 `npm run build` 就说系统稳定。
4. 禁止旧入口、旧脚本、历史文件继续参与当前验收。
5. 禁止没有读回验证的写入测试。
6. 禁止无白名单的数据自动修复。
7. 禁止使用默认 PowerShell 编码判断中文文件是否损坏。
8. 禁止在没有 5001 运行证据时说“已经打开系统”。

## 7. 当前结论

本轮不是“完美完成”，而是把最容易反复的几类问题做了收束：

1. 生产 BOM 的真实浏览器输入和后端完工校验已经补强。
2. 发布核心、阶段 3 浏览器闸门、十包聚合审计均有通过证据。
3. 当前最大剩余风险不是单点 bug，而是继续拆大页面、继续降低脚本/报告噪声、继续累计长时运行证据。
4. 后续每一包都要沿用这份边界：少改业务，多留证据，先定位层级，再修正确层级。

## 8. 结构目录同步补充

本轮继续收口后，启动修复链已明确为两层：

1. `runtime-schema-repair.ts`：只处理表、字段、索引、schema 级幂等补齐。
2. `runtime-schema-repair-utils.ts`：只提供建表、加字段、建索引、白名单列检查等通用 helper。
3. `runtime-schema-stock-repair.ts`：只处理 `warehouses / locations / stock_balances / stock_entries / stock_movements` schema。
4. `runtime-schema-auth-repair.ts`：只处理 `auth_roles / auth_permissions / auth_role_permissions` schema。
5. `runtime-schema-barter-repair.ts`：只处理 `barter_settlements / barter_items / barter_valuation_snapshots / barter_offset_postings / barter_reversal_logs` schema。
6. `runtime-schema-production-repair.ts`：只处理 `production_boms / production_bom_items / inventory_cost_ledgers` schema。
7. `runtime-schema-receipt-repair.ts`：只处理 `purchase_receipts / shipment_receipts / receipt_discrepancy_cases / receipt_discrepancy_actions / receipt_tolerance_rules` schema 和默认规则 seed。
8. `runtime-data-repair.ts`：只处理白名单数据修复、默认仓库/库位、历史坏名清污。

这次把生产历史 mojibake 白名单修复从 schema 层移到 data 层，避免 schema 修复文件继续变成万能补丁容器。
后续如继续拆基础字段扩容，应复用 `runtime-schema-repair-utils.ts`，不要在各子文件复制一套 helper。
