# 业务数据指纹共享库收口记录 2026-04-22

## 结论

- 本包目标：降低刚新增的业务数据指纹闸门维护成本，避免以后重启持久化、迁移演练、备份恢复各自复制一套表口径。
- 已完成：把 43 张业务表的指纹规则抽到共享库。
- 备份恢复指纹脚本已改为调用共享库，行为保持不变。
- 当前验证结果：Phase3 19/19 passed，Release 26/26 passed。

## 为什么要做

- 业务数据指纹是阶段 3 的关键底座。
- 如果每个审计脚本都复制一份表清单和金额字段，后续一定会出现：
  - 某个脚本漏表。
  - 某个脚本字段口径变旧。
  - 某个脚本把审计日志误纳入业务数据。
  - 某个脚本恢复后看似通过但口径不一致。
- 这类问题就是“越修越乱”的来源，所以要尽早收束为一个共享入口。

## 新增共享库

- `scripts/lib/business-data-fingerprint.ts`

职责：

- 定义业务数据指纹表清单。
- 定义核心金额、数量、库存、生产、货抵、应收调整等聚合字段。
- 通过后端已生成的 Prisma Client 读取任意 SQLite 文件。
- 计算业务数据 hash。
- 比较两个业务数据指纹的表数量、记录数和聚合值。
- 统一路径标准化。

## 改造脚本

- `scripts/backup-restore-data-fingerprint-audit-v1.ts`

变化：

- 移除内嵌的 43 表清单、Prisma 读取、hash 计算、指纹比较逻辑。
- 保留 API 编排：
  - 登录。
  - 创建备份。
  - 恢复备份。
  - 写报告。
- 调用共享库完成业务数据指纹采集和比较。
- 脚本版本从 `1.0` 升级到 `1.1`。

## 当前共享口径

- 业务表数量：43。
- 不纳入严格业务指纹的表：`audit_logs`。
- 原因：备份恢复操作本身可能产生审计流水，把它纳入严格一致性会造成误判。
- 审计日志仍由错误日志静默窗口、业务拒绝日志分类、AI 安全等其他闸门覆盖。

## 后续制度

- 后续凡是需要判断“业务数据有没有丢、恢复后是否一致、重启后是否一致、迁移后是否一致”，必须优先复用 `scripts/lib/business-data-fingerprint.ts`。
- 不允许在新脚本里复制一套新的业务表清单。
- 如果业务模型新增关键表，先更新共享库，再跑：
  - `npm run audit:backup-restore:fingerprint`
  - `npm run verify:phase3`
  - `npm run verify:release`
