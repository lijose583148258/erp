# 主线防跑偏执行制度

日期：2026-04-18

## 一句话总目标

爱劳达是一个本地离线可稳定运行、后续可平滑迁移服务器的 ERP+CRM 系统，不是智仔，不是演示站，不是只靠页面好看的空壳。

所有后续改动都必须服务这个目标。

## 当前系统定位

- 产品：爱劳达 ERP+CRM。
- 运行优先级：本地单机稳定运行第一，服务器部署迁移第二。
- 技术主线：React + Vite + TypeScript 前端，Node + Express + Prisma 后端，SQLite 本地运行库。
- 业务主线：客户/供应商主数据、销售订单、回款、采购、仓储、生产 BOM、货抵支付、物流、财务、权限、备份恢复。
- 设计风格：保留当前轻玻璃、蓝色主调、圆角工作台风格，只做统一和稳定化，不大换皮。

## 每包开工前必须回答

每一包任务开始前，必须先写清楚 6 个问题：

1. 本包修的是哪条主线？
2. 本包不修什么？
3. 会影响哪些前端页面？
4. 会影响哪些后端接口？
5. 会影响哪些数据库表或运行数据？
6. 通过什么证据才算完成？

如果这 6 个问题答不清楚，不能直接改代码。

## 防跑偏边界

### 绝对不能偏离

- 不能把爱劳达和智仔目录、端口、页面、启动链混在一起。
- 不能把 `HTTP 200` 当成业务闭环。
- 不能把 `npm run build` 当成上线完成。
- 不能只改前端隐藏按钮，不改后端权限。
- 不能只做 API 成功，不做数据库回读。
- 不能只做截图漂亮，不做输入、保存、刷新回读。
- 不能把终端乱码直接当源码乱码，必须先按 UTF-8 直接读取验证。
- 不能删除历史文件、用户数据、数据库、备份资料。
- 不能为了快速修复大面积重写核心文件。

### 允许做

- 允许新增治理文档和验收脚本。
- 允许新增小型兼容层，降低旧入口风险。
- 允许新增权限点、API 验收、浏览器点测脚本。
- 允许拆分过大的页面、controller、service，但必须先保留原有行为。
- 允许对旧文件降权或隔离，但不能无证据删除。

## 六条主线

### 主线 1：运行稳定与启动链

目标：

- 本地 5001 稳定启动。
- 页面必须是爱劳达。
- 数据库路径、备份路径、日志路径明确。
- 所有长命令 5 分钟内必须有结论。

验收：

- `GET http://127.0.0.1:5001/` 返回爱劳达标题。
- `GET http://127.0.0.1:5001/api/health` 返回 200。
- Node 进程必须是 `backend/dist/server.js`。
- 不误杀其他系统进程。

### 主线 2：权限、角色、AI 隔离

目标：

- 后端是权限真源头。
- 前端只按权限清单展示菜单和按钮。
- 自定义角色可创建、授权、禁用。
- AI 不能绕过角色权限读取数据。

验收：

- 登录返回权限清单。
- 动态角色授权前拒绝、授权后放行、禁用后旧 token 失效。
- 不同角色浏览器真实切换不崩。
- AI 问敏感数据时按当前角色拒绝或脱敏。

### 主线 3：客户/供应商主数据

目标：

- 一家公司一条主数据。
- 支持中/英/越多名称。
- 支持多地址、多联系人。
- 客户和供应商规则统一，但搜索时不能互相污染。

验收：

- 新建、编辑、搜索、刷新回读不丢。
- 地址和联系人独立保存。
- 客户池、公海/私海、内销/分销权限边界清楚。

### 主线 4：钱货业务闭环

目标：

- 销售订单、分批回款、回款核验、财务状态一致。
- 采购订单、分批入库、收发货差异、库存凭证一致。
- 货抵支付/换货贸易支持分批抵扣。

验收：

- 订单金额、已回款、未回款、状态一致。
- 库存数量、批次、凭证一致。
- 货抵协议、分批交换、抵扣余额一致。

### 主线 5：生产 BOM 与仓储

目标：

- 适配胶水、树脂、涂料等化工配方。
- 支持至少 10 种原料的 BOM 网格录入。
- 允许用代号保护配方。
- 完工必须扣原料、入成品、生成成本凭证。

验收：

- 少耗料必须被后端阻止。
- 原料齐套后才能完工。
- 原料扣减、成品入库、成本凭证三者一致。
- 仓库/库位默认规则稳定：`WH-MAIN`、`LOC-RAW`、`LOC-FG`、`LOC-WIP`、`LOC-SCRAP`。

### 主线 6：UI、离线、EXE、上线迁移

目标：

- UI 统一到 token、组件、页面模板。
- 禁止新增 CDN、Google Fonts、远程图标依赖。
- EXE 壳能本地运行。
- 后续服务器部署不重做业务逻辑。

验收：

- build 通过。
- 离线资源检查通过。
- 浏览器逐页无白屏、无核心乱码、无明显布局脱钩。
- 备份恢复演练通过。

## 三阶段推进

### 阶段 A：保命稳定

先修会导致系统打不开、数据丢失、权限越权、库存/金额不一致的问题。

### 阶段 B：业务闭环

再修真实业务流程：创建、审批、分批、核验、凭证、刷新回读。

### 阶段 C：治理美化

最后做 UI 统一、大文件拆分、文档清洁、warning 清理。

任何时候不能为了 C 阶段美化破坏 A/B 阶段稳定。

## 每包完成标准

每包必须至少有以下证据：

- 静态证据：相关 TypeScript/build/lint/db audit。
- API 证据：写入、读取、状态变化、失败场景。
- 浏览器证据：能打开、能输入、能保存、能刷新回读。
- 数据证据：数据库或 API 回读不丢字段、不丢金额、不丢库存。
- 治理证据：治理中心记录“改了什么、为什么、证据是什么、还缺什么”。

## 反思制度

每包结束必须自动反思：

1. 有没有偏离当前系统定位？
2. 有没有把显示层问题误判为源码问题？
3. 有没有只修页面没修接口？
4. 有没有只修接口没修数据？
5. 有没有旧入口仍在影响当前运行？
6. 有没有报告假绿？
7. 有没有新增维护成本？
8. 下一包最值钱的动作是什么？

如果答案里有高风险项，下一包必须先处理高风险项。

## 当前下一包推荐

下一包应继续做权限治理而不是跳去新功能：

1. 做角色管理 UI：角色列表、权限分组勾选、启用/禁用、保存回读。
2. 继续迁移旧 `authorize(...)` 路由到 `authorizePermission(...)`。
3. 给 AI 助手加权限上下文过滤，避免无权限数据泄露。
4. 再进入数据范围：我的客户、部门客户、全部客户、公海/私海池。

这样不会跑偏，因为它承接上一包动态 RBAC，而不是突然去扩新模块。
