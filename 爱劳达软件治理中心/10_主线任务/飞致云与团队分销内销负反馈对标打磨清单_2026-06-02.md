# 飞致云与团队分销/内销负反馈对标打磨清单

日期：2026-06-02

## 1. 对标定位

飞致云/FIT2CLOUD 不能被当作传统 ERP 竞品直接照抄。它的参考价值在于产品化能力：安装部署、开源社区、企业版授权、BI、测试管理、运维安全审计、知识库和智能问数。对爱劳达来说，它是“平台化交付质量”的标杆，不是“销售、采购、库存、货抵业务规则”的标杆。

团队分销和内销系统才是业务闭环对标对象。它们的核心负反馈集中在：销售与库存断裂、渠道价格失控、客户归属不清、权限边界模糊、经销商库存不可见、内销团队互抢客户、报价到订单到回款口径不一致。

## 2. 外部负反馈提炼

### 2.1 飞致云类产品化负反馈

| 反馈类别 | 容易出现的问题 | 对爱劳达的约束 |
| --- | --- | --- |
| 部署与升级 | 离线安装、容器升级、数据备份、配置域名等步骤一旦不清楚，用户会卡在启动和登录前 | 纯净包必须可移动、可启动、可自检；启动失败要给明确原因 |
| 权限与审计 | 运维类系统强调用户、角色、资产、会话、操作审计；权限弱会直接失去企业信任 | 子账号、角色授权、敏感资料访问、审计日志必须形成闭环 |
| BI 与自助分析 | DataEase 类产品证明客户希望自己配置报表，而不是只看固定 Dashboard | P3 必须保留 BI/readiness/预警蓝图，后续向自助报表演进 |
| 测试平台化 | MeterSphere 类产品说明企业级交付依赖测试计划、缺陷和报告闭环 | 每次打包必须绑定自动审计报告，不能只靠人工感觉 |
| 商业化 | 社区版/企业版、授权、支持服务边界清晰，降低售前误解 | 后续要明确本地版、团队版、云 SaaS 版能力边界 |

### 2.2 团队分销/内销负反馈

| 反馈类别 | 典型负反馈 | 当前系统必须防住的问题 |
| --- | --- | --- |
| 客户归属 | 内销销售互抢客户，经理无法判断谁负责、谁跟进、谁有提成 | CRM 必须支持负责人、协作人、客户池、公海/私海、移交审计 |
| 渠道冲突 | 经销商价、内销价、客户特价互相覆盖，报价和开票不一致 | 价格策略要有来源、有效期、审批、覆盖优先级 |
| 库存承诺 | 销售看到的是库存余额，但实际已被订单、采购、生产或货抵占用 | 可售库存必须区分现存、锁定、在途、质检、已分配、可承诺 |
| 经销商库存 | 厂家只看自己出库，看不到经销商二级库存和动销 | P3 BI 要预留渠道库存、动销、滞销和补货预警读模型 |
| 回款与信用 | 销售只关心下单，财务发现超信用、超账期、回款承诺失效 | 订单确认必须联动授信、逾期、冻结、回款承诺和财务审批 |
| 供应商敏感数据 | 销售为了跟单需要采购状态，但不应直接看到供应商联系人、地址、采购价格 | 已按“销售看 B2B 状态，不看供应商主数据”收口，后续不得回退 |
| 报表不可信 | CRM、ERP、财务、仓储各有口径，最后员工又导出 Excel 处理 | 汇总报表必须能下钻到原始单据、凭证和审计记录 |
| 移动端作业 | 外勤销售、仓库平板没有 hover，按钮找不到，字小不能缩放 | 触屏必须强制显示操作入口，关键字段对比度和密度要可配置 |

### 2.3 货物兑换/货抵业务负反馈

| 反馈类别 | 典型负反馈 | 对系统的要求 |
| --- | --- | --- |
| 估值争议 | 换入货物价值、换出抵扣金额、税费和汇率不透明 | 货抵协议必须记录估值依据、币种、汇率、费用和审批痕迹 |
| 库存错位 | 货抵货物入库了，但财务未过账；或财务抵扣了，但仓库未收货 | 货抵必须保持库存凭证、应收冲抵、结算过账同链路可追溯 |
| 多批次执行 | 一份协议分多批交付时，余额、批次、过账和冲销容易混乱 | 批次执行必须支持分批、剩余额、重复提交幂等和冲销 |
| 合同口径 | 销售、仓库、财务对同一货抵单理解不同 | 页面必须展示协议、执行批次、库存、回款/冲抵四个视角 |

## 3. 纳入 P0/P1/P2/P3 的统一判断

### P0：安全与可登录

必须先保证子账号可创建、可登录、可禁用、可改密；默认密码和 JWT fallback 不能作为生产路径；销售账号不得越权读取供应商主数据。

验收标准：
- 管理员能创建员工账号并分配角色。
- 员工登录后只能看到被授权模块。
- 销售访问供应商主数据接口返回 403，但能看到采购/B2B 协同状态。

### P1：业务闭环

必须保证内销、分销、采购、库存、回款、货抵之间不是“页面堆砌”。每条链路要有状态、责任人、审批点、异常处理、审计。

验收标准：
- 报价/订单/发货/回款口径一致。
- 采购到货、库存入库、财务应付/成本有凭证。
- 货抵协议、批次、库存、冲抵、冲销能回读。

### P2：高频可用性

必须把“精致 UI”改成“能干活的 UI”：紧凑模式、强对比度、触屏不依赖 hover、错误提示指向具体行和字段。

验收标准：
- 表格一屏密度提高，关键按钮触屏可见。
- 禁止强制禁用浏览器缩放。
- 关键字段使用业务语言，不出现技术错误文案。

### P3：平台化与商业化

必须把飞致云式产品化能力转化为爱劳达自己的平台底座：纯净包、启动自检、可观测性、BI、工作流、PostgreSQL 迁移准备、版本与回滚策略。

验收标准：
- P3 readiness 能说明数据库、工作流、BI、预警、Metrics 当前状态。
- 打包后 E 盘纯净运行版可启动、可登录、可跑核心链路。
- 发布包包含审计报告，保留一个可回滚备份即可。

## 4. 对当前系统的直接结论

1. 不能再把“销售可看供应商基础目录”当作默认正确。更合理边界是：销售只能看采购/B2B 协同状态，供应商主数据由采购、仓库、财务、经理管理。
2. 当前 Dashboard 不能代表经营分析能力，后续要向渠道库存、客户流失、库存呆滞、超信用、超账期、报价命中率、回款承诺失效等主动预警演进。
3. 团队管理不应只是角色列表，必须形成“账号生命周期 + 角色授权 + 数据范围 + 审计 + 禁用/离职交接”闭环。
4. 货抵不能只看作库存模块功能，它横跨销售、采购、仓储、财务和合同，后续任何重构都要保持四视角一致。
5. PostgreSQL 主从、工作流引擎、BI 自助分析属于 P3 平台化，不应阻塞当前本地纯净包，但必须在 readiness 和蓝图中保留明确状态。

## 5. 后续打磨规则

| 触发条件 | 处理方式 |
| --- | --- |
| 页面文案、对比度、hover、密度问题 | 优化 |
| 单接口权限缺口、错误提示不准、审计缺字段 | 优化 |
| 同一业务被多个模块重复维护且口径不同 | 重构 |
| 库存、回款、货抵、审批存在跨模块状态不一致 | 重构 |
| SQLite 本地版无法满足云 SaaS 并发 | 保留本地版，另起 PostgreSQL 云端架构重构 |
| Dashboard 固定图表无法满足管理分析 | 先建 BI 宽表/readiness，再逐步重构为自助分析 |

## 6. 当前已纳入验证的事项

- 供应商权限专项：销售禁止直接读取供应商主数据，管理员/经理/仓库/财务可按授权读取。
- 商业化平台专项：readiness、工作流定义、工作流实例、BI summary、alert run、notification、metrics 已纳入 API 审计。
- 阶段 3 总闸门：以上专项已挂入 P3 readiness 审计链，打包前必须重新跑通。
