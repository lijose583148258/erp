# 阶段 3 调整单成本台账同事务收口记录

日期：2026-04-27

目标：把库存 / 生产调整单从“调整业务成功后再尝试补写成本台账”收口为“调整业务、库存数量、成本台账同一事务闭环”，并用 E 盘纯净运行版和运行库真实回读证明。

## 本包结论

- 已移除 `AdjustmentController` 中调整单创建、审核、反冲后的外层补写台账逻辑，不再吞掉成本台账写入失败。
- 已在 `AdjustmentService` 的事务内写入 `inventory_cost_ledgers`，库存 / 生产调整单与成本台账一起成功或一起失败。
- 已修复库存 / 生产调整单字段归属错位：`targetId` 不再被错误回退成 `orderId`，避免批次 ID 被写入订单外键。
- 已新增真实审计脚本 `npm run audit:adjustment:cost-ledger`，覆盖库存调整减少、反冲恢复、批次库存回读、成本台账回读、测试数据清理。
- 已重新打包并刷新到 `E:\爱劳达纯净系统`，当前入口仍为 `http://127.0.0.1:5001`。

## 真实根因

本轮新增审计第一轮失败，失败不是“环境卡住”，而是暴露出一个真实业务 BUG：

- 请求库存调整单时传入 `targetId=batchId`。
- 控制器旧逻辑同时执行 `resolvedOrderId = orderId ?? targetId` 和 `resolvedBatchId = batchId ?? targetId`。
- 对库存 / 生产域来说，`targetId` 应该只代表批次，不应该代表订单。
- 结果是 `adjustment_records.order_id` 被写成批次 ID，SQLite 外键检查失败。

修复原则：

- 财务域：`targetId` 可以回退为 `orderId`。
- 库存 / 生产域：`targetId` 只能回退为 `batchId`。
- 不绕过外键，不放宽数据库约束。

## 反思

- 本轮方向没有偏离。新增审计不是多余脚本，它抓到了一个隐藏字段归属 BUG，这类问题靠编译和普通页面打开不会暴露。
- “同事务化”不能只看代码结构，必须用 API 写入 + SQLite 回读证明，否则仍可能是假闭环。
- 控制器里的字段回退逻辑属于高风险区域，后续凡是出现 `targetId`、`orderId`、`batchId`、`customerId` 混用，都要单独做字段归属审计。
- 旧的 `backend/src/controllers/adjustment/adjustment-ledger.ts` 现在已不是主链路，不应再被新代码依赖；后续需要纳入旧接口隔离台账，而不是立即删除。
