# 系统总治理路线图（2026-04-16）

状态：当前总控基线  
适用范围：爱劳达 ERP + CRM 全项目  
执行原则：从现在开始，按 6 条主线、3 个阶段、1 套验收制度推进；遇到乱码默认开启“三步法 + 禁乱码闸门”。

## 一、总目标

把当前系统从“局部可用、局部补丁化”治理成：

- 运行入口单一
- 新旧代码边界清楚
- 主业务模型统一
- 页面交互范式统一
- 浏览器验收与 API 回读制度化
- 本地离线可稳定运行，再进入 EXE 和后续服务器迁移

## 二、6 条主线

### 主线 A：运行底座治理

目标：

- 统一正式运行链
- 固定稳定端口、稳定启动、稳定停止
- 固定超时判定与卡住处理
- 固定运行库路径与健康检查

产出：

- 唯一运行链定义
- 运行 / 停止脚本基线
- 5 分钟超时制度
- 健康检查与恢复手册

### 主线 B：新旧入口与旧坏文件治理

目标：

- 每个模块只认一个主入口
- 旧页面、兼容壳、桥接层、归档文件分层管理
- 降低搜索误判、补丁误判、入口误判

产出：

- 活跃入口清单
- 兼容壳清单
- 待隔离文件清单
- 待正名文件清单

### 主线 C：业务模型统一

目标：

- 全系统尽量统一成少数稳定业务范式

统一范式：

- 主单 + 子记录
- 主数据 + 子实体
- 工作台 + 当前对象详情 + 全局台账

当前重点：

- 订单 + 回款记录
- 货抵协议 + 批次执行
- 客户主数据 + 多名 + 多地址 + 多联系人 + 审计
- 供应商主数据后续跟齐客户规则，但保持检索边界分离

### 主线 D：前端交互范式统一

目标：

- 不再让每个模块各自长成完全不同的交互逻辑

当前范式：

- 工作台型：动作区 + 当前对象详情 + 全局台账
- 主数据型：简版新建 + 详情页分区 + 高级字段折叠
- 明细密集型：头部表单 + Excel 风格明细网格
- 执行流水型：主单汇总 + 子流水记录

### 主线 E：编码、多语言与文案清污

目标：

- 清除源码层、运行层、审计层的乱码和文案脱钩
- 建立长期有效的乱码治理制度

默认制度：

- 遇到乱码，默认开启“三步法”
- 修完后，默认开启“禁乱码闸门”

### 主线 F：真实验收与稳定性闭环

目标：

- 从“页面能打开”升级为“真实业务闭环已验证”

标准动作：

- 静态检查通过
- 浏览器级真实点击通过
- API 回读通过
- 必要时数据库核对通过

## 三、3 个阶段

### 阶段 1：先把地基做硬

顺序：

1. 运行底座治理
2. 新旧入口收口
3. 编码与文案制度化
4. 审计脚本制度化

目标：

- 系统先“不乱”
- 入口先“单一”
- 验收先“可信”

### 阶段 2：把主业务链做统一

建议顺序：

1. collections
2. adjustment
3. salesOrders
4. procurement
5. risk / holds / milestones
6. customer / supplier 主数据

目标：

- 高价值链路先统一
- 让系统逐步形成可复制的模块模板

### 阶段 3：为长期本地运行与部署做准备

顺序：

1. 离线能力核实
2. 备份 / 恢复 / 迁移演练
3. EXE 打包前置清单
4. 本地长时间稳定运行验证
5. 服务器迁移前置条件

目标：

- 不是先“包装”
- 而是先“稳定”

## 四、1 套验收制度

每一包必须过以下 4 层：

1. `tsc --noEmit`
2. `npm run build`
3. 浏览器级真实点击
4. API 回读

必要时追加：

5. 数据库核对
6. 恢复验证
7. 并发 / 冲突 / 幂等校验

不允许：

- 只看页面打开
- 只看命令退出码
- 只看单一截图

## 五、乱码治理制度

### 1. 三步法默认开启

只要出现乱码、文案异常、文案脱钩，一律执行：

1. 先翻译
2. 再判断
3. 再修复

判断层必须明确：

- 源码文件污染
- 旧 bundle / 旧 dist
- 错入口 / 错页面
- 显示层误判
- 测试脚本误判
- API 返回正常但前端映射错误

### 2. 禁乱码闸门默认开启

修复后必须验证：

- 关键正确文案必须存在
- 典型乱码关键词必须不存在

### 3. 适用范围

- 页面标题
- tab 标签
- 表格列名
- 按钮文案
- toast 提示
- 模态框标题
- 导出文件名
- 浏览器审计脚本
- API 显示映射

## 六、当前优先级判断

当前不再继续零碎补点，统一按以下优先顺序推进：

1. 运行底座与入口治理
2. adjustment 接入与 collections 相同的制度化治理
3. salesOrders 双轨改造稳定化
4. procurement 真实新增 / 搜索 / 保存 / 回读链路
5. risk / holds / milestones 口径统一
6. customer / supplier 主数据深化
7. 离线运行、备份恢复、EXE 和迁移准备

## 八、还必须补齐的治理细节

### 1. 模块状态分级表

每个模块都要挂一个统一状态：

- `green`：结构清楚、页面干净、浏览器闭环和 API 回读都通过
- `yellow`：主链可用，但仍存在旧入口、文案污染或交互不统一
- `red`：入口不清、真实闭环未通、金额或状态存在高风险

### 2. 重写 / 修补判定规则

后面每个包都要先判断：

- 什么值得继续修补
- 什么应该重写

### 3. 证据包标准

以后每一轮验收都要有统一证据包：

- 审计脚本
- 报告 JSON
- 关键截图
- 关键记录 ID

### 4. 冻结与解冻规则

满足以下任一条件时，先冻结当前包，进入定位，不继续叠改：

- 稳定链未确认
- 入口未确认
- 运行超过 5 分钟未判定
- 金额、状态、回读出现冲突

### 5. 回退与恢复规则

必须给每一包都明确：

- 这轮改坏怎么退
- 运行挂了怎么恢复
- 数据异常怎么核对

### 6. 模块负责人视角

每个模块至少区分三种视角：

- 使用者看什么
- 维护者改什么
- 审计者验什么

### 7. 真实业务口径词典

后面要逐步沉淀统一词典，尤其是金额和状态：

- 已收 / 待核销 / 未收
- 承诺 / 失约 / 取消
- 争议 / 处理中 / 已解决
- 过账 / 冲销 / 释放
- 主单 / 子记录 / 批次执行

### 8. 模块完成定义

以后“做完”必须同时满足：

- 结构落位
- 文案干净
- 真实点测通过
- API 回读通过
- 已纳入总台账

### 9. 长期运行前置条件

在进入 EXE、本地两个月稳定运行、服务器迁移前，必须先确认：

- 正式入口唯一
- 运行库路径明确
- 备份恢复能演练
- 浏览器级闭环覆盖核心模块
- 关键金额链无未解释冲突

### 10. 后续总控节奏

每次推进都遵循：

1. 先定当前包属于哪条主线
2. 先定它处于哪个阶段
3. 先定是修补还是重构
4. 再执行
5. 最后附证据包
