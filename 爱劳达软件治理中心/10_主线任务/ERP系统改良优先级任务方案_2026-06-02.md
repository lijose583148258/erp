# ERP 系统改良优先级任务方案

日期：2026-06-02

## 1. 总目标

这轮改良不以“增加功能数量”为目标，而以“业务闭环可信、员工可用、后续可扩展”为目标。

后续所有任务按四个问题判断：

1. 是否影响钱、货、权限、审批、客户数据范围。
2. 是否能形成创建、审核、过账、回读、冲销、审计的完整证据链。
3. 是否能被普通员工在高频场景里看懂、点到、查到。
4. 是否只是局部体验或校验问题，还是已经暴露模型层缺陷，需要重构。

## 2. 优先级总表

| 优先级 | 目标 | 处理方式 | 打包要求 |
| --- | --- | --- | --- |
| P0 | 登录、账号、权限、库存、财务金额不能错 | 必须先修，必要时重构 | 未通过不得打包 |
| P1 | 货物兑换、销售、采购、出入库、回款形成闭环 | 以证据链补强为主 | 通过主业务链后打包 |
| P2 | 前端中文、排版、紧凑模式、移动端触屏可用 | 局部优化为主 | 通过浏览器抽检后打包 |
| P3 | BI、预警、审批引擎、PostgreSQL 云端化 | 先设计蓝图，分阶段重构 | 不阻塞本地纯净包 |

新增对标约束：
- `飞致云与团队分销内销负反馈对标打磨清单_2026-06-02.md` 已纳入本方案。飞致云/FIT2CLOUD 作为产品化、部署、BI、测试、权限审计和商业化边界参考；团队分销/内销作为销售、客户归属、渠道价格、库存承诺、回款信用和经销商库存闭环参考。
- 后续判断优化或重构时，不再只看单页面表现；必须同时判断角色边界、业务链路、数据口径、打包迁移和审计证据。

## 3. P0：可信底座

### P0-1 账号与员工子账号

问题：
- 用户明确反馈无法使用密码登录，也无法给员工开个人登录账户。
- 账号系统如果不可信，后续权限、审计、数据归属都不可信。

任务：
- 确认管理员能创建员工账号。
- 员工账号必须能独立登录。
- 改密后旧 token 必须失效。
- 停用账号、停用角色后必须无法继续访问。
- 员工只能看到自己角色和数据范围内的数据。

验收证据：
- API 链路：管理员登录 -> 创建员工 -> 员工登录 -> 修改密码 -> 旧 token 失效 -> 新密码登录。
- 浏览器链路：团队管理页能创建、编辑、停用员工。
- 数据库回读：users、roles、user_roles、refresh_tokens 状态一致。

优化或重构判断：
- 如果只是提示、按钮、字段映射问题，做优化。
- 如果 token、角色、数据范围彼此不一致，必须重构认证和授权边界。

### P0-2 库存可信底座

问题：
- ERP 的底层可信度取决于库存流水是否能回读。
- 不能只看单据状态，必须看到库存凭证和余额变化。

任务：
- 所有真实改库存的动作必须落 stock_entries 和 stock_movements。
- 货物兑换、采购收货、销售出库、生产入库、调整单都要能按 sourceType/sourceRef 回查。
- 禁止无来源单号的手工库存变更。
- 负库存必须有明确拦截或审批策略。

验收证据：
- 每个业务单据能回读库存凭证号、库位、批次、变动前、变动量、变动后。
- 重复提交不会重复扣库存。
- 冲销会产生反向库存凭证，而不是直接删除原记录。

优化或重构判断：
- 如果只是缺显示字段，前后端补 readback 即可。
- 如果库存余额是直接改数、没有流水，必须重构。

### P0-3 金额与回款可信

问题：
- 财务类系统不能只显示“已付款/已抵扣”，必须能解释金额来源。

任务：
- 销售订单、回款、货抵、调账都要统一计算未回款金额。
- payment_records、receivable_adjustments、barter_offset_postings 必须能互相追溯。
- 过账、冲销必须触发回款状态重算。

验收证据：
- 订单 finalAmount、paidAmount、receivableAdjustmentAmount、paymentStatus 与付款记录聚合一致。
- 货抵过账后能看到 paymentRecordId。
- 货抵冲销后 paymentRecord 状态反向变化，订单回款状态同步变化。

优化或重构判断：
- 如果聚合公式缺少字段，做优化。
- 如果多个模块各算各的未回款，必须抽出统一财务计算服务。

## 4. P1：主业务闭环

### P1-1 货物兑换系统证据链

问题：
- 当前货抵已经有协议、批次、审批、过账、冲销，但用户需要看到“这一笔到底影响了什么”。

任务：
- 在后端 getSettlement 或新增 evidence 接口返回：
  - 协议进度：协议总额、已抵、待抵。
  - 货物明细：对方交付、我方抵扣。
  - 估值快照：参考价格、来源、估值时间。
  - 财务证据：offsetPostings、paymentRecord。
  - 库存证据：barter_receipt、barter_issue、reversal stock entries。
  - 审计证据：创建、审核、过账、冲销日志。
- 前端批次流水卡片显示“证据链”区域。

验收证据：
- 创建协议 -> 创建批次 -> 审核 -> 过账 -> 回读能看到付款记录、库存凭证、审计日志。
- 冲销后能看到反向库存凭证和冲销原因。

优化或重构判断：
- 如果底层数据已存在，只补 readback 和前端展示。
- 如果过账没有库存或财务落账，必须重构过账服务。

### P1-2 销售订单到回款闭环

任务：
- 销售订单草稿、提交、发货、签收、收款、调账、RMA 必须可追踪。
- 订单详情页必须显示钱货链路：
  - 发货记录。
  - 签收差异。
  - 回款记录。
  - 货抵记录。
  - 调账记录。
  - RMA 记录。

验收证据：
- 任一订单能解释“还欠多少钱、货发到哪、有没有差异、有没有售后”。

### P1-3 采购到入库闭环

任务：
- 采购订单、部分收货、质检差异、供应商维度必须可回读。
- 采购收货必须产生库存凭证。
- 多次收货不能超收，除非走容差/审批。

验收证据：
- 采购单能看到已收、未收、差异、库存凭证。

### P1-4 生产型 ERP 闭环

任务：
- 工单创建时必须锁定 BOM/配方版本快照。
- 领料、报工、入库、成本台账必须能串起来。
- 禁止完工后因为 BOM 被改，历史成本解释不清。

验收证据：
- 任一工单能回读 BOM 快照、领料、产出、成本差异。

优化或重构判断：
- 如果只是页面缺字段，局部优化。
- 如果工单没有 BOM 快照，必须重构生产模型。

## 5. P2：前端与员工体验

### P2-1 中文与翻译一致性

任务：
- 清理页面中英文混用、旧模块命名、技术化错误提示。
- 业务提示必须说人话，例如“第 3 行商品数量不能大于可用库存”，而不是“参数错误”。

验收证据：
- 高频模块页面无乱码、无未翻译英文、无旧模块名。

### P2-2 高频数据密度

任务：
- 保留现代视觉，但提供紧凑模式。
- 表格行高、padding、圆角、卡片间距要适合销售、仓管、财务连续录单。

验收证据：
- 1366x768 下核心表格能看到足够多行。
- 表格操作按钮不因为 hover 才出现。

### P2-3 触屏与移动端

任务：
- 触屏设备强制显示操作按钮。
- 禁止依赖 hover 才能编辑、删除、查看。
- 不禁用页面缩放。

验收证据：
- iPad/手机宽度下关键按钮可见、可点、文字不重叠。

### P2-4 可访问性与对比度

任务：
- 关键辅助文字从过浅的 slate-400 提升到更可读层级。
- 错误、库存不足、逾期、冻结等严肃状态必须更醒目。

验收证据：
- 强光/低视力场景下关键数字和状态可读。

## 6. P3：平台化与商业化能力

### P3-1 PostgreSQL 与 SaaS 数据架构

任务：
- 本地版继续支持 SQLite。
- 云端 SaaS 版规划 PostgreSQL 主从、备份、迁移脚本。
- 明确租户模型：短期可混合隔离，长期建议 tenantId 逻辑隔离 + 关键大客户物理隔离。

验收证据：
- 有 PostgreSQL ADR。
- 有迁移脚本、环境变量、备份恢复流程。
- 关键查询都带租户或数据范围边界。

### P3-2 审批流引擎

任务：
- 从状态机升级为可配置工作流：
  - 多级审批。
  - 会签/或签。
  - 金额、客户风险、库存负数等条件分支。
  - 审批超时和撤回。

验收证据：
- 单据不能绕过审批直接过账。
- 审批记录和业务过账记录分离。

### P3-3 BI 与主动预警

任务：
- 建立运营宽表或报表服务。
- 加入库存呆滞、客户流失、逾期回款、异常毛利、负库存风险预警。
- 增加分销/内销管理指标：客户归属变更、报价命中率、渠道价格覆盖、经销商库存、动销、窜货/串单风险、超信用和超账期。
- 预警通过站内信，后续扩展企业微信/钉钉/邮件。

验收证据：
- 管理者能看到可行动清单，而不是只看静态 dashboard。

### P3-4 可观测性与运维

任务：
- 增加 metrics endpoint。
- 规划 OpenTelemetry/APM。
- 打包版本必须有启动健康检查、日志路径、端口冲突处理。

验收证据：
- 本地运行失败能快速定位是端口、数据库、迁移、前端资源还是权限问题。

## 7. 执行节奏

### 第一轮：可打包稳定版

必须完成：
- P0-1 账号与员工子账号验证。
- P0-2 库存凭证回读基本验证。
- P0-3 货抵过账和回款状态回读。
- P1-1 货物兑换证据链展示。
- P2-1/P2-2 高频页面中文和布局抽检。

完成后：
- 前端 build。
- 后端 build。
- release core verification。
- clean runtime audit。
- 重新打纯净包。

### 第二轮：主业务链增强版

必须完成：
- 销售订单钱货链路。
- 采购部分收货链路。
- 生产工单 BOM 快照方案和最小实现。

完成后：
- 跑销售、采购、生产、库存、回款专项脚本。

### 第三轮：平台化重构版

必须完成：
- PostgreSQL 双模式部署方案。
- 工作流引擎 ADR。
- BI 宽表/报表服务设计。
- metrics 与日志治理。

该轮不应混进第一轮纯净包，避免把本地可运行版本拖成半成品。

## 8. 每次改良的验收门槛

任何任务完成前必须满足：

1. 静态检查没有明显乱码、未翻译、旧入口残留。
2. 前端构建通过。
3. 后端构建通过。
4. 涉及业务写入的任务必须有 API 写入 + 回读证据。
5. 涉及前端页面的任务必须至少做目标页面浏览器抽检。
6. 涉及打包的任务必须验证 zip 不包含 node_modules、数据库影子文件、旧包、临时日志。

## 9. 当前下一步建议

下一步不要先做 PostgreSQL 或大审批流。当前最应该做的是：

1. P1-1 货物兑换证据链 readback。
2. P0-1 员工账号创建与登录链路复核。
3. P2-1/P2-2 货抵、销售、采购、仓库页面中文和高频布局复核。
4. 构建、验证、打包。

理由：
- 用户当前最关心的是“本地能跑、能登录、能给员工用、能移到其他机器测”。
- PostgreSQL、工作流、BI 都重要，但它们属于 P3 平台化重构，不应阻塞当前可测试纯净包。
