# 采购前端大页拆分执行记录_2026-04-21

## 范围

- 本包只处理 `pages/Procurement.tsx` 的前端结构维护问题。
- 不改变采购 API、供应商 API、采购订单状态机、收货入库链路、B2B 关联逻辑和现有视觉风格。
- 目标是降低采购页面后续维护成本，避免供应商、采购单、到岸成本、收货抽屉继续混在一个 1000 行大页里。

## 拆分前问题

- `pages/Procurement.tsx` 约 1066 行。
- 页面同时承担：
  - 数据加载。
  - 供应商搜索与新增。
  - 多名、多址、多联系人供应商表单。
  - 采购订单创建。
  - B2B 销售订单关联。
  - 到岸成本计算。
  - 采购单审批、发运、收货状态流转。
  - 收货批次抽屉。
  - 表格列定义与统计卡片。
- 这种结构会导致后续任何细节变动都要进同一个大文件，维护成本高，也容易重复出现“改一处坏一处”。

## 乱码三步法复核

### 1. 翻译

- PowerShell `Get-Content` 曾显示 `浠?`、`宸叉敹`、`鍒板哺` 等内容。
- Node 以 UTF-8 读取源码后确认真实源码中存在：
  - `件`
  - `已收货`
  - `到岸成本`
  - `汇率`
  - `暂无采购订单`
  - `关闭`
  - `保存中`

### 2. 判断

- 这不是源码乱码，而是终端显示层误解码。
- 不能因为终端输出乱码就重写采购页面。

### 3. 修复

- 本包没有做文案重写。
- 只做结构拆分。
- 保留原有中文、英文、越南文输入能力与 UI 风格。

## 重要验收注意

- 本轮第一次把 `procurement-browser-audit-v1.cjs` 与 API/Phase3 并行跑时，出现过 `expected approved, got pending`。
- 单独顺序重跑采购浏览器审计后通过。
- 判断：这是并行审计抢同一稳定运行层和业务状态窗口造成的误判，不是本次拆分造成的真实断链。
- 固化规则：采购浏览器状态流转类脚本要顺序执行，不要和 Phase3 或采购 API 写入类审计并行抢同一运行层。

## 反思

- 这次拆分是正确方向：主页面不再承载全部 JSX 和工具函数，后续供应商、采购订单、收货批次可以独立维护。
- 本包没有引入新的业务判断，没有改数据库，没有改接口，风险可控。
- 采购页仍有后续优化空间：
  - 供应商新增表单可进一步升级成“简版 + 高级字段折叠”。
  - 到岸成本字段可以沉淀为统一财务成本组件。
  - 收货抽屉可以继续与收发货差异工作台做更清晰的跳转关系。
  - `procurement-api-audit-v1.cjs` 自身仍是大脚本，后续需要拆成供应商、采购单、收货、B2B 四段。
