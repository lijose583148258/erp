# 多智能体阶段 3 收口包：入口、权限、数据保护与职责冲突 2026-04-26

## 本包目标

本包按多智能体分工推进，但最终由主控重新验收，不直接采信子任务报告。

目标不是扩新功能，而是收口反复出现的真实问题：

- 旧入口和 `localhost:3000` 噪声继续误导验收。
- 页面职责冲突导致用户不知道在哪里录入。
- 静默失败导致用户以为系统卡住或数据丢失。
- 后端修复脚本和认证链存在真实数据保护风险。

## 子任务分工

| 角色 | 结论 |
| --- | --- |
| 前端静默失败审计 | 普通页面层 `console.error/alert/空 catch` 基本清零，补了发货 OCR 客户列表刷新失败提示 |
| 后端链路审计 | 发现 P0：固定 ID 运行数据修复可能覆盖真实数据；GET query token 可能进入日志 |

| 模块职责冲突审计 | 发现 P0：采购收货仍显示新增采购单；BOM 有效行统计与保存过滤不一致 |

## 本轮未全部修完的残余项

| 优先级 | 问题 | 后续建议 |
| --- | --- | --- |
| P1 | 调整单库存/批次过账后，成本台账失败可能只记录 warn | 成本台账进入同事务，或接口明确返回 `ledgerRecorded:false` 并禁止标记闭环 |
| P1 | 回款核验、应收调整存在提交后同步客户状态失败造成“假失败”的风险 | 改事务内同步或 outbox，避免已提交业务被后置同步失败变成 500 |
| P1 | 财务应收调整缺少订单/客户行级数据范围校验 | 写入前叠加订单/客户 data scope |
| P1 | 团队接口仍可能给经理看到过多全员信息 | 按 segment/team scope 裁剪成员和业绩字段 |
| P1 | 仓储补录还缺后端来源/原因/备注强合同 | 2026-04-26 已完成前端正名为“应急补录 / 盘盈入库”，但后端字段合同仍待补 |
| P1 | 货抵协议和执行批次仍需要完全动态多明细行 | 2026-04-26 已补当前协议选择器和批次余额约束，动态多明细后续处理 |
| P2 | CRM 客户池动作权威审计还可继续增强 | 2026-04-26 已统一前端动作确认壳，权威记录仍以后端池历史为准 |
| P2 | AI 回复统计应只读 `visibleCounts`，避免安全化后语义失真 | 2026-04-26 已完成规则引擎可见数量口径，后续继续扩红队用例 |

## 反思结论

- 本轮方向没有偏离阶段 3：重点是本地稳定两个月、服务器可迁移、数据不被误修、入口不误导。
- 子智能体报告有效，但至少两处必须由主控复核才发现真正边界：采购验收脚本旧 testId、启动链相对路径进程兼容。
- 当前不能称为“完美商业系统”，但本轮已经把几个会造成真实损失的高风险点压下来了。
