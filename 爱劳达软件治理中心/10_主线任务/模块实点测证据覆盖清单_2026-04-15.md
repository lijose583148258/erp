# 模块实点测证据覆盖清单

- 日期：2026-04-15
- 目的：把“已经有真实浏览器点测证据”的模块，和“还没有闭环证据”的模块彻底分开，避免把路由可打开误当成功能已验完。

## 一、判定口径

### A 档：已拿到闭环实点测证据
- 至少包含一次真实录入或真实交互
- 且有刷新回读、列表回读、或 API 回读证据

### B 档：只有页面级 / 路由级证据
- 浏览器可打开
- 壳层和主要标题正常
- 但还没有关键业务动作的提交与回读证据

### C 档：当前还没有专项实点测证据
- 未进入专门浏览器验收脚本
- 或只有历史口头结论，没有本轮证据文件

## 五、当前最容易误判的地方

1. 路由能打开，不等于模块已验完
2. 页面中文标题正常，不等于录入与回读已经闭环
3. API 能成功，不等于浏览器交互链已经稳定
4. 浏览器专项脚本失败，也不一定等于业务代码坏了，可能是鉴权引导或壳层初始化没有对齐

## 六、建议的后续实点测顺序

1. Collections
原因：已完成双轨改造，但仍缺真正动作闭环证据

2. Procurement 采购订单主链
原因：供应商新增已闭环，继续做订单链最顺

3. Barter
原因：当前只有路由证据，没有真正业务闭环

4. Adjustment
原因：与订单、回款、冲销联动紧密，后续最容易出金额错链

5. Production
原因：后续复杂度高，越晚验证越容易积累隐藏问题

6. Contracts / Risk / Samples / Team / RMA
原因：这些模块当前证据明显不足，需要逐模块补专项

## 七、当前结论

- 当前不是“全系统都验完了”
- 更准确的状态是：
  - 有 4 个模块已经拿到较强闭环证据
  - 有 4 个模块只有页面级证据
  - 还有 7 个模块缺少专项实点测证据

- 所以后续推进原则应该是：
  - 先补 B 档
  - 再清 C 档
  - 每个模块都要留专项证据，而不是只靠一次总验收脚本
