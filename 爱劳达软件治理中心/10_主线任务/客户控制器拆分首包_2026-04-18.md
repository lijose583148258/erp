# 客户控制器拆分首包（2026-04-18）

## 目标

把 `backend/src/controllers/customer.controller.ts` 从单文件承载“权限、数据范围、payload 归一化、联系人地址持久化、接口处理”的状态，拆成更清楚的客户主数据边界，降低后续维护成本。

本包不改变客户 API 路由、不改变前端调用契约、不删除历史文件，优先保证现有 CRM 客户主数据链路稳定。

## 拆分结果

| 层级 | 文件 | 职责 |
| --- | --- | --- |
| 控制器入口 | `backend/src/controllers/customer.controller.ts` | 保留 Express handler、请求响应、事务编排 |
| 类型定义 | `backend/src/controllers/customer/customer.types.ts` | 客户池、业务线、审计动作、订单统计等共享类型 |
| payload 归一化 | `backend/src/controllers/customer/customer.payload.ts` | 三语名称、别名、联系人、地址、订单统计、显示名归一 |
| 权限与数据范围 | `backend/src/controllers/customer/customer.access.ts` | 客户读写权限、业务线约束、销售负责人校验、池操作能力 |
| 持久化辅助 | `backend/src/controllers/customer/customer.persistence.ts` | 客户详情加载、地址/联系人保存、订单统计、审计记录 |

## 乱码三步法复核

1. 现象：PowerShell `Get-Content` 显示 `crm-masterdata-browser-audit-v1.cjs` 中中文测试数据为乱码。
2. 判断：使用 Node 以 UTF-8 读取同一文件，真实源码为正常中文，例如“爱劳达测试客户”“越南平阳省化工园法定地址”。
3. 处理：判定为终端显示层误解码，不改业务源码；后续遇到类似情况继续先做 Node/UTF-8 直读复核。

## 反思

本包方向没有偏离：它没有新增业务功能，而是降低客户主数据核心链路的维护风险。客户 controller 仍有 1000+ 行，原因是本包只抽出低风险纯函数和辅助逻辑，没有动 Express handler 的路由行为。下一次如果继续拆客户模块，应优先抽 `list/create/update/detail/pool/import/export` 子 handler，但必须逐段配 API 读回和浏览器回读证据。

## 剩余风险

1. `backend/src/services/barter.service.ts` 仍是唯一 P1 大文件，应作为下一包的最高维护治理对象。
2. `customer.controller.ts` 仍超过理想控制器规模，但已经从“全混合”变成“handler + 模块辅助”，后续可继续渐进拆分。
3. Lint 仍有 100 个 warning，多数是未使用变量和 hooks 依赖，暂不阻塞本包，但会持续增加维护噪音。
4. 浏览器级 CRM 主数据通过，不等于所有 CRM 子场景都完整通过；客户池流转、导入导出、批量操作仍应保持分项验收。
