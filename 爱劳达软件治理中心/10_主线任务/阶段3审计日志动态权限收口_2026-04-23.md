# 阶段3审计日志动态权限收口_2026-04-23

## 背景

权限系统已经进入动态角色和权限点模型，审计日志读取权限也已注册为 `audit.read`。但 `audit.controller.ts` 内部仍保留 `req.user?.role !== 'admin'` 的二次硬编码检查。

这会造成权限语义冲突：

- 路由层允许拥有 `audit.read` 的自定义角色进入。
- controller 层又只允许 `admin`。
- 结果是超级管理员明明给某个角色授予 `audit.read`，该角色仍然无法读取审计日志。

这属于主框架问题，不是 UI 问题。

## 本次改动

| 文件 | 作用 |
| --- | --- |
| `backend/src/controllers/audit.controller.ts` | 移除 controller 内 `admin` 硬编码二次门禁，统一交给路由层 `authenticate + authorizePermission('audit.read')`。 |
| `scripts/audit-read-dynamic-permission-audit-v1.cjs` | 新增专项回归，证明 `audit.read` 动态授权有效。 |
| `package.json` | 新增 `npm run audit:permissions:audit-read`。 |
| `scripts/phase3-readiness-audit-v1.cjs` | 将 `audit-read-dynamic-permission-chain` 接入阶段 3 总闸门。 |

## 回归逻辑

专项脚本执行以下闭环：

1. admin 登录。
2. sales 登录。
3. 读取权限定义，确认 `audit.read` 存在。
4. 超级管理员确保 sales 没有 `audit.read`。
5. sales 访问 `/api/audit?page=1&pageSize=1`，必须返回 `403`。
6. 超级管理员授予 sales `audit.read`。
7. sales 再访问 `/api/audit?page=1&pageSize=1`，必须返回 `200`。
8. 超级管理员撤销 sales `audit.read`。
9. sales 再访问必须返回 `403`。
10. 恢复 sales 原始角色权限。

该脚本能防止以后重新出现“动态权限表显示授权，但 controller 内硬编码角色拒绝”的假绿。

## 当前结论

审计日志读取权限已回到动态权限主框架。后续审计日志访问权应只通过权限点 `audit.read` 管理，不再在 controller 中硬编码 `admin`。

下一步权限治理仍需单独处理：

1. Casbin fallback 上线语义。
2. token 黑名单和 refresh token 从内存迁出。
3. `auth.controller.ts` 拆分 session / registration / password / token-store。
4. 业务控制器中残留的 role fallback 和 data scope 混用。
