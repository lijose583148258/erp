# 发货出库回单闭环执行记录 2026-04-17

## 本包目标

- 把发货链路从“状态推进 + 回单上传”升级为“发货真实扣库存 + 出库凭证回读 + 回单送达”。
- 修复直接上传签收回单导致 `delivered` 但没有库存出库凭证的结构性缺口。
- 让 API 审计和浏览器审计都必须验证 `shipping_issue` 凭证和成品区库存余额。

## 发现的问题

| 问题 | 判断 | 风险 |
|---|---|---|
| `uploadReceipt` 可以把 `pending` 直接推进到 `delivered` | 原逻辑不会保证先扣库存 | P1 |
| API 审计只验证发货单和订单状态 | 没有验证出库凭证和库存余额 | P1 |
| 浏览器审计只验证 UI 状态和回单 | 没有验证 `shipping_issue` 和 `LOC-FG` 余额 | P1 |
| 审计脚本复用随机客户/库存 | 容易被授信、状态、历史库存污染 | P2 |

## 保留风险

| 风险 | 当前处理 | 后续建议 |
|---|---|---|
| 分批发货 | 当前发货单是一单一出库凭证模型 | 后续应设计 `shipment_lines` 或 `shipment_issue_seq` 支持分批发货 |
| 数据库级幂等 | 当前通过状态流转 + `hasShippingIssuePosted` + 审计验证保证 | 上线 PostgreSQL 前建议引入 `idempotencyKey`，避免全局唯一 `sourceType/sourceRef` 误伤分批业务 |
| 回单文件事务一致性 | 当前保证库存和状态一致，但文件写入仍在事务前 | 后续可改为临时文件 + 成功后确认引用，减少孤儿文件 |
| OCR 发货单 | 浏览器脚本验证 OCR 创建存在，但没有把 OCR 单也推进库存闭环 | 后续可单独做 OCR 发货闭环验收 |

## 反思结论

- 本包修复的是后端真实业务缺口，不只是补测试。
- 发货链路现在已经具备“订单确认、发货出库、库存扣减、凭证回读、回单送达、订单送达”的小闭环。
- 当前发货验收可以作为后续销售出库、换货出库、生产领料出库的模板。
