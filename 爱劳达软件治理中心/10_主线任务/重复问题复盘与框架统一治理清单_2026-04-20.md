# 重复问题复盘与框架统一治理清单（2026-04-20）

## 0. 结论先行

当前系统不是“一个小 bug 没修完”，而是进入了典型的半成品 ERP 治理期：

- 业务模块已经很多，主链路也有一部分能跑通。
- 但历史脚本、旧入口、页面重构后的旧选择器、运行缓存、权限会话、保存后回读口径反复交叉，造成“越修越像补丁”的感觉。
- 框架主方向是统一的：前端 `React + TypeScript + Vite + Tailwind`，后端 `Express + TypeScript + Prisma`。
- 但治理层不统一：测试脚本大量 `.cjs`、旧 `complete-server.js`、历史 stable package、quarantine 文件、报告和源码混搜，会让维护者误以为代码语言混乱。

因此后续不应继续按“发现一个按钮失败就补一个按钮”的方式推进，而要改成“五关收口”：

1. 运行入口与缓存关。
2. 权限会话与角色切换关。
3. 业务闭环与前置数据关。
4. 架构拆分与文件瘦身关。
5. 验收脚本可信化关。

## 1. 历史记录中重复出现的问题

### A. 保存后回读缺失

重复表现：

- 创建成功，但列表/详情/库存台账/回款台账没有立即形成可验证回读。
- 页面提示成功，脚本却在错误页面继续找数据。
- API 已写入，但浏览器没有切到正确读模型。

近期证据：

- `browser-human-flow-audit-report-v1.json` 中 `procurement-warehouse` 仍报 `warehouse inbound record not visible after save`。
- 仓储截图显示“入库成功”，但脚本仍在手动入库表单页查产品名，而不是切到库存台账搜索回读。
- 订单、调账、发货也多次出现“保存/动作后在哪里回读”的口径漂移。

根因判断：

- 页面缺少统一的“保存后回读契约”。
- 测试脚本仍按旧页面结构猜 DOM。
- 各模块的列表刷新、详情刷新、API 回读没有统一规范。

治理方向：

- 每个写操作必须明确：写入接口、成功提示、列表回读、详情回读、API 回读。
- UI 中补稳定 `data-testid`，但不能只补测试锚点，要同时补业务读模型。

### B. 权限会话与角色切换反复出现 403

重复表现：

- 切换到 sales、warehouse、finance 后，页面仍出现上一角色遗留请求。
- 控制台反复出现 `403 Forbidden`、`API Error: 权限不足`。
- 读接口和写接口权限口径不统一。

近期证据：

- 最新 `browser-human-flow-audit-report-v1.json` 中，`#shipping` 和 `#procurement` 出现 403。
- 治理记录中已有“旧请求防踢登录”“采购仓储资产货抵数据范围落地”等专项，说明不是第一次发生。

根因判断：

- 前端角色切换后仍有旧页面请求在飞。
- 部分页面加载时会请求当前角色不该看的数据。
- 读接口“空结果 vs 403”规则不统一。

治理方向：

- 角色切换必须统一执行：取消旧请求、清理页面状态、重新拉取权限、再进入新页面。
- 后端按模块定义读写权限矩阵：无权限读数据应返回空范围还是 403，必须一致。
- 浏览器验收脚本要把 403 单独列为权限会话缺陷，不能混成业务失败。

### C. 页面重构后旧选择器持续误判

重复表现：

- 当前页面已经改版，但浏览器脚本还用旧 `tbody tr`、`div.fixed.inset-0`、`.rounded-[36px]` 等猜测选择器。
- 页面真实存在数据，脚本找不到。
- 页面没有前置业务数据，脚本直接点不存在按钮。

近期证据：

- CRM 曾因脚本按内部主名 `HF-CRM-*` 查找，而实际列表显示中文名 `护风 CRM *`，造成假失败。
- 订单脚本曾把任意 fixed 元素当成订单弹窗。
- 调账脚本曾用非法 CSS 选择器 `.rounded-[36px]`。
- 发货脚本仍假设存在签收按钮，但当前页面没有可签收前置单据。

根因判断：

- 测试脚本没有跟页面组件签稳定契约。
- 业务显示名、内部编号、三语名称没有统一测试口径。
- 脚本复用过度，变成“巨型端到端脚本”，任何一个模块变了都会误伤全局。

治理方向：

- 浏览器验收脚本拆成模块级脚本，不再一个巨脚本包全系统。
- 页面必须暴露稳定锚点：创建按钮、弹窗、主字段、保存按钮、列表行、详情抽屉。
- 测试输入要按业务显示规则：例如客户列表优先显示三语名称，不再只按内部 code 查找。

### D. 乱码与显示层误判反复出现

重复表现：

- PowerShell 显示中文为乱码。
- 报告或终端看起来坏了，但 Node UTF-8 读取源码正常。
- 历史文档中有真实乱码污染，当前源码有时只是显示层误读。

近期证据：

- `browser-human-flow-audit-v1.cjs` 和 helper 用 Node UTF-8 读取无替换符，但 PowerShell 输出显示乱码。
- 治理中心已有“乱码三步法”“禁乱码闸门”，但执行中仍容易忘记。

根因判断：

- Windows 终端显示层和源码层没有强制隔离。
- 历史文档与当前源码混在一起搜索，导致误判范围扩大。

治理方向：

- 遇到乱码默认三步法：翻译还原、判断层级、只修正确层。
- 源码乱码闸门只扫当前有效源码，不扫 dist、output、历史归档。
- 报告读取必须用 Node `fs.readFileSync(..., 'utf8')`，不以 PowerShell 显示为准。

### E. Service Worker / dist 旧包残留导致“修了没生效”

重复表现：

- 构建后页面仍像旧页面。
- CSS 或 chunk 看起来丢失。
- dist 中旧 hash 文件仍在，容易误导判断。

近期证据：

- `public/sw.js` 原先对 `/assets/` 使用 cache-first 且缓存名固定 `ailaoda-shell-v1`。
- 当前已改为 `ailaoda-shell-v2` 和 network-first，但旧浏览器仍可能被旧 SW 控制一次。
- Vite build 未清空 dist，旧 chunk 与新 chunk 并存。

根因判断：

- PWA 离线能力没有“开发/验收模式”的缓存清理规则。
- 构建产物目录没有强制 clean。

治理方向：

- 验收脚本开头清理本次浏览器上下文的 SW/cache。
- 稳定启动脚本应支持 `clean-dist -> build -> start`。
- EXE 本地壳应在版本升级时强制更新 shell cache。

### F. 代码过大与补丁化

重复表现：

- 单文件承担太多业务：页面、表单、状态、API 调用、校验、导出、审计混在一起。
- 后续修复很难定位，容易改一个地方影响另一条链。
- 脚本也越来越大，变成第二套“屎山”。

当前活跃源码超大文件：

| 文件 | 行数 | 问题 |
|---|---:|---|
| `backend/prisma/schema.prisma` | 1193 | 所有领域集中在一个 schema，可接受但需要分区注释和迁移治理 |
| `pages/ProductionWorkspaceV2.tsx` | 1089 | 生产页面过重，需要拆 BOM、工单、完工、调整、库存联动 |
| `backend/src/controllers/procurement.controller.ts` | 1067 | 采购控制器过重，供应商、采购单、收货、B2B、库存写入应拆 |
| `backend/src/controllers/customer.controller.ts` | 1051 | 客户主数据、池流转、统计、导入导出混在一起 |
| `backend/src/services/barter.service.ts` | 1036 | 货抵协议、批次抵扣、估值、冲销、对账混在一起 |
| `backend/src/controllers/shipping.controller.ts` | 1005 | 发货、签收、OCR、回单、差异处理需要拆边界 |
| `pages/Procurement.tsx` | 951 | 供应商、采购订单、右侧表单、权限状态混杂 |
| `pages/crm/useCRM.tsx` | 731 | CRM 状态、权限、池流转、AI、导入导出过重 |
| `pages/sales-orders/useSalesOrders.ts` | 599 | 订单头、明细、回款、OCR、离线草稿、库存洞察混杂 |
| `scripts/browser-human-flow-audit-v1.cjs` | 557 | 总脚本过大，模块失败互相污染 |

治理方向：

- 页面按 `Shell / List / CreateEdit / Detail / Hooks / Service Adapter` 拆。
- 后端按 `controller -> service -> repository/readModel` 拆。
- 浏览器验收按模块拆，不再全局巨脚本。

## 2. 框架和语言是否统一

### 当前主框架

| 层 | 当前方向 | 结论 |
|---|---|---|
| 前端 | React 19 + TypeScript + Vite + Tailwind | 主方向统一 |
| 后端 | Express + TypeScript + Prisma | 主方向统一 |
| 数据库 | SQLite 本地优先，保留 PostgreSQL 迁移脚本 | 方向可行，但迁移治理需收口 |
| 自动化脚本 | Node `.cjs` + PowerShell | 可接受，但需要分层和命名规范 |
| 历史/隔离 | `.js`、`.bak`、legacy、quarantine | 必须从活跃运行链隔离 |

### 当前不统一的地方

- 前端根目录不是传统 `src/`，而是 `pages/components/services/app` 平铺。可运行，但新人维护成本高。
- 后端有 `src` 正规链，也残留 `complete-server.js`、旧修复脚本、历史 stable package。
- 测试脚本是 `.cjs`，和业务 TypeScript 不一致。短期可接受，长期应迁到 `scripts/audits/*.ts` 或保留 `.cjs` 但统一 helper 层。
- 治理文档、历史归档、输出报告和当前源码混放在同一项目目录，搜索时非常容易误判。

## 3. “还差多少步才算能用”

不能说“完美”，只能说分阶段达到可用。

### 阶段一：止血可用，还差 5 步

目标：本地启动稳定，核心链路不会假绿，能人工试用。

1. 统一启动链：只认 `http://127.0.0.1:5001/`，清理/标记 3000、5173、旧端口脚本。
2. 修权限会话：角色切换后取消旧请求，403 不再污染新页面。
3. 拆浏览器验收：CRM、订单、采购仓储、发货、回款调账、生产各自独立。
4. 每个模块补保存后回读：列表、详情、API 至少两层证据。
5. 清理缓存与 dist 旧包：build 前 clean，SW network-first，验收前清缓存。

阶段一完成后，可以进入“内部试用”，但不能说线上完美。

### 阶段二：两个月本地稳定，还差 6 步

目标：本地 EXE/壳稳定跑，数据不丢，断网/重启/长时运行可恢复。

1. 数据库备份恢复自动化：启动前轻备份，关键写入前事务化。
2. 并发与幂等：重复提交、重复入库、重复回款、重复冲销必须有防重。
3. 核心业务状态机：订单、回款、发货、采购、生产、货抵统一状态机。
4. 操作审计：谁、何时、为什么、前后值。
5. 错误提示商业化：400/403 不裸露给用户，要变成可理解动作提示。
6. 长时运行监控：5 分钟卡住裁判、进程健康、内存/端口占用检查。

### 阶段三：后续服务器部署，还差 5 步

目标：本地 SQLite 能迁移到服务器数据库和服务部署。

1. Prisma migration 固化，不再靠 runtime repair 当主路径。
2. SQLite -> PostgreSQL 演练：导出、导入、校验数量、金额、库存。
3. 环境变量分层：本地、测试、生产。
4. 文件上传存储策略：本地壳和服务器对象存储分离。
5. 安全策略：JWT、RBAC、AI 数据隔离、日志脱敏、备份加密。

## 5. 反思

这段时间最大偏差不是技术难，而是执行方法偏了：

- 过早追求“全模块都点一遍”，导致巨型浏览器脚本不断补丁化。
- 页面改版后，没有先建立稳定测试锚点和前置数据工厂。
- 把 API 绿、build 绿、页面能打开误当成业务闭环绿。
- 对历史文件、报告、dist、当前源码的边界不够硬，造成反复误判。

后续必须改成：

- 先定边界，再修模块。
- 先小闭环，再大闭环。
- 先可验证，再说完成。
- 先拆掉巨脚本和巨文件，再继续扩功能。
