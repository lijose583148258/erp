# 备份恢复业务数据指纹闸门记录 2026-04-22

## 结论

- 本包目标：把备份恢复验收从“备份文件存在、manifest 正常、恢复后能登录”升级为“业务数据恢复后完全一致”。
- 已新增业务数据指纹闸门：`backup-restore-data-fingerprint`。
- 当前验证结果：43 张业务表，备份文件指纹与恢复后的运行库指纹一致，0 mismatch。
- 已接入 `verify:phase3` 与 `verify:release`。

## 为什么要做

- 备份恢复只看 HTTP 200 和登录成功是不够的。
- 真正上线最怕的是：
  - 客户还在，但订单丢了。
  - 订单还在，但回款金额丢了。
  - 库存还在，但流水或批次少了。
  - 货抵单还在，但分批抵扣金额错了。
  - 恢复后系统能打开，但业务数据已经不一致。
- 所以必须比较备份文件本身与恢复后运行库的业务表指纹。

## 新增脚本

- `scripts/backup-restore-data-fingerprint-audit-v1.ts`

流程：

1. 通过真实 API 登录。
2. 通过真实 API 创建备份。
3. 直接读取备份文件，计算业务数据指纹。
4. 通过真实 API 恢复该备份。
5. 直接读取恢复后的运行库，计算业务数据指纹。
6. 比较表数量、核心金额、数量、库存、生产、采购、回款、货抵、应收调整等聚合值。
7. 指纹不一致则失败。

## 指纹范围

覆盖 43 张业务表，包括：

- 用户与权限：`users`、`auth_roles`、`auth_permissions`、`auth_role_permissions`
- CRM 与订单：`customers`、`orders`、`order_items`
- 回款与应收：`payment_records`、`receivable_adjustments`
- 合同与催收：`contracts`、`contract_milestones`、`collection_promises`、`collection_disputes`
- 采购：`suppliers`、`purchase_orders`
- 样品、发货、售后：`samples`、`shipments`、`rmas`
- 收发货差异：`receipt_discrepancy_cases`、`receipt_discrepancy_actions`、`receipt_tolerance_rules`
- 仓储：`warehouses`、`locations`、`stock_balances`、`stock_entries`、`stock_movements`
- 库存成本：`product_batches`、`inventory_cost_ledgers`、`asset_balances`、`asset_transactions`
- 生产：`production_boms`、`production_bom_items`、`production_work_orders`、`production_process_steps`、`production_quality_checks`
- 货抵支付 / 换货贸易：`barter_agreements`、`barter_agreement_items`、`barter_settlements`、`barter_items`、`barter_valuation_snapshots`、`barter_offset_postings`、`barter_reversal_logs`
- 调整：`adjustment_records`

说明：

- 不把 `audit_logs` 纳入严格指纹比较，因为备份和恢复操作本身可能自然产生审计流水。
- 这不是忽略审计日志，而是避免把“恢复操作产生的正常流水变化”误判为业务数据丢失。

## 后续制度

- 以后不能只说“备份恢复接口通过”。
- 任何本地稳定、服务器迁移、EXE 打包前，都必须至少通过：
  - `npm run audit:db:integrity`
  - `npm run audit:db:shadow`
  - `npm run audit:backup-restore:fingerprint`
  - `npm run verify:phase3`
- 如果指纹不一致：
  - 先停止上线判断。
  - 保留备份文件和报告。
  - 对比 mismatch 表和字段。
  - 不允许直接覆盖或删除运行库。
