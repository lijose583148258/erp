# 阶段3 认证 Token 存储服务化与会话审计收口_2026-04-23

## 背景

`auth.controller.ts` 仍然同时承担登录、注册、刷新、登出、密码修改、Token 黑名单和 refresh token 存储。更重要的是，认证中间件为了检查黑名单需要反向导入控制器，这会让控制器承载非 HTTP 职责。

本包目标不是重写认证，而是先把 Token 存储和会话校验从控制器中拆出，并补上真实 API 审计。

## 本轮改动

| 文件 | 改动 |
| --- | --- |
| `backend/src/services/auth-token-store.service.ts` | 新增 Token 存储服务，集中 access token 黑名单、refresh token 创建、校验、删除和定时清理 |
| `backend/src/controllers/auth.controller.ts` | 登录/刷新/登出改为调用 Token 服务；控制器从 527 行降到 482 行 |
| `backend/src/middleware/auth.ts` | 黑名单检查改为导入 Token 服务，不再反向导入 `auth.controller.ts` |
| `services/auth.service.ts` | 前端登出时先调用 `/auth/logout`，再清本地存储，避免只做本地假登出 |
| `scripts/auth-session-token-api-audit-v1.cjs` | 新增会话审计，覆盖登录、`/auth/me`、refresh 轮换、旧 refresh 拒绝、登出黑名单、登出后 refresh 撤销 |
| `scripts/phase3-readiness-audit-v1.cjs` | 新增 `auth-session-token-chain`，纳入阶段 3 主闸门 |
| `package.json` | 新增 `audit:auth:session-token` |

## 当前会话规则

| 场景 | 行为 |
| --- | --- |
| 登录 | 生成 access token 和 refresh token |
| refresh | 校验 refresh token，签发新 access token 和新 refresh token，并删除旧 refresh token |
| 登出 | 将当前 access token 加入黑名单 |
| 带 refresh token 登出 | 同时删除传入的 refresh token |
| 前端登出 | 调用后端 `/auth/logout` 后清本地 `token/user` |

## 反思

本轮出现过一次测试层误判：多个会修改 `sales` 权限的审计脚本并行运行，导致 `/auth/me` 回读权限时出现瞬时不一致。串行复跑后通过。

结论：权限、角色、会话类审计不能随意并行。后续多智能体可以并行读代码、并行做不共享状态的浏览器截图，但凡会改角色表、用户表、Token 或权限表的脚本，必须串行或使用独立沙盒数据。

## 后续约束

1. 后续改认证、Token、登录、登出、权限中间件时必须跑 `npm run audit:auth:session-token`。
2. 会修改 `sales/admin/roles` 的审计脚本不能并行跑。
3. 前端不能只清本地 token 就宣称登出完成。
4. 认证控制器下一步可以继续拆 session、registration、password，但必须保持本包会话审计为绿。
