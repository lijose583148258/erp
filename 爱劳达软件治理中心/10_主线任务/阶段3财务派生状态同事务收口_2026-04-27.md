# 阶段 3 财务派生状态同事务收口记录

日期：2026-04-27

目标：继续推进“本地稳定两个月 + 后续服务器可迁移”，本包专门处理应收调整、付款核销、催收动作中的派生状态同步假 500 风险。

## 本包结论

- 应收调整过账 / 红冲已把客户催收状态刷新纳入同一数据库事务。
- 付款核销与订单支付状态重算已把客户催收状态刷新纳入同一数据库事务。
- 催收承诺、争议、客户冻结/解冻、订单发货冻结/解冻已把派生状态刷新纳入同一数据库事务。
- 争议导致的订单发货冻结同步已支持事务客户端，不再事务提交后补写。
- E 盘纯净运行版已重新打包、刷新、重启，并通过财务链路、浏览器人工流、每日治理闸门。

## 修复前风险

旧逻辑的典型形态：

1. 主交易在事务内成功，例如应收调整过账、付款核销、创建催收承诺。
2. 事务提交后再调用 `CollectionStateService.syncCustomerOverdueAmount(...)` 或 `refreshCustomerCollectionState(...)`。
3. 如果派生状态同步失败，接口会返回 500。
4. 用户看到失败后可能重复点击，但主交易其实已经成功，容易造成重复单据、误判、人工对账困难。

这属于“假失败”风险，不是简单 UI 问题。

## 关键改动

### 1. 催收状态服务支持事务客户端

新增事务内调用能力：

- `syncCustomerOverdueAmountTx(tx, customerId)`
- `refreshCustomerCollectionStateTx(tx, customerId)`

保留原公共方法：

- `syncCustomerOverdueAmount(customerId)`
- `refreshCustomerCollectionState(customerId)`

原公共方法现在自己开启事务，保证独立调用也不会半截写入。

### 2. 应收调整同事务刷新派生状态

过账时：

- 更新订单 `receivableAdjustmentAmount`
- 更新订单 `paymentStatus`
- 更新应收调整单 `posted`
- 同事务刷新客户 `overdueAmount`、`dunningLevel`、`collectionsStatus`

红冲时：

- 恢复订单 `receivableAdjustmentAmount`
- 恢复订单 `paymentStatus`
- 更新应收调整单 `reversed`
- 同事务刷新客户催收状态

### 3. 付款核销同事务刷新派生状态

核销时：

- 抢占待核销付款记录
- 汇总已核销付款
- 更新订单 `paidAmount` 和 `paymentStatus`
- 更新合同里程碑状态
- 同事务刷新客户催收状态

### 4. 催收动作同事务刷新派生状态

已覆盖：

- 创建还款承诺
- 更新承诺状态
- 创建争议
- 更新争议状态
- 客户信用冻结 / 解冻
- 客户发货冻结 / 解冻
- 订单发货冻结 / 解冻

## 反思

- 本包没有扩功能，而是把已经存在的业务链从“事务后补派生状态”改为“主交易与派生状态一致提交”。
- 这类问题最危险的地方不是立刻报错，而是用户看到 500 后重复点击，造成数据层二次变更。
- 同事务化以后，派生状态失败会让主交易一起回滚，错误语义更诚实。
- 后续仍要关注审计日志、通知、报表缓存这类非强一致派生物，它们更适合 outbox / retry，而不是阻塞主交易。

## 下一步建议

| 优先级 | 任务 | 原因 |
| --- | --- | --- |
| P1 | 审计日志与非核心派生事件 outbox 化 | 避免日志失败导致业务误失败 |
| P1 | 全仓搜索事务后补写模式 | 防止类似假 500 在采购、仓储、生产里重复出现 |
| P2 | 给派生同步建立统一返回口径 | 让 API 明确区分主交易成功、派生异步排队、派生失败待重试 |
| P2 | 长时运行下财务链路重复点击压测 | 验证本地两个月试跑期间不会因重复操作造成漂移 |
