# 供应商写入服务化与基础目录权限拆分记录

日期：2026-04-21

## 背景

本轮继续按“系统工程拉正”推进采购主线，目标不是继续在控制器里堆补丁，而是把供应商创建、供应商基础目录读取、采购订单读取三条边界拆清楚。

历史问题主要有三类：

- 供应商创建逻辑写在 `procurement.controller.ts` 中，字段兼容、JSON 序列化、默认值和校验混在控制器里，后续维护成本高。
- 供应商基础资料在客户、货抵、采购等场景都会被搜索引用，但不能因此把完整采购订单权限开放给销售或非采购角色。
- 浏览器人工流曾出现仓储库存回读超时，复核后确认后端和 DOM 可回读，属于验收脚本重复点击查询造成的偶发竞态，需要降低脚本误判。

## 本轮改动

### 1. 供应商创建服务化

新增文件：

- `backend/src/services/procurement-supplier.service.ts`

核心职责：

- `createSupplierRecord(tx, input)` 统一处理供应商创建。
- `getSupplierColumnSet(tx)` 继续兼容本地旧库字段差异，但限制为硬编码 `suppliers` 表。
- 创建必须至少有一个名称：`name`、`nameZh`、`nameEn`、`nameVi`。
- `category` 必填。
- `rating` 限制为 0 到 5。
- `leadTimeDays` 限制为大于等于 0 的整数。
- `riskLevel` 限制为 `low`、`medium`、`high`。
- `status` 限制为 `active`、`inactive`。
- `contacts`、`addresses` 必须是对象数组或可解析为对象数组的 JSON 字符串。

控制器变化：

- `backend/src/controllers/procurement.controller.ts`
- `createSupplier` 只负责权限、事务调用、审计日志和错误映射。
- 供应商字段细节从控制器移出，减少控制器补丁化。

### 2. 供应商基础目录权限拆分

新增权限：

- `procurement.suppliers.read`

调整文件：

- `backend/src/permissions/permissionRegistry.ts`
- `backend/src/routes/procurement.routes.ts`

权限原则：

- `GET /api/procurement/suppliers` 使用 `procurement.suppliers.read`。
- `GET /api/procurement/orders` 继续使用 `procurement.read`。
- 销售、仓储、财务可以读取供应商基础目录，以支持货抵、采购协同、关联字搜索。
- 非采购数据范围角色不能读取供应商敏感字段，供应商联系人、地址、备注等敏感信息继续由 `canViewSupplierSensitiveData` 控制。
- 供应商搜索也按敏感字段隔离：无采购数据范围时不能通过联系人、地址等敏感字段反向搜索。

## 误判修正

采购-仓储人工流曾出现一次：

- `warehouse-inventory-product-readback exceeded 15000ms`

复核步骤：

- 直接调用库存 API，确认 `胶水原料-20260421052506` 已经写入库存余额。
- 独立浏览器诊断确认同一账号、同一 URL、同一搜索词，DOM 表格能显示该库存行。
- 复跑完整人工流通过。

修正：

- `scripts/browser-human-flow-audit-v1.cjs` 中库存回读等待不再每 800ms 连续点击查询。
- 现在改为先点击一次并轮询 DOM，超过 3.5 秒后才补一次查询，减少脚本自身制造的竞态误判。

## 后续约束

- 供应商创建规则不得再回写到控制器中，新增字段优先进入 `procurement-supplier.service.ts`。
- 供应商基础目录读取不得等同于采购订单读取。
- 销售、仓储、财务可以读取供应商名称、分类、评级等基础目录，但不能读取敏感联系人、地址、内部备注。
- 后续做客户/供应商统一主数据时，应复用“基础目录读 + 敏感字段数据范围”的权限模型。
- 浏览器人工流遇到偶发红灯时，必须先区分产品缺陷和脚本误判；不能用 API 绿灯替代浏览器证据，也不能用脚本红灯直接否定业务链路。
