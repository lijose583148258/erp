## 1. 崩溃根因诊断

### 🔴 1.1 SQLite WAL 模式未确认启用

**问题：** `schema.prisma` 使用 `provider = "sqlite"`，但代码中未见显式启用 WAL（Write-Ahead Logging）模式。SQLite 默认为 journal 模式，Electron 的主进程 + 渲染进程同时访问时，极容易触发 `SQLITE_BUSY` 错误直接崩溃。

**表现：** 用户在快速操作（如连续提交订单、批量导出）时系统无响应或白屏。

**修复方案：**
```typescript
// 在 database.ts/config/database.js 初始化时执行
await prisma.$executeRawUnsafe(`PRAGMA journal_mode=WAL;`);
await prisma.$executeRawUnsafe(`PRAGMA busy_timeout=5000;`);
await prisma.$executeRawUnsafe(`PRAGMA synchronous=NORMAL;`);
await prisma.$executeRawUnsafe(`PRAGMA cache_size=-64000;`); // 64MB 页缓存
await prisma.$executeRawUnsafe(`PRAGMA foreign_keys=ON;`);
```
这5行必须在任何业务操作之前完成。WAL 模式允许并发读，`busy_timeout` 避免立即崩溃。

---

### 🔴 1.2 三倍冗余构建产物导致的资源混乱

**问题：** zip 包中每个前端模块存在 **3 个不同哈希的版本**，例如：
```
AdjustmentCenterView-BkRhtSQR.js  ← 当前版本
AdjustmentCenterView-CVjbVvNV.js  ← 上一版本
AdjustmentCenterView-Div8uGIq.js  ← 再上一版本
```
`index.html` 只引用其中一个，但 `dist/assets/` 目录中存在全部 3 份。静态服务器扫描该目录时，如果路由或缓存出错，**可能加载到旧版本 JS**，导致 API 调用不匹配、UI 状态异常。

**修复方案：** 构建前必须清空 `dist/assets/`，CI 脚本中加入：
```bash
rm -rf dist/assets && vite build
```
不允许增量叠加构建产物，否则生产包体积翻三倍且埋下随机崩溃隐患。

---

### 🟠 1.3 Service Worker 反向注销逻辑

**问题：** `index.html` 中：
```javascript
navigator.serviceWorker.getRegistrations()
  .then(registrations => registrations.map(r => r.unregister()))
```
每次页面加载都主动注销 SW，但 `manifest.json` + Apple Web App meta 标签仍声明这是 PWA。这导致：
- 在某些 Chromium 版本下产生竞态条件
- `beforeinstallprompt` 事件无法正常触发
- 离线缓存永远失效，每次都全量下载 367KB 的 `index-CSi9Nami.js`

**修复：** 要么彻底移除 SW 相关代码，要么保留 SW 并实现正确的缓存策略，二选一，不能两头都做。

---

### 🟠 1.4 大型模块无代码分割

**问题（按 minified 体积排序）：**

| 模块 | 体积 |
|------|------|
| SalesOrders | 102 KB |
| ProductionWorkspace | 91 KB |
| CRM | 89 KB |
| CollectionCenterView | 62 KB |
| WarehouseWorkspace | 60 KB |
| Procurement | 54 KB |

在 Electron 的 Chromium 中，加载 102KB 的 SalesOrders 时如果 JS 执行阻塞超过 50ms（低配 Windows 笔记本上常见），UI 会完全冻结。

**修复：** 对每个 Workspace 内部进行二级懒加载，子视图（如订单详情弹窗、打印预览）单独分割：
```typescript
const OrderDetailModal = lazy(() => import('./OrderDetailModal'));
const OrderPrintPreview = lazy(() => import('./OrderPrintPreview'));
```

---

### 🟡 1.5 `dbRetry` 未覆盖所有写操作

部分控制器使用了 `withDbRetry`，但不是全部。在 SQLite WAL 未启用时，即使有重试也只能缓解不能根治。启用 WAL 后，`dbRetry` 应保留但重试次数可降低（3次→2次）。

## 2. 数据模型层深度缺陷

### 🔴 2.1 没有产品主数据表（Product Master）

**问题：** `productName` 作为自由文本字段散布在以下 7 张表中：
- `order_items.product_name`
- `shipments.product_name`
- `samples.product_name`
- `rmas.product_name`
- `product_batches.product_name`
- `production_boms.product_name`
- `production_work_orders.product_name`

同一个产品在不同地方拼写不同（"乳化剂"/"乳化剂A级"/"乳化剂 A"），导致：
- 库存对账无法自动匹配
- 生产BOM无法关联到出货记录
- 报表按产品汇总时数据分裂

**修复方案（Product Master 最小设计）：**
```prisma
model Product {
  id          Int      @id @default(autoincrement())
  code        String   @unique               // 产品编码，如 EMU-A-01
  nameZh      String   @map("name_zh")       // 中文名
  nameVi      String?  @map("name_vi")       // 越南文名
  specification String?                     // 规格
  unit        String                         // 标准单位
  category    String?                        // 分类
  isActive    Boolean  @default(true) @map("is_active")
  createdAt   DateTime @default(now()) @map("created_at")
  
  orderItems  OrderItem[]
  batches     ProductBatch[]
  boms        ProductionBom[]
  
  @@map("products")
}
```
所有 `productName String` 字段替换为 `productId Int` + 外键关联，保留 `productNameSnapshot String?` 作为历史快照防止产品改名影响历史记录。

---

### 🔴 2.2 订单明细无货币字段（多货币断层）

**问题：** `Order` 有 `currency`/`lockedExchangeRate`/`baseAmount` 三个货币字段，但 `OrderItem` 只有：
```prisma
unitPrice   Float
totalPrice  Float
```
完全没有货币信息。当一张订单用 VND 计价时，明细行的 `unitPrice` 到底是 VND 还是 CNY？没有字段区分。导致：
- 越南客户的订单详情页金额显示混乱
- 财务分析无法正确折算明细级别的利润
- 导出 Excel 时金额列无单位标注

**修复：** `OrderItem` 增加：
```prisma
currency      String?   // 继承订单货币，冗余存储用于历史对账
unitPriceCny  Float?    @map("unit_price_cny")   // 按锁定汇率折算的本位币价格
```

---

### 🟠 2.3 Customer 表双轨联系人/地址字段（新旧并存未清理）

**问题：** `Customer` 模型同时存在两套：
```prisma
// 旧的单值字段（遗留）
contactName   String?
contactPhone  String?
contactEmail  String?
address       String?

// 新的 JSON 数组字段
contactsJson  String?   // "[{name, phone, email, role}]"
addressesJson String?   // "[{province, city, detail, isPrimary}]"
```

UI 层面必然面临：是展示旧字段还是新字段？写入时往哪里写？这是反人类布局的直接原因之一——某些客户详情页可能同时显示两套联系信息，或者空白。

**修复：** 执行数据迁移脚本，将所有旧字段数据合并进 JSON 字段，然后在数据库中保留旧字段为 `@deprecated` 但不再在 UI 展示，下一个版本再删除。

---

### 🟠 2.4 所有状态字段均为裸字符串（无枚举约束）

**问题示例：**
```prisma
Order.status       String  // "pending"/"confirmed"/"shipped"/"completed"/"cancelled"
Customer.status    String  // "active"/"inactive"
Shipment.status    String  // "pending"/"shipped"/"delivered"
ProductionBom.status String // "draft"/"active"/"archived"
```

数据库层无任何约束，后端只在部分控制器中做字符串校验，前端传入 `"Pending"`（大写）会静默存入并永远匹配不到任何查询过滤器。

**修复：** SQLite 不支持枚举，但可以用 CHECK 约束（Prisma `@check` 或原生迁移）：
```sql
ALTER TABLE orders ADD CONSTRAINT chk_order_status 
  CHECK (status IN ('pending','confirmed','processing','shipped','completed','cancelled'));
```
同时在后端建立统一的 `OrderStatus` / `ShipmentStatus` 常量对象，不允许魔法字符串散落。

---

### 🟠 2.5 `User.role` 为裸字符串，权限体系双轨

**问题：** `User.role String` 与 `AuthRole/AuthPermission/AuthRolePermission` 同时存在。`recordAccess` 工具函数直接检查 `req.user.role === 'sales'` 这样的硬编码，而新的 RBAC 表（`auth_roles`, `auth_permissions`）提供了精细权限管理。两套体系并行，导致：
- 给用户分配了细粒度权限，但旧的角色判断仍然拦截
- 修改角色需要两处同步修改
- 审计日志无法区分"旧角色拒绝"还是"新权限拒绝"

**修复路线：** 统一迁移至 RBAC，`User.role` 保留作为 `authRole.code` 的快照缓存（提升查询性能），但权限决策完全走 `AuthRolePermission` 表，移除所有 `req.user.role === 'xxx'` 硬编码。

---

### 🟡 2.6 `BarterAgreement.counterpartyName` 与实体解耦

**问题：** `counterpartyType` 可以是 `"customer"/"supplier"/"other"`，但 `counterpartyName` 始终是自由文本。`customerId/supplierId` 是可空的。这意味着可以创建一个 `counterpartyType="customer"` 但 `customerId=null` 的易货协议，所有关联查询会静默失败。

**修复：** 数据库层加触发器或后端校验：当 `counterpartyType='customer'` 时 `customerId` 不得为 null，反之亦然。

---

### 🟡 2.7 `AuditLog.details` 非结构化文本

**问题：** `details String?` 存储的是人类可读字符串，如 `"创建订单 ORD-20260601-001，客户：河内经销商，金额：₫12,500,000"`。这意味着：
- 无法按金额范围查审计日志
- 无法自动 diff（前后快照对比）
- AI 助手无法结构化分析操作历史

**修复：** 改为 JSON 格式：
```typescript
details: JSON.stringify({
  action: 'CREATE_ORDER',
  before: null,
  after: { orderNo, customerId, finalAmount, currency },
  meta: { ip, userAgent }
})
```

---

### 🟡 2.8 `ProductBatch` 与采购入库链路断裂

**问题：** `ProductBatch`（生产批次）没有任何字段链接到 `PurchaseOrder`（采购单）或 `PurchaseOrderReceipt`（收货记录）。生产工单 `ProductionWorkOrder` 关联了 `ProductBatch`，但采购的原材料从哪个批次消耗，无从追溯。

**修复：** 增加物料消耗表或在 `ProductionBomItem` 层面增加 `sourceBatchId`，建立原料批次→生产批次的正向溯源链。

## 3. 后端 API 层问题

### 🔴 3.1 JWT 密钥未做启动时强校验

**问题：** `.env.production.example` 中：
```
JWT_SECRET=replace_with_a_long_random_secret_before_server_deploy
```
服务器在 `JWT_SECRET` 未被替换或为空时仍会正常启动，只是签名的 token 极不安全。

**修复：** 在 `startServer()` 开头加强制校验：
```typescript
const jwtSecret = process.env.JWT_SECRET || '';
if (jwtSecret.length < 32 || jwtSecret.includes('replace_with')) {
  logger.error('FATAL: JWT_SECRET 未正确配置，拒绝启动');
  process.exit(1);
}
```

---

### 🟠 3.2 缺少统一输入验证层（Zod）

**问题：** 从编译后的控制器来看，输入验证方式为：
```typescript
const { customerId, items, paymentTerms = 30, notes } = req.body;
if (!domain || !targetType || !reason) {
  return res.status(400).json({ message: 'Missing required fields' });
}
```
手动解构 + 手动判空，没有 schema 验证。`paymentTerms` 可以传入 `-999`，`finalAmount` 可以传入 `"abc"`，Prisma 会在数据库层报错而不是在 API 层返回友好错误。

**修复：** 在路由层统一接入 Zod 中间件：
```typescript
import { z } from 'zod';
const CreateOrderSchema = z.object({
  customerId: z.number().int().positive(),
  items: z.array(z.object({
    productName: z.string().min(1),
    quantity: z.number().positive(),
    unitPrice: z.number().positive(),
    unit: z.string().min(1),
  })).min(1),
  paymentTerms: z.number().int().min(0).max(365).default(30),
  discountAmount: z.number().min(0).default(0),
  notes: z.string().max(2000).optional(),
});
```

---

### 🟠 3.3 分页缺少上限强制执行

**问题：** 多处控制器：
```typescript
const limit = Math.min(Number(pageSize) || 20, 100);
```
限制了单次最大 100 条，但某些模块（如 `getOrders` 的统计接口）使用 `findMany` 无 `take` 限制，在数据量大时会一次性拉取全部记录导致内存溢出崩溃。

**修复：** 建立全局 `safePaginate` 工具函数，任何 `findMany` 调用必须经过该函数，默认 20、最大 200，超过 200 条的需求走专门的导出接口（异步生成 Excel）。

---

### 🟠 3.4 `order-payment` 控制器命名与集合控制器职责混淆

**问题：** `PaymentRecord` 的核验（`verifyPaymentRecord`）被放在 `CollectionController`（催收模块），而不是支付模块。这是导致 UI 布局混乱的后端原因：前端要同时在"收款工作台"和"订单详情"两处处理付款核验，逻辑分裂。

**修复：** 将 `verifyPaymentRecord` 移至独立的 `PaymentController`，`CollectionController` 只保留催收触发、承诺、争议、提醒四类操作。

---

### 🟡 3.5 备份保留策略默认 `report-only` 的风险

**问题：** `BACKUP_RETENTION_MODE=report-only` 意味着即使备份数量超过 800 个、总大小超过 8GB，系统也只记录日志不删除。在 Windows 本地长期运行后，`runtime-data/` 目录会无限膨胀直至磁盘满。磁盘满是另一类崩溃的根源。

**修复：** 将 `BACKUP_RETENTION_MODE` 默认改为 `enforce`，并在首次启动向导中显式提示用户配置离机备份策略后才切换此选项。

---

### 🟡 3.6 健康检查 `/health` 端点暴露磁盘信息

**问题：** `/health` 返回 `freeDiskBytes` 和 `minimumFreeDiskBytes`，且该端点**无需认证**。攻击者可以探知服务器磁盘余量并据此设计拒绝服务攻击（上传大文件直至磁盘满）。

**修复：** 健康检查端点只返回 `status: ok/degraded`，详细信息需要管理员 token 才能获取。

---

## 4. 前端各模块反人类设计逐一拆解

### 🔴 4.1 DataTable / EnterpriseDataGrid — 两套组件并存

**问题：** `dist/assets/` 中同时存在 `DataTable-CPfoyQgz.js`（10.5KB）和 `EnterpriseDataGrid-CJB_mbvo.js`（11.3KB）两个数据表格组件。不同模块使用不同组件，导致：
- 列宽行为不同（一个能拖拽调整，一个不能）
- 筛选器 UI 风格不同
- 排序交互不统一
- 用户在不同页面需要"重新学习"操作方式

**修复方向：**
- 统一为单一 `EnterpriseDataGrid`（体积较大但功能完整）
- 必须实现的功能：列宽拖拽调整、列显示/隐藏控制、排序状态持久化（localStorage）、行高切换（紧凑/标准/宽松）

---

### 🔴 4.2 SalesOrders（销售订单）— 信息密度过高

**根据模块体积和业务逻辑推断的具体问题：**

**4.2.1 新建订单表单**
- 订单明细行内嵌编辑（inline edit）缺少行确认机制，用户添加一行后直接点其他位置会丢失输入
- `productName` 是自由文本输入框，没有产品选择器/搜索下拉，导致拼写错误的产品名静默存入
- 折扣金额字段（`discountAmount`）与折扣率（百分比）模式未提供切换，输入体验不一致
- 付款周期（`paymentTerms`）只是一个数字输入框，没有常用预设（30天/60天/90天/现款）

**补充细节方案：**
```
新建订单表单结构建议：
┌─────────────────────────────────────────────┐
│ 基本信息                                      │
│  客户 [搜索选择]  合同 [关联可选]  日期 [今天] │
├─────────────────────────────────────────────┤
│ 订单明细                                      │
│  [+添加产品行] ← 弹出产品选择器而非自由输入    │
│  产品 | 规格 | 数量 | 单位 | 单价 | 小计      │
│  ─────────────────────────────────────────   │
│  合计: ¥xxx  折扣: [金额/比例切换] 最终: ¥xxx │
├─────────────────────────────────────────────┤
│ 支付条款                                      │
│  [现款] [30天] [60天] [90天] [自定义___天]    │
│  货币: [CNY ▼] 汇率: 自动填入可手动覆盖       │
├─────────────────────────────────────────────┤
│ 备注 (可选)                      [取消] [创建] │
└─────────────────────────────────────────────┘
```

**4.2.2 订单列表页**
- 状态筛选器应显示每个状态的数量角标：`待确认(12) | 处理中(5) | 已发货(8)`
- 缺少"到期风险"列（根据 `paymentTerms` 和创建日期计算收款截止日）
- 缺少批量操作：批量确认、批量导出、批量打印

**4.2.3 订单详情页**
- 多货币金额展示必须同时显示原始货币 + CNY折算：`₫12,500,000 (≈¥3,680)`
- 付款记录时间线（已收/待收/逾期）应作为侧边栏固定显示，不应藏在 Tab 页里
- 状态变更按钮（"确认"/"发货"/"完成"）操作后没有成功反馈动画，用户不知道是否成功

---

### 🔴 4.3 CollectionCenterView（催收工作台）— 信息架构错误

**4.3.1 整体布局问题**
催收模块包含：逾期概览 + 分级催收工作台 + 还款承诺 + 争议管理 + 客户止货 + 订单止货，这 6 个功能挤在一个 `CollectionCenterView`（62KB）里，导致页面需要无数 Tab 切换才能完成一个完整的催收动作。

**建议拆分为两层：**
```
催收中心
├── 工作台（默认落地页）
│   ├── 今日待跟进  ← 按截止日期排序的行动清单
│   ├── 承诺到期预警  ← 今日/明日到期的还款承诺
│   └── 新增逾期  ← 过去24h新进入逾期的订单
├── 逾期台账  ← 全量逾期订单，支持按客户/金额/分级筛选
├── 承诺管理  ← 所有还款承诺的完整列表
└── 争议管理  ← 所有争议记录
```

**4.3.2 催收动作 Modal（CollectionActionModal 10KB）**
- 单个 Modal 承担"记录催收"+"设置承诺"+"标记争议"+"发提醒"四种动作，选项太多
- 建议：每种动作独立为快捷操作按钮（行内操作），只有"记录催收"需要打开 Modal 填写详情

**4.3.3 止货状态显示缺失**
- 客户止货（`creditHold`）和订单止货（`shipmentHold`）的状态在订单列表中没有视觉强提示
- 建议：被止货的客户名称旁显示红色 `⛔ 止货中` 角标，被止货的订单行用红色背景色标注

### 🟠 4.4 ProductionWorkspace（生产工作区）— 最复杂模块缺少引导

**4.4.1 BOM 管理**
- `formulationMode`（配方模式：按重量/按体积/按百分比）切换后，`percentage` 和 `quantityPerUnit` 字段的标签和验证规则应动态变化，但 UI 很可能是静态表单
- BOM 版本管理（`version: "v1"`）没有版本对比视图，用户无法看到 v1 和 v2 的配方差异
- `processJson` 和 `qualitySpecJson` 以 JSON 字段存储过程步骤和质检标准，但 UI 可能是一个大文本框，不是可操作的表单

**4.4.2 工单执行**
- 工单执行步骤（`ProductionProcessStep`）缺少实时进度追踪——当前处于哪个步骤、该步骤开始了多久
- 质检记录（`ProductionQualityCheck`）结果录入界面（合格/不合格/让步接收）缺少照片附件功能
- 生产损耗（`lossQuantity`）录入后应立即触发库存成本重算，需要一个确认弹窗说明影响范围

**4.4.3 BOM 与采购的连接缺失**
- 用户无法从工单界面直接看到"当前库存是否足够完成本次工单"
- 需要增加：工单创建时，系统自动检查每种原材料的当前库存，不足部分生成采购建议

### 🟠 4.5 WarehouseWorkspace（仓库工作区）— 空间结构模糊

**4.5.1 仓库→库区→库位三级结构缺少可视化**
- `Warehouse → Location` 是两级结构，但现实中通常需要"仓库→库区→货架→库位"四级。当前只有两级时，Location 的 `code` 字段需要用编码规则（如 `A-01-03`）隐式表达层级，UI 上应提供解析和树形展示。
- 库存分布视图应支持按仓库/库区查看存量热力图，而不只是一个平铺列表

**4.5.2 冷链批次管理**
- `ProductBatch.isColdChain` + `Shipment.isColdChain` 存在，但缺少温度超标报警 UI 和温度记录曲线
- 冷链批次在库位分配时应强制只能分配到标记为冷链的库位，这个业务规则是否在前端强制执行？

**4.5.3 库存调整（AdjustmentRecord）**
- `domain` 字段区分"库存调整"和"财务调整"，但用户在调整中心看到的是混合列表
- 建议：将库存盘盈盘亏调整从财务调整中完全分离，独立入口，分别审批流

### 🟠 4.6 BarterWorkspaceView（以货换货）— 概念复杂却没有引导

**4.6.1 协议与结算割裂**
`BarterAgreement`（协议）和 `BarterSettlement`（结算）是两个独立页面，但用户期望的操作流是：
```
[创建协议] → [执行多次部分结算] → [协议自动更新完成比例] → [最终结清]
```
当前 UI 很可能把"协议管理"和"结算记录"分在两个 Tab，用户需要来回切换查看同一协议的执行进度。

建议：协议详情页应内嵌结算时间线，右侧显示 `已执行 / 协议总额 = xx%` 的环形进度条。

**4.6.2 估价快照缺少可视化**
`BarterValuationSnapshot` 存储了市价快照，但用户如何知道"当前市价和协议定价之间的差异"？需要一个价格偏差警示，当市价变化超过协议价 ±5% 时高亮提示重新定价。

### 🟠 4.7 FinanceAnalyticsWorkspaceV2（财务分析）— 图表可信度不足

**4.7.1 缺少数据时间戳**
图表没有显示"数据最后更新于xx时间"，用户不知道看到的是实时数据还是缓存数据。

**4.7.2 多货币混算问题**
越南客户的订单用 VND 计价，当月销售额汇总图表如果把 VND 和 CNY 直接相加（未折算），数字会严重失真。必须在图表说明中标注"所有金额已按当日汇率折算为 CNY"。

**4.7.3 经销商分析（DealerAnalytics）**
三个租户（dealer_haiphong/dealer_hanoi/dealer_saigon）的数据如何在总部视图中汇总？当前的多租户架构（独立 `.db` 文件）意味着跨租户聚合查询需要在应用层合并，这部分逻辑是否有正确处理汇率差异？

### 🟡 4.8 CRM（客户关系管理）— 关键信息藏得太深

**4.8.1 客户概览缺少"风险仪表盘"**
`Customer` 有 `riskLevel`/`creditHold`/`shipmentHold`/`dunningLevel`/`overdueAmount` 等多个风险字段，但在客户列表和客户详情的首屏，用户看到的很可能是基本信息（名称、地址、联系人），风险信息被压缩在某个 Tab 里。

**建议：** 客户详情页顶部固定显示"风险状态条"：
```
[客户名] [活跃状态] ⚠️ 逾期 ¥45,000 | 催收等级 L2 | ⛔ 止货中 | 信用额度余额 ¥12,000/¥200,000
```

**4.8.2 客户公海池（poolState）操作无历史**
`poolState`（私有/公海）的变更有 `poolUpdatedAt`/`poolUpdatedBy` 记录，但没有完整的变更历史日志。销售互相"抢客户"时无法追责。

**4.8.3 客户搜索**
`nameAliases` 字段存储别名，但搜索时是否能匹配别名？`LIKE '%alias%'` 查询在 SQLite 上对 JSON 字符串的效果极差，需要提取别名到单独的 `CustomerAlias` 表。

### 🟡 4.9 AIAssistant — 能力边界不清

AI 助手模块（`AIAssistant-BLvkdfYj.js` 16KB）接入了 Gemini（`geminiService-BNalFbmi.js` 3.4KB），但用户很可能不知道：
- AI 助手能做什么（帮助写催收话术？分析逾期风险？查询订单？）
- AI 助手不能做什么（不能直接修改数据，不能做财务决策）
- AI 的回答是否基于实时系统数据还是训练数据

**修复：** AI 助手入口处显示能力卡片：
```
💬 你可以问我：
• "查询客户[名称]的未收款记录"    → 实时查询
• "起草一封催收邮件给[客户]"       → AI生成
• "分析本月销售趋势"               → 数据分析
• "本次发货的BOM材料消耗情况"      → 溯源查询
```

## 5. 系统级设计遗失细节

### 🔴 5.1 表单无"未保存变更"警告

用户在任何表单填写一半后误触侧边栏导航，表单内容**静默丢失**，没有任何 "你有未保存的更改，确定离开吗？" 提示。

**修复：**
```typescript
// React Router v6 实现
useBeforeUnload(isDirty, '你有未保存的更改，确定要离开吗？');
// 或自定义实现
useEffect(() => {
  if (!isDirty) return;
  const handler = (e: BeforeUnloadEvent) => { e.preventDefault(); };
  window.addEventListener('beforeunload', handler);
  return () => window.removeEventListener('beforeunload', handler);
}, [isDirty]);
```

---

### 🔴 5.2 错误边界（Error Boundary）缺失

任何一个子组件的未捕获 JS 错误会导致整个根节点 `#root` 崩溃，用户看到白屏。102KB 的 `SalesOrders` 如果在渲染时遇到 `undefined.totalAmount`，整个应用崩溃。

**修复：** 对每个 Workspace 级别的路由组件包裹独立的 `ErrorBoundary`：
```tsx
<ErrorBoundary fallback={<WorkspaceCrashPage module="销售订单" />}>
  <SalesOrders />
</ErrorBoundary>
```
`WorkspaceCrashPage` 显示友好信息 + "刷新此模块"按钮，不影响其他模块的正常使用。

---

### 🟠 5.3 数字和日期格式未越南本地化

系统服务越南三个经销商，但：
- 金额格式：应为 `₫12.500.000`（越南用点分千位），而非 `₫12,500,000`（英美习惯）
- 日期格式：越南习惯 `08/06/2026`（日/月/年），系统可能显示为 `2026-06-08`
- 数字小数点：越南用逗号作小数点（`12.500,50`），需根据 locale 切换

**修复：** 全局使用 `Intl.NumberFormat` 和 `Intl.DateTimeFormat`，增加语言切换（zh-CN / vi-VN / en-US），并在首次登录时检测浏览器语言自动设置。

---

### 🟠 5.4 打印/导出覆盖率不足

业务场景中经常需要打印的文件：

| 文件 | 当前状态 | 缺失内容 |
|------|----------|----------|
| 销售订单确认单 | 可能有 | 公司抬头/印章位置 |
| 发货清单 | 可能有 | 冷链温度要求/特殊说明 |
| 采购订单 | 未知 | 供应商签收栏 |
| 催收函 | 未知 | 法律声明/逾期利率条款 |
| 易货协议 | 未知 | 双方签字栏/见证人 |
| 生产工单 | 未知 | 操作人签名/质检记录 |

每种打印模板应支持：A4/A5 纸张、中文/越南文双语、公司 Logo 配置。

### 🟠 5.5 批量操作缺失

以下高频操作在当前可能全部只支持逐条操作：
- 批量确认订单（将多个 `pending` 订单一次性变为 `confirmed`）
- 批量发送催收提醒
- 批量打印发货标签
- 批量更新产品价格（加价 x%）

### 🟠 5.6 键盘快捷键完全缺失

ERP 用户是重度使用者，键盘效率至关重要：

```
建议快捷键：
Ctrl+N          → 在当前模块新建记录
Ctrl+S          → 保存当前表单
Ctrl+F          → 聚焦搜索框
Ctrl+Enter      → 提交表单（替代鼠标点击保存按钮）

F5              → 刷新当前列表数据
```

### 🟡 5.7 加载状态和空状态设计缺失

**加载状态：** 数据表格在等待 API 响应时，应显示 Skeleton（骨架屏）而非空表格或转圈圈。骨架屏让用户知道"数据正在加载"而不是"页面挂了"。

**空状态：** 每个列表在真正没有数据时（如新系统刚启动），应显示引导性空状态：
```
📋 暂无订单
还没有创建任何订单
[立即创建第一个订单 →]
```
而不是一个没有任何解释的空表格。

---

### 🟡 5.8 全局搜索（scopedSearch）能力未充分利用

`dist/assets/scopedSearch-j8XTs-Dw.js`（262字节）体积极小，说明全局搜索功能几乎没有实现。

建议实现命令面板（Command Palette）风格的全局搜索：
- `Ctrl+K` 唤起
- 支持搜索：客户名/订单号/工单号/供应商名/批次号
- 支持快捷动作：`新建客户`/`新建订单`/`查看今日到期`

---

### 🟡 5.9 通知系统缺失

系统内没有通知机制。以下事件应触发站内通知：
- 新订单需要审核
- 逾期催收截止日到达
- 还款承诺到期未履行
- 生产工单超期
- 备份失败（管理员）
- 磁盘空间不足（管理员）

即使是最简单的顶部通知中心（铃铛图标 + 未读数量角标 + 下拉列表）也能大幅提升使用体验。

---

### 🟡 5.10 移交/交接场景设计缺失

`Customer.poolState`（私有/公海）表明系统有客户所有权转移的概念，但：
- 销售人员离职时如何批量将其客户转给新人？
- 临时请假时如何委托他人处理自己的跟进任务？
这两个场景没有专门的界面支持，只能依赖管理员逐条修改数据库记录。
