# 反思治理与冻结边界

日期：2026-06-09

## 反思结论

最近三批未保存治理解决了真实的静默丢单问题，但也暴露出治理方式需要收紧：

1. 不能只验证“有修改会提醒”，还必须验证“没有修改不会提醒”。
2. 不能按页面数量机械接入。只有存在用户输入、尚未落库、离开后会丢失三个条件同时成立时才登记。
3. 自动带入、列表筛选、选中行、分页、只读详情不能算未保存业务数据。
4. 每个保存动作必须同时验证落库回读和表单基线重置，否则会出现保存成功后仍反复提醒。
5. 通用审计脚本达到 300 行后停止继续堆场景；后续复杂业务应放进对应模块的完整链路审计。

## 本次纠偏

- 补充干净页面直接离开的反向审计，覆盖生产、采购、调账和仓储。
- 修复质检保存后没有恢复默认“通过”的问题，避免下一张质检继承上次“不合格”状态。
- 保留现有单一 `useUnsavedForm` 协议，不新增状态库、事件总线或表单框架。
- 将未保存正反向审计纳入 Phase 3 浏览器门禁和每日浏览器巡检，避免只靠人工记忆执行。
- 稳定包新增 `SOURCE_MANIFEST.json`，冻结审计校验源码提交、脏状态、前后端产物哈希和压缩包时序。

## 冻结边界

未满足下列证据前，不再扩大接入范围：

1. 能复现静默丢失。
2. 能指出具体输入状态和离开路径。
3. 能提供“修改后拦截”和“干净状态不拦截”两类测试。
4. 保存成功后能通过浏览器或 API 回读。

发货、回款、退货不再整模块批量接入，后续按实际缺陷逐项治理。
