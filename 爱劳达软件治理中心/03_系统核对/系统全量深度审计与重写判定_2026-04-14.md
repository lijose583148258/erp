# 系统全量深度审计与重写判定（2026-04-14）

## 结论

当前系统不是全盘报废，也不是简单补几个按钮就能稳定上线。真实状态是：主链已经成型，但入口、数据库、接口契约、权限、主数据、运行脚本上叠了较多兼容层和临时补丁，维护者容易找错文件、跑错库、测到 mock、或被后台残留进程误导。

本轮审计采用多角色并行：
- 前端入口与 UI 架构审计
- 后端接口与数据库链路审计
- ERP 业务域与闭环审计
- 主线程运行稳定性复核

## 当前硬验证

- `tsc --noEmit --pretty false`：失败。
- 失败点：`pages/TeamManagement.current.tsx` JSX 结构损坏。
- `npm run build:backend`：通过。
- `npm run db:manage -- status`：通过。
- 当前真实 SQLite：`D:/AilaoDaRuntime/stable.db`。

## P0：立刻影响维护和运行

| 问题 | 判断 | 处理方式 |
|---|---|---|
| `pages/TeamManagement.current.tsx` 真实入口编译失败 | 团队管理菜单会加载它，不能当历史文件看 | 立刻修复，再合并回 `TeamManagement.tsx` |
| 开发环境可能默认走 mock | 容易造成“页面能点但真实库没写入”的假通过 | 统一真实/模拟开关，测试默认真实后端 |
| 数据库文件太多 | `stable.db`、`dev.db`、`main.db`、`fresh.db`、`runtime-db` 并存，容易看错库 | 固定唯一运行库，其他归档或标记只读 |
| Schema 修复脚本和真实数据修复混在一起 | `repair` 可能对真实库做硬编码数据修复 | 拆成只读审计、Schema 修复、数据种子三条命令 |
| 权限策略分散 | CRM、订单、回款、发货可见范围没有统一策略层 | 建统一权限策略模块 |

## P1：会影响上线稳定

| 问题 | 判断 | 处理方式 |
|---|---|---|
| `.current/.live/.clean/.fixed` 文件仍在真实链路附近 | 维护者容易改错入口 | 合并到无后缀 canonical 文件，旧文件移入归档 |
| 前后端接口契约分散 | Prisma、Zod、controller、前端 service、types 多处重复 | 建共享 DTO 或统一 API 契约层 |
| 订单并发和幂等不足 | 双击/并发可能绕过信用校验或重复写 | 订单、付款、发货、货抵、导入统一加幂等 |
| 客户/供应商多名多址多联系人仍是 JSON + 旧字段混合 | 短期能用，长期搜索、审计、导入导出会失真 | 先客户后供应商，实体化名称/地址/联系人 |
| 后端仍有乱码注释和错误文案 | 人工测试无法判断真实失败原因 | 三步法清污：翻译、判断、修复 |
| 端口和启动路径靠脚本纠偏 | 单独跑 `dev:backend` 容易跑到 5000，而前端打 5001 | 固定环境输出和启动前健康检查 |

## P2：治理和可维护性问题

| 问题 | 判断 | 处理方式 |
|---|---|---|
| `types.ts` 和大页面文件过大 | 不是立刻坏，但维护成本高 | 按业务域拆类型和页面区块 |
| 登录页和主系统两套语言体系 | 语言切换后仍可能漏文案 | 登录页接入统一 i18n |
| Service Worker 和旧 dist 可能造成旧壳缓存 | 人工点测可能看到旧页面 | 测试脚本加入缓存清理或版本校验 |
| UI 状态三态不统一 | 容易出现 `undefined`、假 0、空白页 | 统一 loading/error/empty 模式 |

## 补丁可保留

这些不是屎山，短期可以保留：
- `App.tsx` 显式导入 `useAppShell.tsx`。
- `app/appContent.tsx` + `app/activePathRegistry.ts` 的集中入口模式。
- 回款、生产、货抵页面的加载态兜底。
- 订单基础状态机、付款核销、信用拦截。
- 货抵支付的报价、审批、过账、冲销状态思路。
- 发货签收凭证上传和状态推进。
- `runtime-schema-audit` 作为只读审计工具。

## 需要重写或模块级合并

这些继续打补丁会越来越难维护：
- `TeamManagement.current.tsx`：先修编译，再合并回 `TeamManagement.tsx`。
- `BarterWorkspace.clean.tsx`：迁回 `BarterWorkspace.tsx`。
- `Samples.current.tsx`：迁回 `Samples.tsx`。
- `CRMCreateModal.live.tsx`、`CRMCustomerDrawer.live.tsx`、`SalesOrderColumns.live.tsx`：迁回无后缀文件。
- 客户/供应商主数据：从 JSON 混合字段升级为主表 + 名称表 + 地址表 + 联系人表。
- 统一权限策略：角色、业务线、客户池、记录级可见范围集中治理。
- API 契约层：route、validator、service、前端 DTO 统一。
- 批量导入导出：批次任务、幂等、结果明细、失败回滚。
- 货抵支付：估值凭证、库存/采购/销售/财务联动和冲销对账。

## 后续按包执行顺序

1. P0 编译恢复包  
修 `TeamManagement.current.tsx`，让 `tsc --noEmit` 先恢复通过。

2. 真实运行源治理包  
固定真实后端、真实数据库、真实端口，关闭测试默认 mock 误导。

3. 入口收敛包  
把 `.current/.live/.clean` 合并回 canonical 文件，旧文件归档。

4. 数据库治理包  
拆开 Schema 审计、Schema 修复、数据种子；明确 `stable.db` 是唯一运行库。

5. 接口契约包  
优先修 mock 默认值、5000/5001、export token、asset balance、shipping receipt/status。

6. 权限与客户池包  
统一 `admin/manager/sales/warehouse/finance`、`direct/channel/mixed`、公海/内池/私海策略。

7. 主数据稳定包  
客户先实体化，供应商复用同一套规则，但搜索不能串域。

8. 事务与幂等包  
订单、付款、发货、货抵、批量导入统一加幂等和事务内二次校验。

9. UI 与语言清污包  
统一三态、后端错误文案、登录页语言、CRM 硬编码标签。

10. 浏览器级人工点测包  
逐页跑真实数据输入、读回、刷新、重复提交、异常恢复。

## 判断

这套系统可以救，且不需要从零重写。但必须先停止“边跑边补”的方式，改成“主链唯一化 + 按包收敛 + 每包验证”。真正需要重写的是主数据、权限、接口契约、批量任务、货抵深闭环；现有订单、回款、发货、货抵状态机可以作为基础保留。
