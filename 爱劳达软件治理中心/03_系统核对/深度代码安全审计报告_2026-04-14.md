## 二、🔴 严重问题（Critical — 必须立即修复）

### C1. JWT_SECRET 硬编码弱密钥

| 文件 | 位置 |
|------|------|
| `backend/.env` | L9 |
| `backend/src/utils/jwt.ts` | L3 |

**现状**：`.env` 文件中 `JWT_SECRET=pro-sales-secret-key-2024-very-secure`，仅 39 字符且为可猜测的英文短语。代码中 fallback 值为 `'your-secret-key'`。

**风险**：攻击者可伪造任意用户的 JWT Access Token，绕过全部认证。

**修复**：使用 `crypto.randomBytes(64).toString('hex')` 生成 128 字符十六进制密钥，最低 256 位随机熵。

---

### C2. Refresh Token 使用不安全随机数生成

| 文件 | 位置 |
|------|------|
| `backend/src/controllers/auth.controller.ts` | L455-461 |

```typescript
// 当前代码 — Math.random() 不是加密安全的 PRNG
result += chars.charAt(Math.floor(Math.random() * chars.length));
```

**风险**：`Math.random()` 基于 xoshiro128 算法，输出可被回溯预测。攻击者可暴力碰撞 refresh token 获取持久会话。

**修复**：
```typescript
import crypto from 'crypto';
const generateRefreshToken = () => crypto.randomBytes(48).toString('base64url');
```

## 三、🟡 重要问题（Major — 近期需修复）

### M1. Refresh Token 无轮转机制（网络调研新增 🆕）

**行业标准**：每次使用 Refresh Token 换取新 Access Token 时，应同时签发新的 Refresh Token 并销毁旧的（Token Rotation），并实现重用检测（Reuse Detection）。

**现状**：`refreshTokenStore` 仅在显式刷新时删除旧 token 并生成新 token，但无法检测 token 被盗后的重用行为。无 "token family" 概念。

---

### M2. Timber 控制器使用裸 `Request` 而非 `AuthRequest`（人工审查 🔍）

| 文件 | 位置 |
|------|------|
| `timber.controller.ts` L1,L10,L31,L59 |

```typescript
import { Request, Response } from 'express';
async calculateVolume(req: Request, res: Response) { ... }
async convertToPurchase(req: Request, res: Response) { ... }
```

**问题**：`TimberController` 的三个函数全部使用 `express.Request` 而非 `AuthRequest`。这意味着：
- 即使路由挂载了 authenticate 中间件，控制器中 `req.user` 为 `undefined` — 审计日志无法记录操作人
- `convertToPurchase` 一键转采购功能无任何操作者追踪

## 六、只有人工审查才能发现的深层问题（专项清单 🔍）

以下问题无法通过任何自动化工具或 grep 搜索发现，必须依赖逐行人工阅读和业务逻辑推理：

### H1. 信用引擎的 "零额度陷阱"

| 文件 | 位置 |
|------|------|
| `CreditEngine.ts` L94-99 |

```typescript
if (exposure.creditLimit > 0) {
    projectedUsage = (exposure.totalExposure + newOrderAmount) / exposure.creditLimit;
} else {
    projectedUsage = (exposure.totalExposure + newOrderAmount) > 0 ? 1.01 : 0;
}
```

**问题**：当客户 `creditLimit = 0` 时，任何金额 > 0 的订单都会被拒绝（projectedUsage = 1.01）。但新客户默认 `creditLimit = null`（Schema 定义为 `Float?`），此时 `customer?.creditLimit || 0` 会将 null 转为 0，导致**所有新客户只要有第一笔订单就会被信用引擎拦截**。

**影响**：销售人员新建客户后无法下第一笔订单，除非管理员先设置信用额度。

---

### H2. 订单状态机与发货控制的语义不一致

| 订单状态机 | 发货控制器 |
|-----------|-----------|
| `delivered` = 已妥投（终态） | `delivered` = 已签收 |
| `completed` 不在状态机中 | `completeOrder` 将 shipped→delivered |
| 但信用引擎 L31：`status: { notIn: ['completed', 'cancelled'] }` | |

**问题**：信用引擎排除了 `completed` 状态的订单，但订单状态机中不存在 `completed` 状态。这意味着**所有已妥投(delivered)的订单会永远留在信用敞口计算中**，直到全额付款。设计意图可能正确，但状态命名不统一容易引发未来维护错误。

---

### H3. 发货单签收凭证覆盖 shippedAt 时间戳

| 文件 | 位置 |
|------|------|
| `shipping.controller.ts` L306 |

```typescript
data: {
    status: 'delivered',
    shippedAt: new Date(),     // ← 签收时覆盖了发货时间
    deliveredAt: new Date(),
}
```

**问题**：当上传签收凭证时，`shippedAt` 被覆盖为当前时间。如果发货单之前已经通过 `updateStatus('in_transit')` 设置了真正的发货时间，此处覆盖会导致**物流时效统计失真**（发货时间 = 签收时间 = 0 天时效）。

---

### H4. 付款验证后订单金额未同步更新

| 文件 | 位置 |
|------|------|
| `order.controller.ts` L447-477 |

`verifyPayment` 调用了 `CollectionStateService.verifyPaymentRecord` 来验证付款记录，但控制器层面没有显式更新 `order.paidAmount` 和 `order.paymentStatus`。

**假设** `CollectionStateService` 内部处理了同步——但如果没有，已验证的付款不会反映到订单级统计中。这需要逐层追踪验证。

### H5. 自审批漏洞 — 用户可审批自己创建的记录（人工审查 🔍）

现有代码中未发现 "创建者不能审批自己创建的记录" 的校验逻辑。例如：

- 销售人员创建订单 → 自己确认订单（`updateOrderStatus`无此检查）
- 付款提交 → 自行验证付款（`verifyPayment` 仅检查权限角色，不检查是否同一人）

**OWASP 归类**：职责分离 (SoD) 缺陷。ERP 系统应强制实施 "四眼原则"。

---

### H6. 客户控制器中 `ensureCustomerContactsColumn` 的竞态条件

| 文件 | 位置 |
|------|------|
| `customer.controller.ts` L596-610 |

```typescript
let customerContactsColumnReady: Promise<void> | null = null;

function ensureCustomerContactsColumn() {
    if (!customerContactsColumnReady) {
        customerContactsColumnReady = (async () => { ... })().catch((error) => {
            customerContactsColumnReady = null;
            throw error;
        });
    }
    await customerContactsColumnReady;
}
```

**问题**：多个并发请求同时到达时，多次 `ALTER TABLE` 可能被竞争发起。虽然 SQLite 的 DDL 是串行的不会导致数据损坏，但会产生 "duplicate column name" 错误。`catch` 中将 `customerContactsColumnReady` 重置为 null，下次请求会重试，但中间的请求会收到 500 错误。

### H7. 合同 OCR 数据直存 Base64 到 fileUrl（人工审查 🔍）

| 文件 | 位置 |
|------|------|
| `Contracts.tsx` L68-70 |

```tsx
await contractService.create({
    ...ocrResult,
    fileUrl: ocrImage,   // ocrImage = FileReader.readAsDataURL 的结果
});
```

**问题**：`ocrImage` 是完整的 Base64 Data URL（可能 5-10 MB），直接作为 `fileUrl` 字符串存入数据库。这会导致：
- SQLite 单行数据膨胀，查询性能急剧下降
- 合同列表查询时 `select *` 会拉取所有 Base64 数据
- 与 `shipping.controller.ts` 的做法不一致（后者存文件到磁盘，DB 只存路径）

### H8. 付款记录金额校验存在浮点精度问题（人工审查 🔍）

| 文件 | 位置 |
|------|------|
| `order.controller.ts` L377 |

```typescript
if (paymentAmount - outstanding > 0.01) {
    return res.status(400).json({ message: 'Payment amount exceeds outstanding balance.' });
}
```

**问题**：使用 `0.01` 的硬编码容差：
- 多币种场景下 VND（越南盾）最小单位是 1 VND，0.01 VND 不存在
- CNY 场景下 0.01 元是合法金额但永远不会触发报错
- 应按 `currency` 动态设置精度阈值
