# 🔍 系统深层业务隐患专项审查报告（已修复）

> 审查日期：2026-04-14
> 状态：✅ 全部 8 项已修复

---

## 🔴 P1 — 高风险（影响业务正确性或安全性）

### 1. ✅ 订单状态机语义冲突（H2）— 已修复

**修复文件**: `order.controller.ts`

**原问题**: `delivered` 同时表达「物流签收」和「手动结案」两种含义

**修复方案**: 
- 引入独立的 `completed` 终态（手动结案专用）
- `delivered` 仅由 `syncOrderShipmentState` 物流自动设置
- `completeOrder` 方法现在从 `shipped/delivered` → `completed`
- 状态转换矩阵更新：`shipped → [delivered, completed]`，`delivered → [completed]`

---

### 2. ✅ 职责分离（SoD）缺失（H5）— 已修复

**修复文件**: `order.controller.ts`

**修复内容**:
- `updateOrderStatus`：创建者不能审批自己的订单（`createdBy === userId` 且目标状态为 `confirmed` 时返回 403）
- `verifyPayment`：订单创建者不能验证自己订单的付款记录

---

### 3. ✅ Token 黑名单 / RefreshToken 内存泄漏（L5）— 已修复

**修复文件**: `auth.controller.ts`

**修复方案**: 添加每小时执行的定时清理器
- 清理黑名单中 JWT 过期时间已过的 token（解码 payload.exp 对比）
- 清理 refreshTokenStore 中 expiresAt 已过的条目
- 每次清理后记录日志显示清理数量和剩余数量

---

### 4. ✅ Schema 修复脚本 PRAGMA 拼接注入 — 已修复

**修复文件**: `runtime-schema-repair.ts`

**修复方案**: 在 `columnExists()` 函数中添加 `KNOWN_TABLES` 白名单（17 个已知表名），非白名单表名调用时抛出异常。

---

## 🟡 P2 — 中风险（影响数据质量或性能）

### 5. ✅ 信用引擎 null 与 0 的业务语义歧义 — 已修复

**修复文件**: `CreditEngine.ts`

**修复方案**: `checkOrder()` 方法现在明确区分三种信用状态：
| 值 | 业务含义 | 修复后行为 |
|---|---------|-----------|
| `null` | 未设定额度 | 拦截：「请联系管理员先设定客户授信额度」 |
| `0` | 明确禁止赊账 | 拒绝：「客户信用额度为零，不能新增订单」 |
| `> 0` | 正常额度 | 常规敞口检查 |

---

### 6. ✅ OCR 合同图片 Base64 直存数据库（H7）— 已修复

**修复文件**: `contract.controller.ts`

**修复方案**: 
- 新增 `persistBase64ToDisk()` 函数：检测 `fileUrl` 是否以 `data:` 开头
- 若是 base64，自动解码写入 `{uploadDir}/contracts/` 目录
- 数据库只存相对路径 `/uploads/contracts/contract_xxx.png`
- 已有的 express.static 挂载确保文件可直接通过 URL 访问
- 支持 image/* 和 application/pdf 格式
- 文件大小超过 5MB 时记录警告

---

### 7. ✅ 财务精度问题 — JavaScript 浮点 vs 货币计算 — 已修复

**修复文件**: `collection-state.service.ts`

**修复方案**: 
- 新增 `toCents()` 和 `determinePaymentStatus()` 工具函数
- 将金额乘以 100 取整后再比较（整数运算无浮点误差）
- 替换了两处 `paidAmount >= finalAmount` 的直接比较
- 覆盖 `recalculateOrderPaymentState` 和 `verifyPaymentRecord` 事务内的判定
