# 系统演变路径图

## 1. 祖先版本

祖先版本是 [F:/爱牢达_CleanMigration.zip](F:/爱牢达_CleanMigration.zip)。

这个包不是空壳，而是一个已经具备完整业务雏形的迁移期原型：

- 前端是 `Vite + React + TypeScript`
- 后端是 `Express + Prisma + TypeScript`
- 已经有 `controllers`、`routes`、`middleware`、`database` 这些后端分层
- 已经有 `translations.ts`
- 已经有 AI、OCR、样品、订单、CRM、风控、物流、售后、资产、采购、团队、审计等业务面
- 已经有部署文档、测试文档、文件分类清单
- 后端还保留了多租户迁移脚本 `backend/prisma/migrations/multiTenantMigration.ts`

这说明最早的系统不是从零开始，而是已经进入“迁移期原型系统”阶段。

## 2. 祖先版本的结构特征

### 业务面

祖先包里已经具备这些主域：

- `CRM`
- `Orders`
- `Risk Control`
- `Samples`
- `Shipping`
- `RMA`
- `Team`
- `Audit Logs`
- `Assets`
- `Procurement`
- `Timber Workspace`

### 技术面

- 根目录是单体工作区
- 前端和后端共用一个仓库
- 数据库围绕 `Prisma` 和 `SQLite` / 多租户迁移脚本组织
- 配套了部署、测试、分类清单文档

### 说明

祖先版本已经不是“演示页”，而是“业务骨架已出现、治理边界还不稳定”的形态。

## 3. 演变阶段

### 阶段 A：祖先原型

来源：`爱牢达_CleanMigration.zip`

目标：把核心业务和部署链路先跑起来。

特征：

- 模块齐，但边界不清
- 文档多，但没有统一治理入口
- 多租户与迁移脚本存在，但命令口径分散
- 翻译、部署、测试、归档混在一起

### 阶段 B：治理收口

当前仓库已进入这一阶段。

目标：先把“谁是主线、谁是支撑、谁是历史”分清。

已经做的事：

- 建立 [爱劳达软件治理中心](F:/爱牢达/爱劳达软件治理中心/README.md)
- 把方案书、对照表、阶段判定、清理清单、接入清单统一归档
- 把主线拆成包 0 到包 5
- 把根目录、历史归档、文档归档、测试目录分层
- 把 `allowJs`、Prisma 版本、数据库脚本入口、翻译资源做统一

### 阶段 C：主线补全

当前正在推进的阶段。

主线顺序已经明确为：

1. 数据库底座
2. 回款闭环
3. 生产管理主链路
4. 财务报表与经营分析
5. 部署稳定性与上线验收

## 4. 当前版与祖先版的差异

### 保留下来的东西

- 前后端分层
- 订单、CRM、物流、样品、售后、资产、审计、采购、团队等业务骨架
- AI 和多语言能力
- 部署与测试意识

### 被强化的东西

- 治理中心
- 包级主线
- 文档分区
- 单机 / 线上部署统一口径
- 数据库底座统一命令
- 回款闭环和异常处理的执行表

### 被清理的东西

- 旧报告口径
- 历史打包产物
- 目录混杂
- 命令分叉
- 翻译重复键和结构性重复

## 5. 当前结构判断

现在的系统不是“从零做起来”，而是：

- 祖先版本已经有业务原型
- 当前版本在做治理收口
- 下一步是在收口后的主线里继续补完整闭环

更准确地说：

> 现在不是“新做一个系统”，而是“把祖先原型收成一个可长期维护的 ERP / CRM / 经营系统”。

## 6. 建议保留的演变原则

- 先保主线，再扩支撑
- 先分清边界，再加能力
- 先统一入口，再做细分页面
- 先保证单机可用，再考虑线上部署
- 先保留审计留痕，再做自动化优化

## 7. 下一步建议

1. 继续包 3：生产主链路
2. 在生产链路里再补 BOM、工单、工序、损耗、库存联动
3. 再回到财务报表与经营分析
4. 最后做部署验收和发布收口
