# 乱码审计与修复 SOP

## 1. 目的

本 SOP 用于把爱劳达 ERP+CRM 中所有乱码、脱钩、旧入口误挂载、打包缓存污染、终端显示误判等问题，统一收口为一套固定制度。

本制度不是建议，而是执行门禁。

## 2. 适用范围

适用于以下情况：

- 页面出现中文乱码、符号异常、状态口径错乱
- PowerShell、日志、报告、JSON、CSV 中出现疑似乱码
- 页面点击后跳到旧样式、旧页面、裸 HTML 页面
- 编译错误与乱码同时出现
- 修复过程中怀疑“不是源码坏，而是显示层坏”
- 审计报告写着通过，但人工浏览器看到仍有脱钩

## 3. 固定三步法

任何乱码问题都必须按以下顺序处理：

### 第一步：先翻译

目标是确认原意，不是立即改代码。

必须先回答：

- 这段乱码原本想表达什么业务语义
- 它是客户可见文案、内部错误提示、字段标签、状态值，还是注释
- 它影响的是展示、逻辑判断，还是编译

禁止事项：

- 禁止一看到乱码就全局替换
- 禁止未翻译原意就改状态枚举、字段键名、接口字段

### 第二步：再判断

必须先完成四类判断：

1. 活跃链判断  
   这段内容是否位于当前真实运行链：
   - 当前路由入口
   - 当前活跃组件
   - 当前 service / controller / validator
   - 当前构建脚本 / 验收脚本

2. 层级判断  
   先确认问题在哪一层：
   - 源文件真损坏
   - PowerShell 或编辑器显示层误解码
   - 浏览器缓存 / dist / 旧 runtime 污染
   - 旧文件被误挂载
   - 报告产物编码错误

3. 风险判断  
   必须分清：
   - 只是文案脏
   - 已经影响语法
   - 已经影响业务判断
   - 已经影响写入回读

4. 范围判断  
   必须分清：
   - 单点问题
   - 单文件整片污染
   - 模块级污染
   - 运行链误指向

### 第三步：最后修复

只允许在完成翻译和判断之后修复。

修复顺序固定如下：

1. 先修活跃链
2. 先修会导致编译失败或真实页面脱钩的问题
3. 再修高频可见文案
4. 最后清理旧文件、旧桥接、旧报告污染

## 4. 执行门禁

### 4.1 单文件闭环

乱码修复必须单文件闭环执行：

1. 锁定一个文件
2. 完成翻译
3. 完成判断
4. 修复
5. 立刻验证

未完成当前文件验证前，不进入下一个坏文件。

### 4.2 补丁止损

当出现以下任一情况时，禁止继续缝补：

- 同一文件已出现多次补丁叠加
- 字符串、模板字符串、TSX 标签已断裂
- 修一次多出两个新错误
- 同一文件连续两次修复后仍无法通过 `tsc --noEmit`

此时强制切换为：

- 局部重写坏段
- 或隔离旧坏段，再以业务语义重建最小可用块

### 4.3 时间门禁

任何一步超过 5 分钟没有明确结果，必须判定一次是否卡住：

- 继续等待是否有证据支持
- 是否是搜索范围过大
- 是否是命令卡死
- 是否需要缩小到单文件

禁止长时间挂跑后再回头解释。

## 5. 修复后强制验证

每个文件修完至少执行以下验证中的适用项：

- `tsc --noEmit`
- `npm run build`
- `npm run build:backend`
- 稳定版重启
- 浏览器人工点测
- 写入后刷新回读
- 双端口核对

如果修的是：

- 前端页面：必须看真实页面
- service / controller / validator：必须做接口或页面回读验证
- 脚本 / 报告：必须看产物内容是否正常

## 6. 文件分类规则

### 可以直接修

- 当前活跃页面
- 当前活跃 hooks / services / controllers / validators
- 当前构建与验收脚本
- 当前治理中心“当前版”文档

### 先隔离再决定

- `.bak`
- `.old`
- `.current`
- `.live`
- `.clean`
- 历史归档目录
- 旧 `src`
- 旧 `output`

### 禁止误判为源码损坏

- 终端输出乱码但源文件正常
- 二进制搜索命中内容
- 旧报告文件历史编码污染
- 浏览器缓存导致的假回退

## 7. 台账制度

每次乱码修复必须登记：

- 问题编号
- 文件路径
- 原始乱码
- 翻译后的原意
- 判断结论
- 采用修法
- 验证结果
- 是否涉及 HarnessEngine / 旧入口 / 旧 runtime

台账文件统一使用：

- `爱劳达软件治理中心/06_版本治理/乱码与隔离治理台账-当前版.md`

## 8. 与 HarnessEngine 的关系

如果乱码问题涉及浏览器审计、验收脚本、自动填充、假数据、测试注入、批量点测、恢复脚本，则必须同时检查：

- 是否被 HarnessEngine 误接入主运行链
- 是否由 HarnessEngine 写入了不该存在的 mock 状态
- 是否是测试壳替代了正式壳
- 是否审计脚本报告“假绿”

只要与 HarnessEngine 有关，必须联动参考：

- `爱劳达软件治理中心/06_版本治理/HarnessEngine隔离架构治理规范-当前版.md`

## 9. 一句话原则

乱码问题一律按：

先翻译，后判断，再修复；
先活跃链，后外围；
先保编译与真实业务，后保文案与整洁。
